# Stage 67: Identifier Resolution

## In one line
Static semantic resolution pass via AST traversal that precomputes lexical scope hop counts to decouple variable binding from runtime environment mutations.

## Self-test (cover the answers below and answer these first)
- Why does pure dynamic environment lookup cause late-declared local variables to shadow earlier closures in the same block?
- What data structure does `Resolver` use to track scopes during semantic analysis?
- If a variable expression is not found in any entry of `scopes`, where does the interpreter resolve it at runtime?

## The problem it solved
In dynamic environment lookup, if a function declaration captures a block's environment and is invoked after a new variable of the same name is declared in that same block, dynamic lookup finds the newly declared variable instead of the outer variable that was in scope when the function was created. Static identifier resolution resolves each identifier reference to a fixed ancestor distance at compile time, guaranteeing true lexical scoping.

## Concepts (the transferable part)
- **Separate Semantic Resolution Pass**:
  Before interpreting statements, `Resolver` walks the AST:
  ```java
  Resolver resolver = new Resolver(interpreter);
  resolver.resolve(statements);
  ```
- **Scope Stack & Variable State**:
  Scopes are modeled as a stack of maps:
  `Stack<Map<String, Boolean>> scopes = new Stack<>();`
  - `false`: Declared but not yet defined (disallows `var a = a;`).
  - `true`: Fully defined and ready to read.
- **Resolving Local vs. Global**:
  ```java
  private void resolveLocal(Expr expr, Token name) {
      for (int i = scopes.size() - 1; i >= 0; i--) {
          if (scopes.get(i).containsKey(name.lexeme)) {
              interpreter.resolve(expr, scopes.size() - 1 - i);
              return;
          }
      }
  }
  ```
  If found, `depth = scopes.size() - 1 - i` is recorded in `Interpreter.locals (Map<Expr, Integer>)`.
  If not found, it is treated as a global variable.
- **Direct Ancestor Access**:
  At runtime, `Interpreter` checks `locals.get(expr)`:
  - If non-null: `environment.getAt(distance, name.lexeme)` directly jumps up `distance` enclosing links.
  - If null: resolves in `globals`.

## What breaks it (failure modes)
- Storing variable names instead of expression AST node instances in `locals`.
- Forgetting to resolve statements inside function bodies or conditionals.
- Resolving global variables into `locals` with incorrect depth instead of letting them fall back to `globals`.

## Tradeoffs
- Requires a full AST traversal before execution starts, adding compile-time latency, but guarantees correct lexical scoping and faster runtime variable lookup by bypassing dynamic name walking.

## CLI / Protocol format
- Command: `./your_program.sh run <file.lox>`
- Input:
  ```lox
  fun global() {
    print "global";
  }
  {
    fun f() {
      global();
    }
    f();
    fun global() {
      print "local";
    }
    f();
  }
  ```
- Stdout:
  ```
  global
  global
  ```
- Exit code: `0`
