# Stage 36: Runtime Errors: Binary Operators (1/2)

## In one line
Enforcing numeric operands on binary multiplication (`*`) and division (`/`), reporting `Operands must be numbers.` and terminating with exit code 70 on type violations.

## Self-test (cover the answers below and answer these first)
- Does evaluating `"foo" * 42` result in string repetition or a runtime error in Lox?
- What error message and exit code does Lox produce when binary `/` is given boolean operands?
- Are binary operand checks executed before or after evaluating both left and right expressions?

## The problem it solved
Unlike dynamically typed languages that coerce types or overload `*` for string repetition (like Python), Lox strictly requires both operands of `*` and `/` to be numbers. Providing non-number operands must trigger a `RuntimeError` with line tracking and exit code 70.

## Concepts (the transferable part)
- **Binary Operand Type Validation**:
  ```java
  private void checkNumberOperands(Token operator, Object left, Object right) {
      if (left instanceof Double && right instanceof Double) return;
      throw new RuntimeError(operator, "Operands must be numbers.");
  }
  ```
- **Operator Handler Integration**:
  ```java
  case SLASH:
      checkNumberOperands(expr.operator, left, right);
      return (double) left / (double) right;
  case STAR:
      checkNumberOperands(expr.operator, left, right);
      return (double) left * (double) right;
  ```
- **Execution Order**:
  Both operands are evaluated first via post-order AST traversal (`evaluate(expr.left)` then `evaluate(expr.right)`). Only then are operand types validated before applying the operation.

## What breaks it (failure modes)
- Throwing `ClassCastException` by directly casting `(double) left` without checking `instanceof Double`.
- Checking only one operand or returning incorrect error message (`Operand must be a number.` vs `Operands must be numbers.`).
- Emitting exit code 65 instead of 70.

## Tradeoffs
- Eager operand evaluation vs short-circuiting: Arithmetic operators evaluate both subtrees unconditionally, unlike logical `and` / `or` which short-circuit.

## CLI / Protocol format
- Command: `./your_program.sh evaluate <file.lox>`
- Input: `"foo" / 42`
- Stderr:
  ```
  Operands must be numbers.
  [line 1]
  ```
- Exit code: `70`

## Java specifics — lookup, don't memorize
- `left instanceof Double && right instanceof Double` safely checks types before unboxing.
