# Stage 57: Syntactic errors

## In one line
Catching invalid grammar productions in statements/loops during recursive descent parsing and exiting with code 65.

## Self-test (cover the answers below and answer these first)
- Why does `if (true) "ok"; else var foo;` produce an error at `'var'`?
- Where are parser error messages routed?
- What exit code signals syntactic/compilation failure to the caller?

## The problem it solved
Users frequently write syntactically invalid code (such as placing declarations directly in single-statement branches or malformed clauses in `for` loops). The parser must detect these invalid sequences, report standard error diagnostics, and halt before evaluation with exit code 65.

## Concepts (the transferable part)
- **Declaration vs Statement in Branches**:
  The grammar restricts statement positions (like the then/else branches of an `if`, or the body of a `while`/`for`) to `statement()`, not `declaration()`:
  ```
  ifStmt         → "if" "(" expression ")" statement
                   ( "else" statement )? ;
  ```
  A variable declaration (`var foo;`) is only allowed at the top level or inside a block `{ var foo; }`. When `'var'` appears where a statement is expected, `statement()` falls through to `expressionStatement()`, which calls `primary()`, throwing:
  `[line N] Error at 'var': Expect expression.`
- **Parser Error State and Process Termination**:
  ```java
  Parser parser = new Parser(tokens);
  List<Stmt> statements = parser.parseStatements();

  if (parser.hasError()) {
      System.exit(65);
  }
  ```
  All errors are written to `System.err`, ensuring `System.out` is clean.

## What breaks it (failure modes)
- Permitting `var` declarations in bare statement positions, allowing un-scoped variables.
- Printing error messages to `System.out` instead of `System.err`.
- Failing to exit with code 65 when `parser.hasError()` is set.

## Tradeoffs
- Parsing all statements with synchronization allows reporting multiple syntactic errors in a single compiler pass rather than halting on the very first failure.

## CLI / Protocol format
- Command: `./your_program.sh run <file.lox>`
- Stderr:
  ```
  [line 1] Error at 'var': Expect expression.
  ```
- Exit code: `65`

## Java specifics — lookup, don't memorize
- `System.err.println(...)` outputs directly to standard error stream (file descriptor 2).

## Rebuild checklist
- [ ] Enforce `statement()` rather than `declaration()` in branch and loop bodies.
- [ ] Record `hasError = true` on any `parseError`.
- [ ] In `Main.java` `run` mode, check `parser.hasError()` and exit with code 65.
