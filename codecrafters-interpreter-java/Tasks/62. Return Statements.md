# Stage 62: Return statements

## In one line
Unwinding call stacks and returning values from user-defined functions using `Stmt.Return` and a lightweight unwinding exception `Return`.

## Self-test (cover the answers below and answer these first)
- Why is an exception used to implement `return` in tree-walk interpreters?
- What does a function return if execution reaches a bare `return;` statement?
- What does a function return if execution falls off the end of its body without returning?

## The problem it solved
Functions need the ability to exit early and produce result values. Because a return statement can occur deep inside nested blocks, conditionals, and loops, the interpreter needs a clean mechanism to unwind the call stack immediately back to the function call boundary.

## Concepts (the transferable part)
- **Grammar for Return**:
  ```
  statement  → exprStmt | forStmt | ifStmt | printStmt | returnStmt | whileStmt | block ;
  returnStmt → "return" expression? ";" ;
  ```
- **AST Node**:
  ```java
  public static class Return extends Stmt {
      public final Token keyword;
      public final Expr value;
      // ...
  }
  ```
- **Unwinding with Exceptions**:
  Java `RuntimeException` is repurposed as control flow to instantly unwind nested Java calls inside `executeBlock()`:
  ```java
  public class Return extends RuntimeException {
      public final Object value;

      public Return(Object value) {
          super(null, null, false, false); // disables stack trace generation for performance
          this.value = value;
      }
  }
  ```
- **Executing and Catching Return**:
  In `Interpreter.visitReturnStmt()`:
  ```java
  Object value = null;
  if (stmt.value != null) value = evaluate(stmt.value);
  throw new Return(value);
  ```
  In `LoxFunction.call()`:
  ```java
  try {
      interpreter.executeBlock(declaration.body, environment);
  } catch (Return returnValue) {
      return returnValue.value;
  }
  return null;
  ```

## What breaks it (failure modes)
- Using standard exception construction with stack traces, causing massive performance overhead in recursive functions.
- Forgetting to evaluate `stmt.value` before throwing `Return`.
- Allowing `Return` exceptions to escape uncaught to top-level `interpret()`.

## Tradeoffs
- Exceptions for control flow in Java: Very clean to implement in a tree-walk interpreter, but incurs some overhead compared to bytecode VM registers/jump tables (mitigated by disabling stack traces via `super(null, null, false, false)`).

## CLI / Protocol format
- Command: `./your_program.sh run <file.lox>`
- Input:
  ```lox
  fun fib(n) {
    if (n < 2) return n;
    return fib(n - 2) + fib(n - 1);
  }
  print fib(10) == 55;
  ```
- Stdout:
  ```
  true
  ```
- Exit code: `0`

## Java specifics — lookup, don't memorize
- `super(null, null, false, false)` in `RuntimeException` sets `enableSuppression=false` and `writableStackTrace=false`.
