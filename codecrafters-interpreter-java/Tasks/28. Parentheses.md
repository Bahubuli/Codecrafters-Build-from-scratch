# Stage 28: Parentheses

## In one line
Recursively unwrapping and evaluating grouped expressions wrapped in parentheses.

## Self-test (cover the answers below and answer these first)
- Does a grouping expression alter the value or type of its inner subexpression?
- How does the interpreter's `visitGroupingExpr()` method process grouped expressions?
- Why is grouping in an AST purely syntactic and transparent to semantic evaluation?

## The problem it solved
Parentheses explicitly override operator precedence and group subexpressions together. At evaluation time, the grouping node in the AST must evaluate its inner expression and yield whatever that subexpression computes without modifying it.

## Concepts (the transferable part)
- **Transparent Evaluation**:
  A grouping node `( expr )` is a wrapper containing a single child expression. In the tree-walk evaluator:
  ```java
  @Override
  public Object visitGroupingExpr(Expr.Grouping expr) {
      return evaluate(expr.expression);
  }
  ```
- **Arbitrary Nesting Depth**:
  Because `evaluate()` recursively calls `expr.accept(this)`, nested groupings like `((false))` seamlessly unwrap through recursive dispatch until the inner literal or expression is reached.

## What breaks it (failure modes)
- Returning a wrapper object or losing the inner value during unwrapping.
- Premature termination on deeply nested parentheses due to missing recursive calls.

## Tradeoffs
- Grouping nodes in AST vs Preserving precedence solely via tree shape — Retaining `Expr.Grouping` explicitly mirrors the source code structure and allows lossless round-tripping/printing while making evaluation trivial.

## CLI / Protocol format
- Command: `./your_program.sh evaluate <file.lox>`
- Examples:
  - `("hello world!")` $\to$ `hello world!`
  - `(true)` $\to$ `true`
  - `(10.40)` $\to$ `10.4`
  - `((false))` $\to$ `false`

## Java specifics — lookup, don't memorize
- `return evaluate(expr.expression);` — direct recursion on the inner `Expr`.
