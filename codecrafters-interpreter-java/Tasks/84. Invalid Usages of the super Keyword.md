# Stage 84: Invalid Usages of the super Keyword

## In one line
Enforcing static syntax and lexical scope constraints on `super` so that usage outside classes, within classes without superclasses, or with malformed syntax emits compile errors (exit code 65).

## Self-test (cover the answers below and answer these first)
- Why must `super` expressions be validated at compile time by the Resolver rather than deferred to runtime?
- Under what two scope conditions does the Resolver reject `super`?
- What syntax rule governs `super` in the Parser, and what error is produced if violated?

## The problem it solved
Using `super` in invalid contexts—such as in top-level code outside any class, inside a root class that has no parent class, or without specifying an accessed method—would lead to undefined runtime behavior, null dereferences, or scope index out-of-bounds exceptions. Compile-time validation detects these mistakes immediately before interpretation starts.

## Concepts (the transferable part)
- **Syntax Validation**:
  In `Parser.primary()`:
  ```java
  if (match(TokenType.SUPER)) {
      Token keyword = previous();
      consume(TokenType.DOT, "Expect '.' after 'super'.");
      Token method = consume(TokenType.IDENTIFIER, "Expect superclass method name.");
      return new Expr.Super(keyword, method);
  }
  ```
  `super` is not an isolated expression; it must always be followed by `.` and an identifier method name.
- **Context-Aware Semantic Validation**:
  In `Resolver`:
  ```java
  private enum ClassType {
      NONE,
      CLASS,
      SUBCLASS
  }
  ```
  Tracking `currentClass` throughout AST traversal enables validating that:
  1. `currentClass != ClassType.NONE`: `super` cannot appear outside a class declaration (`"Can't use 'super' outside of a class."`).
  2. `currentClass == ClassType.SUBCLASS`: `super` cannot appear in a class that does not inherit from another class (`"Can't use 'super' in a class with no superclass."`).
- **Exit Code 65**:
  Any compile-time syntax or semantic error halts execution and exits with status 65 before runtime execution begins.

## What breaks it (failure modes)
- Forgetting to track class nesting level (`enclosingClass`) when classes are nested inside methods or other classes, which corrupts `currentClass` after an inner class ends.
- Allowing `super` to parse as a standalone variable without consuming `.` and the method name.
- Failing to return exit code 65 upon semantic resolution failure.

## Tradeoffs
- Restricting `super` to `super.method(...)` prevents using `super` as a first-class value (e.g., passing `super` into a function), which aligns with Lox's static dispatch design for parent methods.

## CLI / Protocol format
- Syntax error:
  ```lox
  super;
  ```
  Output (stderr):
  ```
  [line 1] Error at ';': Expect '.' after 'super'.
  ```
  Exit code: 65
- Semantic error (outside class):
  ```lox
  super.foo();
  ```
  Output (stderr):
  ```
  [line 1] Error at 'super': Can't use 'super' outside of a class.
  ```
  Exit code: 65
- Semantic error (no superclass):
  ```lox
  class A {
    foo() { super.foo(); }
  }
  ```
  Output (stderr):
  ```
  [line 2] Error at 'super': Can't use 'super' in a class with no superclass.
  ```
  Exit code: 65

## Java specifics — lookup, don't memorize
- In Java compilers (`javac`), using `super` in a static context or without an explicit member access (`super.x` or `super()`) generates compile-time error: `cannot find symbol / cannot be referenced from a static context`.

## Rebuild checklist
- [ ] In `Parser.primary()`, require `.` and an identifier method name after `super`.
- [ ] In `Resolver`, maintain `ClassType` state (`NONE`, `CLASS`, `SUBCLASS`).
- [ ] In `Resolver.visitSuperExpr`, report error if `currentClass == NONE` or `currentClass != SUBCLASS`.
