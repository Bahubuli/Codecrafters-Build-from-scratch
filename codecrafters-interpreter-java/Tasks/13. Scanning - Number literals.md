# Stage 13: Scanning - Number literals

## In one line
Scanning number literals requires consuming contiguous digit sequences with lookahead-of-two (`peekNext`) to optionally match a fractional decimal part without consuming trailing dots belonging to method calls or property accessors.

## Self-test (cover the answers below and answer these first)
- Why does number scanning require two characters of lookahead (`peek()` and `peekNext()`) instead of just one?
- How does the token's lexeme differ from its literal value for integer inputs like `42`?
- What should the scanner do when encountering a number immediately followed by a dot without trailing digits (e.g., `123.`)?

## The problem it solved
Prior to this stage, any digit encountered in the source code triggered an unexpected character lexical error. Number scanning groups sequences of integer digits and optional decimal fractions into numeric tokens, converting the matched lexeme into a double-precision float literal value.

## Concepts (the transferable part)
- **Lookahead (k=2) in Lexical Analysis** — Recognizing tokens sometimes requires peeking beyond the immediate next character. In `123.foo()`, seeing the `.` is not enough to decide if it's a decimal point or a property access operator; checking whether the character *after* the `.` is a digit determines whether the dot belongs to the number or is a separate token.
- **Maximal Munch / Longest Match Rule** — A scanner greedily consumes digits to form the longest possible valid numeric token.
- **Lexeme vs. Literal Representation** — The lexeme retains the exact source text (e.g., `"42"` or `"42.0000"`), while the literal value normalizes it to a numeric type (`42.0`).

## What breaks it (failure modes)
- Consuming a trailing dot without a subsequent digit (`123.`) — If `peekNext()` is not checked before consuming `.`, `123.` would consume the dot and leave no digits for the fractional part, failing to leave the dot as a `DOT` token.
- Out-of-bounds lookahead (`peekNext()` at EOF) — Peeking two characters ahead when near the end of the source string can throw `StringIndexOutOfBoundsException` unless guarded with bounds check (`current + 1 >= source.length()`).
- Floating point parsing exceptions — Calling `Double.parseDouble` on malformed substrings will fail if the lexer allows invalid characters into the number slice.

## Tradeoffs
- Parsing numbers during scanning vs during compilation/runtime — Converting the substring to a `Double` at scan time avoids repeated string parsing later in the pipeline, at the slight expense of committing early to double-precision representation.
- Unified IEEE 754 double precision vs distinct integer and floating-point types — Lox simplifies the language specification by representing all numbers as 64-bit doubles (matching JavaScript and Lua), eliminating distinct int/float types in the scanner and runtime.

## CLI / Protocol format
- Execution: `./your_program.sh tokenize <filename>`
- Output format:
  - `stdout`: `NUMBER <lexeme> <literal>` followed by remaining tokens and `EOF  null`.
  - For integers, the literal displays with `.0` (e.g., `NUMBER 42 42.0`).
  - For numbers with fractional parts, trailing zeroes are normalized by standard double string formatting (e.g., `NUMBER 42.0000 42.0`).
- Exit code: `0` on success.

## Java specifics — lookup, don't memorize
- `Double.parseDouble(String s)` — Parses the string argument as a signed `double`.
- `Character.isDigit(char c)` or `c >= '0' && c <= '9'` — Checks if a character is an ASCII decimal digit.
- `Double.toString(double d)` / implicit string conversion — Automatically appends `.0` for whole doubles (e.g., `42.0`).
