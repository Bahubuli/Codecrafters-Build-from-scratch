# Stage 17: Number literals

## In one line
Parsing numeric tokens into AST literal nodes (`Expr.Literal`) and rendering them with canonical floating-point representation (`Double.toString()`).

## Self-test (cover the answers below and answer these first)
- Why does Lox represent all numbers internally as 64-bit IEEE 754 floating-point doubles (`double` in Java)?
- How does the parser handle numbers compared to booleans and nil in `primary()`?
- Why does input `42` print as `42.0`, while input `12.34` prints as `12.34`?
- What role does `previous().literal` play in extracting the pre-scanned number value?

## The problem it solved
In the previous stage, the parser only recognized boolean tokens (`true`, `false`) and `nil`. Feeding a numeric literal like `74` or `56.78` caused an unexpected token error. This stage extends `primary()` to recognize `TokenType.NUMBER` and store the parsed `Double` literal on the AST node.

## Concepts (the transferable part)
- **Unified Number Semantics** — Like JavaScript and Lua, Lox uses double-precision IEEE 754 floats for all numbers. By converting integer lexemes into `Double` during scanning, numeric arithmetic later in the interpreter pipeline remains uniform without needing type coercion between integer and floating types.
- **AST Literal Nodes for Values** — An AST `Expr.Literal` wraps Java primitive objects (`Boolean`, `Double`, `String`, or `null`). During parsing, `primary()` consumes the token and reads `previous().literal`, passing the exact Java value to the node.
- **Visitor Serialization** — `AstPrinter` implements the visitor interface, formatting `Double` values through standard string conversion, producing `42.0` for whole numbers and `12.34` for fractional numbers.

## What breaks it (failure modes)
- **Formatting Truncation** — Trying to format doubles as integers if they have `.0` at the end violates the Lox specification, which expects whole numbers to retain the `.0` suffix (e.g. `74` $\to$ `74.0`).
- **Precision Loss or NumberFormatException** — Relying on custom string parsing rather than standard IEEE 754 `Double.parseDouble` can lead to inaccuracies or crashes on edge cases like very large numbers or zeroes (`0.0`).
- **Token Lookahead Discrepancy** — Forgetting to consume the token with `advance()` leaves the token in the parser stream, corrupting subsequent expression parsing.

## Tradeoffs
- **Double Representation vs Separate Int / Float Types** — Storing all numbers as `double` simplifies the scanner, parser, AST, and runtime evaluator at the cost of slight overhead and limited integer precision (53 bits of mantissa). For an interpreted language like Lox, this trade-off dramatically reduces language complexity.

## CLI / Protocol format
- Execution: `./your_program.sh parse <filename>`
- Output format:

  - Examples:
    - Input `74` $\to$ Output `74.0`
    - Input `56.78` $\to$ Output `56.78`
    - Input `0.0` $\to$ Output `0.0`
- Exit code: `0` on success.

## Java specifics — lookup, don't memorize
- `Double.toString(double d)` — In Java, `Double.toString(74.0)` produces `"74.0"`, and `Double.toString(56.78)` produces `"56.78"`, matching Lox's expected AST printer format.
- `previous().literal` — In recursive descent, `match(TokenType.NUMBER)` calls `advance()`. Calling `previous()` retrieves the consumed token containing the `Double` object.
