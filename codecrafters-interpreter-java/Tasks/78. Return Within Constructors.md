# Stage 78: Return Within Constructors

## In one line
Enforcing initializer return semantics by allowing early bare returns (`return;`) returning `this` while statically rejecting returns with expressions (`return value;`) with exit code 65.

## Self-test (cover the answers below and answer these first)
- Why is `return;` legal inside an `init()` method but `return "foo";` or `return this;` is rejected?
- What does an early `return;` inside `init()` produce as its evaluation result?
- How does the resolver differentiate return statements inside nested functions declared within `init()` from return statements of `init()` itself?

## The problem it solved
Lox constructors are intended to initialize newly allocated instances, and calling a class or `init()` always evaluates to the instance. Allowing arbitrary return expressions (e.g. `return 42;`) would contradict constructor semantics and break caller expectations. Conversely, early termination via `return;` is a legitimate pattern to skip further initialization work.

## Concepts (the transferable part)
- **Static Check in Resolver**:
  The `Resolver` tracks `FunctionType.INITIALIZER` when analyzing an `init` method. When encountering `Stmt.Return`:
  ```java
  if (stmt.value != null) {
      if (currentFunction == FunctionType.INITIALIZER) {
          Main.error(stmt.keyword, "Can't return a value from an initializer.");
      }
      resolve(stmt.value);
  }
  ```
  If `stmt.value == null` (i.e. bare `return;`), no error is raised.
- **Enclosing Function Stack Preservation**:
  When a local function is defined inside `init()`, `resolveFunction` saves `currentFunction`, sets it to `FunctionType.FUNCTION`, and restores it on exit. Thus, returning values from functions defined inside `init()` is completely legal.
- **Runtime Return Handling**:
  In `LoxFunction.call()`:
  ```java
  try {
      interpreter.executeBlock(declaration.body, environment);
  } catch (Return returnValue) {
      if (isInitializer) return closure.getAt(0, "this");
      return returnValue.value;
  }

  if (isInitializer) return closure.getAt(0, "this");
  return null;
  ```
  Whether `init()` finishes its body or catches an early `Return`, it returns `this`.

## What breaks it (failure modes)
- Failing to return `this` when catching a `Return` exception: an early `return;` would return `null` instead of the initialized instance.
- Permitting `return this;`: Lox specifically disallows returning any value (even `this`) to keep initializers uniform and prevent accidental returns of other expressions.

## Tradeoffs
- Disallowing value returns statically via `Resolver` avoids the ambiguity of whether constructor calls return the allocated instance or the user's returned value.

## CLI / Protocol format
- Input:
  ```lox
  class Person {
    init() {
      print "world";
      return;
    }
  }
  Person();
  ```
- Output:
  ```
  world
  ```
  Exit code: 0

- Input (Invalid return):
  ```lox
  class Foo {
    init() {
      return "something else";
    }
  }
  Foo();
  ```
- Output:
  ```
  [line 3] Error at 'return': Can't return a value from an initializer.
  ```
  Exit code: 65

## Java specifics — lookup, don't memorize
- `FunctionType enclosingFunction = currentFunction; try { currentFunction = type; ... } finally { currentFunction = enclosingFunction; }` ensures context correctness even across AST sub-traversals.
