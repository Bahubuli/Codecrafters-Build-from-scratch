# Stage 18: String literals

## In one line
Parsing string token literals into AST literal nodes (`Expr.Literal`) and rendering the unwrapped text content via `AstPrinter`.

## Self-test (cover the answers below and answer these first)
- Why does the AST printer output the raw unquoted string content (e.g. `hello world!`) rather than retaining surrounding quotes (`"hello world!"`)?
- Where are the enclosing quotes stripped: in the scanner during tokenization or in the parser during AST construction?
- How does `primary()` in the parser treat `TokenType.STRING` vs `TokenType.NUMBER`?
- What happens when a string literal contains spaces, numbers, or special characters?

## The problem it solved
Prior to this stage, passing a string literal such as `"foo"` or `"hello world!"` to the `parse` command was unsupported if string tokens were not handled in `primary()`. This stage ensures string tokens produce an `Expr.Literal` carrying the unquoted string value.

## Concepts (the transferable part)
- **Token Literal Decoupling** — The scanner already extracted the clean string value (stripping leading and trailing `"` characters) and stored it in `Token.literal`. When the parser matches `TokenType.STRING`, it directly extracts this stored value into an `Expr.Literal` node.
- **Representation vs Value** — Lexical representations include syntactic delimiters (like quotation marks) to demarcate tokens. Once parsed into an AST or value representation, delimiters are discarded; only the pure semantic payload is retained.
- **Uniform Literal Handling** — In recursive descent parsing, both numbers and strings are atomic expressions parsed at the lowest precedence level (`primary`).

## What breaks it (failure modes)
- **Double Stripping or Missing Delimiters** — If the parser attempts to strip quotes again from an already stripped `Token.literal`, characters are mistakenly removed from user data.
- **Unescaped or Special Characters Handling** — Strings containing spaces, tabs, or symbols must retain their exact contents when passed through `AstPrinter`.

## Tradeoffs
- **Storing Lexeme vs Raw Value in AST** — Storing the raw value (`String`) in `Expr.Literal.value` separates syntax from semantics, making both pretty-printing and evaluation straightforward.

## CLI / Protocol format
- Execution: `./your_program.sh parse <filename>`
- Output format:
  - `stdout`: The string value of the literal without quotes.
  - Examples:
    - Input `"foo"` $\to$ Output `foo`
    - Input `"hello world!"` $\to$ Output `hello world!`
- Exit code: `0` on success.

## Java specifics — lookup, don't memorize
- `Token.literal` — The Java `String` stored on the token.
- `expr.value.toString()` — Prints the raw Java string directly to standard output.
