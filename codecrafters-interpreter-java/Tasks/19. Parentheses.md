# Stage 19: Parentheses

## In one line
Parsing grouped expressions wrapped in parentheses into `Expr.Grouping` AST nodes and rendering them recursively with prefix notation `(group <inner_expr>)`.

## Self-test (cover the answers below and answer these first)
- Why do parentheses create an `Expr.Grouping` node in the AST rather than directly evaluating or discarding the parentheses?
- How does the parser handle nested parentheses like `((true))`?
- How does recursive descent handle the closing parenthesis `)` after parsing the inner expression?
- What happens if an opening parenthesis has no matching closing parenthesis?

## The problem it solved
In previous stages, expressions could only consist of isolated literals. In programming languages, parentheses alter operator precedence and explicitly group subexpressions. This stage adds support for recognizing parenthesized expressions in the parser grammar and generating structured grouping AST nodes.

## Concepts (the transferable part)
- **Grouping in Formal Grammar** — In Backus-Naur Form (BNF), primary expressions include parenthesized expressions:
  $$primary \to NUMBER \mid STRING \mid "true" \mid "false" \mid "nil" \mid "(" expression ")"$$
- **Recursive Grammar Navigation** — When matching `(`, the parser calls `expression()`, recursively descending into the full expression grammar. This allows arbitrary expressions of any complexity (literals, binary operations, unary operations, or further nested groups) to appear inside parentheses.
- **Syntactic Assertion (`consume`)** — After parsing the inner expression, the parser must encounter and consume the matching closing delimiter `)`. If not present, a syntax error is raised.
- **Prefix Grouping in AST Serialization** — `AstPrinter` formats `Expr.Grouping` as `(group <inner_expr>)`. Nested groups naturally nest their prefix notation (e.g. `((true))` $\to$ `(group (group true))`).

## What breaks it (failure modes)
- **Unclosed Parentheses** — Missing `consume(TokenType.RIGHT_PAREN, "Expect ')' after expression.")` can leave the parser hanging or consuming tokens past their intended subexpression boundary.
- **Infinite Recursion on Empty Parentheses** — Empty parentheses `()` without an inner expression must be reported as a syntax error rather than looping or creating empty nodes.

## Tradeoffs
- **Retaining Grouping Nodes in AST vs Folding** — Some optimizing compilers discard grouping nodes after building the tree because tree structure alone encodes precedence. Keeping an explicit `Expr.Grouping` node preserves exact source syntax, facilitating source maps, linters, and AST serialization (`AstPrinter`).

## CLI / Protocol format
- Execution: `./your_program.sh parse <filename>`
- Output format:
  - `stdout`: `(group <inner_expr>)`
  - Examples:
    - Input `("foo")` $\to$ Output `(group foo)`
    - Input `((true))` $\to$ Output `(group (group true))`
- Exit code: `0` on success.

## Java specifics — lookup, don't memorize
- `consume(TokenType type, String message)` — Verifies `check(type)` is true, advances the token pointer, or throws a `ParseError`.
- `Expr.Grouping(Expr expression)` — Stores the encapsulated subexpression.
