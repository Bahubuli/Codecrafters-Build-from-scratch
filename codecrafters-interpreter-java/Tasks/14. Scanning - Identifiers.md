# Stage 14: Scanning - Identifiers

## In one line
Scanning user-defined identifiers by matching leading alphabetical characters or underscores (`[a-zA-Z_]`) and greedily consuming subsequent alphanumeric characters (`[a-zA-Z0-9_]`) via maximal munch.

## Self-test (cover the answers below and answer these first)
- Why must an identifier start with an alpha character or underscore instead of a digit?
- How does the scanner distinguish between an identifier and a number literal when both contain digits?
- What is the difference between an identifier's token type, its lexeme, and its literal value?
- When should the scanner check if an identifier matches a reserved keyword like `var`, `if`, or `while`?

## The problem it solved
Before this stage, any letter or underscore encountered in the source text was treated as an invalid lexical character, triggering an unexpected character error. Supporting identifiers enables variable names, function names, class names, and property labels to be recognized as discrete tokens for subsequent syntactic and semantic analysis.

## Concepts (the transferable part)
- **Identifier Grammar Rule** — In most programming languages (including Lox, C, Java, Python), identifiers follow the regular definition: `[a-zA-Z_][a-zA-Z0-9_]*`. Restricting the leading character to non-digits prevents ambiguous prefixes where a number literal could bleed into an identifier (e.g., `123foo`).
- **Maximal Munch (Longest Match)** — When scanning contiguous characters, the lexer consumes as many alphanumeric characters as possible before delimiting the token. For example, `_hello123` is scanned as a single identifier token rather than `_hello` and `123`.
- **Lexeme vs Literal for Identifiers** — For an identifier token, the literal value is `null` because the identifier refers to a named symbol whose value is bound later during interpretation/runtime, while the lexeme captures the exact identifier name in source text (e.g. `foo`).

## What breaks it (failure modes)
- **Allowing Leading Digits** — If digit checks are not prioritized or if `isAlpha` includes digits, tokens like `123var` would misidentify as identifiers or cause grammar ambiguity. Checking `isDigit(c)` before `isAlpha(c)` in the scanner loop preserves strict number tokenization.
- **Missing Underscore Support** — Identifiers frequently start with or contain underscores (e.g., `_counter`, `user_id`). Omitting `_` from `isAlpha` or `isAlphaNumeric` breaks standard idiomatic naming.
- **Accidental Lookahead Consumption** — Advancing past trailing whitespace or delimiters when scanning the identifier tail would consume punctuation (e.g., consuming the `(` in `foo()`). Using non-advancing `peek()` in the loop guarantees stopping immediately before the first non-identifier character.

## Tradeoffs
- **Scanning Identifiers First vs Tying Lexer to Keyword Trie** — Scanning all alpha-sequences as generic identifiers and then querying a keyword lookup map (in Stage 15) decouples the character-advancement logic from the reserved word set. The alternative (a hardcoded finite-state automaton or trie for each keyword) is marginally faster in C but adds substantial complexity compared to a hash map lookup.

## CLI / Protocol format
- Execution: `./your_program.sh tokenize <filename>`
- Output format:
  - `stdout`: `IDENTIFIER <lexeme> null` followed by remaining tokens and `EOF  null`.
  - Example: For input `foo bar _hello`, output is:
    ```
    IDENTIFIER foo null
    IDENTIFIER bar null
    IDENTIFIER _hello null
    EOF  null
    ```
- Exit code: `0` on success.

## Java specifics — lookup, don't memorize
- `c >= 'a' && c <= 'z' || c >= 'A' && c <= 'Z' || c == '_'` — Direct ASCII range check for alphabetic characters and underscore.
- `Character.isLetterOrDigit(char c)` — Java standard library alternative, though it matches unicode letters (Lox restricts to ASCII).
- `TokenType.IDENTIFIER` — Enum constant representing user-defined identifier tokens.
