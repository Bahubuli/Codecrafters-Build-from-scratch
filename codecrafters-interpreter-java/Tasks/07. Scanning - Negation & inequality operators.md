# Stage 07: Scanning - Negation & inequality operators

## In one line
Extending conditional lookahead (`match`) to the exclamation mark `!` differentiates logical negation (`BANG`) from the inequality operator (`BANG_EQUAL`).

## Self-test (cover the answers below and answer these first)
- How does `match('=')` allow the lexer to distinguish between a unary negation operator (`!`) and a binary inequality comparison (`!=`)?
- What token stream and lexemes should be produced for the input string `!=!===`?
- If the file ends with a trailing `!`, why does `match('=')` safely return `false` without throwing an index out of bounds error?

## The problem it solved
Logical negation (`!`) and relational inequality (`!=`) share the identical leading character `!`. Without lookahead, reading `!` would force an immediate, premature classification as `BANG`. By querying the next character conditionally via `match('=')`, the scanner greedily constructs the compound `BANG_EQUAL` token when followed by `=`, or settles on `BANG` without advancing when followed by any other character or EOF.

## Concepts (the transferable part)
- **Compound Operator Disambiguation** — The general pattern in lexical analysis where a prefix character may represent either a standalone operator or the first character of a multi-character operator (e.g. `!`, `!=`, `<`, `<=`, `>`, `>=`).
- **Lookahead Buffer & Sentinel Checks** — Verifying bounds before probing ahead in the input stream, ensuring end-of-file conditions act as natural token delimiters without causing read errors.
- **Unary vs Binary Operator Lexing** — While the parser later assigns syntactic meaning (unary negation vs binary equality comparison), the lexer's sole responsibility is recognizing the surface representation based on immediate character boundaries.

## What breaks it (failure modes)
- Accidental advancement on mismatch — If `match()` consumed the character when it was *not* `=`, a sequence like `!x` would swallow `x` and erroneously emit `BANG_EQUAL` or drop `x` from subsequent identifier scanning.
- Unterminated lookahead at EOF — Probing `source.charAt(current)` without guarding for `current >= source.length()` would crash with `IndexOutOfBoundsException` on files ending with `!`.
- Incorrect lexeme slicing — Slicing `source.substring(start, current)` relies on `current` having advanced exactly two characters for `!=` and one character for `!`. If `start` or `current` are mishandled, the emitted lexeme will not match the matched token type.

## Tradeoffs
- Unified `match()` helper vs individual character peeks — Using a helper `match(char expected)` combines inspection and conditional consumption into an atomic helper, eliminating code duplication across `!`, `=`, `<`, and `>`.
- Distinct token types (`BANG_EQUAL`) vs operator-value tokens (`OPERATOR` with string value) — Emitting strongly-typed enums (`TokenType.BANG_EQUAL`) shifts grammar decisions directly into the parser's switch/match cases, eliminating string comparison overhead during parsing.

## CLI / Protocol format
- Execution: `./your_program.sh tokenize <filename>`
- Output format: `<token_type> <lexeme> <literal>` on stdout for each token.
- Example for input `!!===`:
  ```
  BANG ! null
  BANG_EQUAL != null
  EQUAL_EQUAL == null
  EOF  null
  ```
- Exit code: `0` on clean lexical scan.

## Java specifics — lookup, don't memorize
- Ternary operator (`cond ? a : b`) — Succinctly branches between `TokenType.BANG_EQUAL` and `TokenType.BANG`.
- `switch` character branches — `case '!': addToken(match('=') ? TokenType.BANG_EQUAL : TokenType.BANG); break;` provides clean O(1) dispatch.
