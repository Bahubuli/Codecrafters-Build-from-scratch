# Stage 05: Scanning - Lexical errors

## In one line
Lexical errors decouple error reporting from fatal termination: the scanner logs invalid characters to stderr and continues scanning valid tokens, setting an error flag that forces a non-zero process exit (exit code 65) only after the entire pass.

## Self-test (cover the answers below and answer these first)
- Why should a lexical scanner continue processing remaining characters after encountering an unrecognized character instead of terminating immediately with an exception or `System.exit`?
- What is UNIX Sysexits code 65 (`EX_DATAERR`), and why does the interpreter distinguish between lexical/syntax errors and runtime execution errors?
- Why are lexical error messages directed to `stderr` rather than interleaved into `stdout` alongside token streams?

## The problem it solved
Previously, encountering unrecognized or illegal source characters had no standard contract: an unhandled character could either crash the scanner or quietly produce invalid tokens. This stage establishes a robust lexical error pipeline: invalid characters trigger standardized diagnostics on stderr, remaining valid tokens are still emitted to stdout for downstream reporting, and the program exits with code 65 to signal data format failure.

## Concepts (the transferable part)
- **Error Recovery and Batch Reporting** — A compiler or interpreter should never stop at the first error if it can safely resume; recovering and scanning the rest of the source allows developers to see multiple diagnostic errors in a single pass rather than fixing one character at a time.
- **Separate Diagnostic vs Data Streams** — Sending token representations to `stdout` and error diagnostics to `stderr` prevents log and diagnostics pollution in standard pipeline compositions (such as piping tokens into subsequent tooling or tests).
- **Sysexits Standards (`EX_DATAERR` = 65)** — Per `<sysexits.h>`, exit code 65 indicates that the input data was incorrect in format (e.g. syntax/lexical error), distinguishing user code errors from CLI usage errors (`EX_USAGE` = 64) or internal software failures (`EX_SOFTWARE` = 70).
- **Error Flag Aggregation** — Rather than throwing checked or unchecked exceptions immediately, the scanner sets an internal boolean flag (`hasError = true`). Control flow completes normally, and the driver checks the aggregate error state at the end of the phase before proceeding.

## What breaks it (failure modes)
- Immediate termination on first error (`System.exit(65)` inside `scanToken()`) — Breaks error batching and fails to emit subsequent valid tokens or identify subsequent errors across the file.
- Writing errors to `stdout` instead of `stderr` — Violates standard stream contracts and corrupts the token stream consumed by downstream stages.
- Swallowing errors and exiting with code 0 — Downstream phases (parser, evaluator) would receive a truncated or corrupted token sequence and attempt to parse invalid code.

## Tradeoffs
- Continue scanning single character error vs Panic mode / Token synchronization — For single invalid characters in lexical analysis, skipping the invalid character and continuing scanning is trivial and safe because tokens are largely local; in parsing, recovering requires synchronization (e.g. searching for statement boundaries or semicolons) to avoid cascading noise errors.
- Boolean flag tracking vs Error list collection — Storing an internal `hasError` flag is lightweight and sufficient when diagnostics are streamed immediately to `stderr`; storing a `List<ScanError>` is preferable when formatting or structured JSON/LSP diagnostics are required.

## CLI / Protocol format
- Execution: `./your_program.sh tokenize <filename>`
- Error message format on `stderr`: `[line <line>] Error: Unexpected character: <c>`
- Token output format on `stdout`: `<token_type> <lexeme> <literal>`
- Exit code: `65` if any lexical error was encountered; `0` if all characters scanned successfully.
- Example for input `,.$(#`:
  - `stderr`:
    ```
    [line 1] Error: Unexpected character: $
    [line 1] Error: Unexpected character: #
    ```
  - `stdout`:
    ```
    COMMA , null
    DOT . null
    LEFT_PAREN ( null
    EOF  null
    ```
  - Exit code: `65`

## Java specifics — lookup, don't memorize
- `System.err.println(...)` — Writes formatted diagnostic text directly to the standard error stream.
- `System.exit(int status)` — Terminates the running Java Virtual Machine with the specified process return code.
