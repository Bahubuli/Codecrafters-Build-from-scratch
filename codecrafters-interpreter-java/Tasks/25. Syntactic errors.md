# Stage 25: Syntactic errors

## In one line
Detecting grammar violations during parsing, emitting standardized diagnostic error messages to standard error, and terminating with exit code 65.

## Self-test (cover the answers below and answer these first)
- Why does the parser use a custom unchecked `ParseError` exception to unwind the call stack?
- How does error reporting distinguish between an unexpected token mid-stream and an unexpected `EOF`?
- What is panic mode recovery and why is `synchronize()` used when parsing complete statements?

## The problem it solved
When source code contains malformed syntax like `(72 +)` or missing closing delimiters, the parser must report informative line numbers and token lexemes rather than crashing with an unhandled exception or printing corrupted AST output.

## Concepts (the transferable part)
- **Unwinding via Exceptions**:
  In recursive descent parsing, when a syntax error occurs deeply nested inside grammar methods (e.g. inside `primary()` when expecting an operand after `+`), throwing a Sentinel `ParseError` cleanly unwinds back to `parse()` without polluting every intermediate return type with error checks:
  ```java
  public Expr parse() {
      try {
          return expression();
      } catch (ParseError error) {
          return null;
      }
  }
  ```
- **Error Formatting**:
  Lox error formatting convention:
  ```java
  private ParseError error(Token token, String message) {
      hasError = true;
      if (token.type == TokenType.EOF) {
          System.err.println("[line " + token.line + "] Error at end: " + message);
      } else {
          System.err.println("[line " + token.line + "] Error at '" + token.lexeme + "': " + message);
      }
      return new ParseError();
  }
  ```
- **Exit Code Convention**:
  CLI tools follow standard POSIX/UNIX `sysexits.h` conventions: syntax/data errors exit with code 65 (`EX_DATAERR`).

## What breaks it (failure modes)
- Printing error messages to `System.out` instead of `System.err`.
- Exiting with code 0 or 1 instead of 65.
- Continuing to print an AST when `hasError` is true or `expression == null`.

## Tradeoffs
- Immediate abort vs Panic-mode error recovery — Aborting on the first parse error avoids cascading nonsensical errors, while panic-mode recovery (`synchronize()`) allows reporting multiple independent syntax errors across different statements in a single run.

## CLI / Protocol format
- Command: `./your_program.sh parse <file.lox>`
- Stderr: `[line 1] Error at ')': Expect expression.`
- Exit code: `65`

## Java specifics — lookup, don't memorize
- `System.err.println(...)` — standard output stream for error messages.
- `System.exit(65)` — programmatic exit code.
