# Stage 01: Scanning: Empty file

## In one line
An interpreter transforms character streams into meaningful lexical tokens, ending with an explicit EOF marker even for empty inputs.

## Self-test (cover the answers below and answer these first)
- Why does the scanner emit an explicit EOF token rather than simply returning an empty list of tokens?
- Why is there a double space in the output representation `EOF  null`?
- What is the difference between a token's lexeme and its literal value?

## The problem it solved
Compilers and interpreters cannot efficiently parse raw character sequences. The scanner (or lexer) groups characters into atomic tokens so subsequent grammar analysis can operate on symbols rather than characters. For an empty file, the scanner establishes the baseline by returning a single EOF token.

## Concepts (the transferable part)
- **Lexical Analysis (Scanning)** — The first phase of a compiler/interpreter pipeline that converts a linear stream of characters into a sequence of categorized tokens.
- **Sentinel Token (EOF)** — An explicit end-of-input token that allows the parser downstream to perform uniform lookaheads without checking collection bounds or encountering out-of-bounds index exceptions.
- **Token Anatomy** — A token comprises:
  1. `type`: Categorical classification (e.g. `EOF`, `IDENTIFIER`, `STRING`).
  2. `lexeme`: The exact character slice from source code that matched (for `EOF`, it is empty `""`).
  3. `literal`: Evaluated native runtime representation (e.g. `Double`, `String`, or `null`).
  4. `line`: Source line number for debugging and error reporting.

## What breaks it (failure modes)
- Missing EOF token — The parser expects a terminal token and loops or throws unexpected end-of-file exceptions when traversing tokens.
- Missing lexeme spacing — Emitting `EOF null` (single space) instead of `EOF  null` (double space due to the empty lexeme between type and literal) violates the CodeCrafters/Crafting Interpreters token output format.

## Tradeoffs
- Eager token scanning into a `List<Token>` vs on-demand lazy stream iterator — Eager scanning is simpler to implement and debug in tree-walk interpreters, while lazy scanning conserves memory on massive source files.

## CLI / Protocol format
- Execution: `./your_program.sh tokenize <filename>`
- Output format per token: `<token_type> <lexeme> <literal>`
- Empty file output:
  ```
  EOF  null
  ```

## Java specifics — lookup, don't memorize
- `Files.readString(Path.of(filename))` — Reads all characters from a file into a Java `String` using UTF-8 encoding.
- `enum TokenType` — Strongly typed representation of all legal Lox token types.
