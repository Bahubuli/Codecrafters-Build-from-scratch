# Stage 06: Scanning - Assignment & equality Operators

## In one line
Handling multi-character operator tokens requires conditional lookahead (`match`), where the scanner inspects the next character without unconditionally advancing unless it matches the expected successor.

## Self-test (cover the answers below and answer these first)
- What is conditional lookahead, and how does `match(char expected)` differ from `advance()`?
- Why does the scanner need to update both the token type and the token lexeme text when scanning multi-character operators like `==`?
- What happens if the source ends immediately after seeing an `=` character, and how does `match()` prevent out-of-bounds index errors?

## The problem it solved
Single-character tokenization assumed each character deterministically mapped to one token. When operators share prefixes—such as assignment `=` and equality `==`—the scanner cannot decide which token to emit upon reading the first character alone. Adding conditional lookahead allows the scanner to greedily combine adjacent characters into compound tokens when present.

## Concepts (the transferable part)
- **Lookahead (Lookahead-1 / `match`)** — Inspecting future input characters before committing to a token transition. Conditional lookahead (`match`) consumes the lookahead character only if it matches an expected pattern, acting as a guarded advance.
- **Maximal Munch (Greedy Lexing)** — A foundational rule of lexical analyzers: when multiple lexical rules could match at the current position, the scanner matches the longest possible sequence of characters (e.g., `==` is scanned as a single `EQUAL_EQUAL` token rather than two consecutive `EQUAL` tokens).
- **Prefix Disambiguation** — Solving lexical ambiguity where shorter tokens form exact prefixes of longer tokens by branching based on lookahead.

## What breaks it (failure modes)
- Out-of-bounds on Lookahead at EOF — Checking `source.charAt(current)` without first checking `isAtEnd()` causes an `IndexOutOfBoundsException` when `=` is the very last character of the source. `match()` guards this by returning `false` if `isAtEnd()`.
- Unconditional consumption on mismatch — Incrementing `current` before verifying the character matches consumes an unrelated character, corrupting the subsequent token.
- Desynchronized lexeme length — Failing to advance `current` inside `match()` when a match occurs would emit `EQUAL_EQUAL` with a single-character lexeme `"="` instead of `"=="`.

## Tradeoffs
- Ad-hoc `match()` method vs Full DFA / Table-driven Lexer — Hand-written conditional lookahead (`match`) is simple, fast, and easy to maintain for small languages like Lox; table-driven lexers (like Flex/Lex) generate state transition tables and scale better to dozens of compound operators and keyword rules.
- Greedy matching (Maximal Munch) vs Context-sensitive lexing — Maximal munch is standard across almost all programming languages, but can cause surprises in corner cases (e.g. `x= =y` vs `x==y`, or C++ `>>` in nested templates `vector<list<int>>`).

## CLI / Protocol format
- Execution: `./your_program.sh tokenize <filename>`
- Token output format on `stdout`: `<token_type> <lexeme> <literal>`
- Example for input `={===}`:
  ```
  EQUAL = null
  LEFT_BRACE { null
  EQUAL_EQUAL == null
  EQUAL = null
  RIGHT_BRACE } null
  EOF  null
  ```
- Exit code: `0` if all tokens scanned cleanly.

## Java specifics — lookup, don't memorize
- `String.charAt(int index)` — Returns the `char` value at the specified 0-based index.
- Ternary operator (`condition ? expr1 : expr2`) — Inline conditional expression used to select `TokenType.EQUAL_EQUAL` or `TokenType.EQUAL`.
