# Stage 82: Inheritance Errors

## In one line
Enforcing static resolution error detection for self-inheritance (`class Foo < Foo`) and dynamic runtime verification that superclass identifiers evaluate to actual `LoxClass` instances.

## Self-test (cover the answers below and answer these first)
- Why can self-inheritance be caught statically at compile/resolution time, while inheriting from a string or function must be caught at runtime?
- What exit code is produced when a class inherits from itself?
- What exit code and message format are produced when a superclass expression evaluates to a non-class value?

## The problem it solved
Without inheritance validation:
1. Self-inheritance (`class Foo < Foo`) creates cycles in the class hierarchy, sending `findMethod` into an infinite recursion and causing stack overflow crashes.
2. Inheriting from non-class values (strings, numbers, functions) causes `ClassCastException` or null pointer crashes in the host interpreter instead of graceful Lox errors.

## Concepts (the transferable part)
- **Compile-time Cycle Check**:
  In `Resolver.visitClassStmt`:
  ```java
  if (stmt.superclass != null &&
      stmt.name.lexeme.equals(stmt.superclass.name.lexeme)) {
      Main.error(stmt.superclass.name, "A class can't inherit from itself.");
  }
  ```
  Since both tokens are available during static analysis, self-inheritance is reported as a syntax/resolution error with exit code 65.
- **Dynamic Type Assertion on Superclasses**:
  In `Interpreter.visitClassStmt`:
  ```java
  Object superclass = null;
  if (stmt.superclass != null) {
      superclass = evaluate(stmt.superclass);
      if (!(superclass instanceof LoxClass)) {
          throw new RuntimeError(stmt.superclass.name, "Superclass must be a class.");
      }
  }
  ```
  Because Lox variables are dynamically typed, whether a variable or function name holds a class or not cannot be known until evaluation. If it is not a `LoxClass`, a runtime error is thrown and caught by `Interpreter.interpret()`, reporting the error message and line number with exit code 70.

## What breaks it (failure modes)
- Trying to validate whether `superclass` is a class during the resolver pass: in dynamic languages, identifiers in superclass position may refer to global variables or functions defined later or modified dynamically.
- Throwing a generic exception instead of `RuntimeError`: bypasses line number reporting and exit code 70 convention.

## Tradeoffs
- Static checking is limited to self-inheritance in single-pass resolution; multi-step cycles (`A < B` where `B < A`) are deferred until runtime or require a whole-program symbol dependency graph.

## CLI / Protocol format
- Input (Static Self-Inheritance):
  ```lox
  class Foo < Foo {}
  ```
- Output:
  ```
  [line 1] Error at 'Foo': A class can't inherit from itself.
  ```
  Exit code: 65

- Input (Runtime Non-Class Superclass):
  ```lox
  var A = "not a class";
  class B < A {}
  ```
- Output:
  ```
  Superclass must be a class.
  [line 2]
  ```
  Exit code: 70

## Java specifics — lookup, don't memorize
- `instanceof LoxClass` is safe even when `superclass` is `null` (evaluates to `false`).
