# Stage 69: Variable Redeclaration

## In one line
Compile-time detection and prohibition of declaring multiple variables or function parameters with the same identifier in the same local scope map.

## Self-test (cover the answers below and answer these first)
- Why does Lox permit redeclaring variables in the global scope but reject it in local scopes?
- In what function-related scenarios can duplicate declarations occur?
- Why is variable shadowing across different nested scopes allowed while redeclaration in the same scope is prohibited?

## The problem it solved
Declaring two local variables with the exact same name in the same block (or declaring two function parameters with identical names, or declaring a local variable that collides with an existing parameter name) is almost always a copy-paste error or programming bug. Catching it at compile time during resolution prevents confusing shadowing within the same lexical frame.

## Concepts (the transferable part)
- **Local Scope Collision Detection**:
  In `Resolver.declare(Token name)`:
  ```java
  private void declare(Token name) {
      if (scopes.isEmpty()) return;

      Map<String, Boolean> scope = scopes.peek();
      if (scope.containsKey(name.lexeme)) {
          Main.error(name, "Already a variable with this name in this scope.");
      }

      scope.put(name.lexeme, false);
  }
  ```
- **Unified Parameter and Body Scope**:
  Because function parameters are declared in the innermost function scope, any `var <param>` statement inside the function body targets the exact same `scopes.peek()` frame and is immediately detected as a duplicate.
- **Global Scope Permissiveness**:
  In global scope (`scopes.isEmpty()`), `declare()` returns immediately without tracking or rejecting duplicate names, allowing top-level scripting and interactive REPL workflows.

## What breaks it (failure modes)
- Using `scopes.contains(name.lexeme)` across all scopes in the stack instead of just `scopes.peek().containsKey(...)`, which would incorrectly reject legal lexical shadowing in child scopes.
- Pushing a second scope for the function body instead of sharing the parameter scope, which would fail to catch `fun foo(a) { var a; }`.
- Checking duplicate parameter names during runtime call execution instead of statically at compile time.

## Tradeoffs
- Enforces strict hygiene within individual blocks and functions while preserving pragmatic flexibility for global scripting.

## CLI / Protocol format
- Command: `./your_program.sh run <file.lox>`
- Input:
  ```lox
  fun foo(a) {
    var a;
  }
  ```
- Stderr:
  ```
  [line 2] Error at 'a': Already a variable with this name in this scope.
  ```
- Exit code: `65`

## Java specifics — lookup, don't memorize
- `Map.containsKey(key)` checks if an entry already exists in the current scope frame before inserting `false`.
