# Stage 65: Function scope

## In one line
Binding function execution environments to their lexical closure parent to preserve variable scoping across global, local, and nested function invocations.

## Self-test (cover the answers below and answer these first)
- When a function executes, what is the enclosing environment of its call-frame environment?
- If a function accesses a variable not declared in its own parameters or body, where does it look?
- What happens if a local variable inside a function shadows an outer variable of the same name?

## The problem it solved
Functions must resolve variables using lexical scoping (the scope where the function was declared), rather than dynamic scoping (the scope from which the function was invoked). When a function is called from inside an inner block with local variables that share names with outer variables, the function must still see its own lexical bindings or global variables, not the caller's transient local variables.

## Concepts (the transferable part)
- **Lexical Environment Binding**:
  In `LoxFunction`:
  ```java
  @Override
  public Object call(Interpreter interpreter, List<Object> arguments) {
      Environment environment = new Environment(closure);
      for (int i = 0; i < declaration.params.size(); i++) {
          environment.define(declaration.params.get(i).lexeme, arguments.get(i));
      }
      ...
  }
  ```
  The newly instantiated call frame has `closure` as its enclosing environment.
- **Dynamic Call Isolation**:
  Regardless of where `function.call()` is invoked in the code (deep within local loops or other function frames), its environment chain links back to `closure`, completely isolating it from the caller's local scope.
- **Variable Shadowing**:
  Inside a function, declaring `var a = 95;` defines `a` within the current local activation environment, shadowing the outer `a` for subsequent accesses in that block without altering the outer `a`'s value.

## What breaks it (failure modes)
- Using the interpreter's active `environment` as the parent when constructing the function's call environment (dynamic scoping bug).
- Forgetting to link `Environment` instances hierarchically with enclosing references.
- Not unwinding environments when returning from blocks or functions.

## Tradeoffs
- Lexical scoping requires each function instance (`LoxFunction`) to hold a reference to the environment in which it was declared (`closure`). This keeps environments alive in memory as long as the function is reachable (standard closure semantics).

## CLI / Protocol format
- Command: `./your_program.sh run <file.lox>`
- Input:
  ```lox
  var a = 38;
  fun printAndModify() {
    print a;
    var a = 95;
    print a;
  }
  print a;
  a = 68;
  printAndModify();
  ```
- Stdout:
  ```
  38
  68
  95
  ```
- Exit code: `0`

## Java specifics — lookup, don't memorize
- `new Environment(closure)` where `closure` is an immutable field stored on `LoxFunction`.
