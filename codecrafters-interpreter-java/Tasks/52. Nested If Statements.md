# Stage 52: Nested if statements

## In one line
Resolving arbitrary nesting and the dangling else ambiguity by recursively matching `if` statements within `then` and `else` branches.

## Self-test (cover the answers below and answer these first)
- What is the dangling else problem?
- In `if (true) if (false) print "world"; else print "baz";`, which `if` does `else` bind to and why?
- How does the recursive descent parser enforce this association without ambiguous grammar shift/reduce conflicts?

## The problem it solved
When an `if` statement appears inside the then-branch of another `if` statement, an `else` keyword could syntactically belong to either the outer or inner `if`. The interpreter must unambiguously bind each `else` to the nearest preceding `if` statement.

## Concepts (the transferable part)
- **The Dangling Else Problem**:
  Given:
  ```lox
  if (first) if (second) print "both"; else print "first only?";
  ```
  Does `else` belong to `first` or `second`?
  In almost all programming languages (C, Java, Python, Lox), an `else` is bound to the closest preceding unmatched `if`.
- **Recursive Descent Resolution**:
  ```java
  private Stmt ifStatement() {
      consume(TokenType.LEFT_PAREN, "Expect '(' after 'if'.");
      Expr condition = expression();
      consume(TokenType.RIGHT_PAREN, "Expect ')' after if condition.");

      Stmt thenBranch = statement();
      Stmt elseBranch = null;
      if (match(TokenType.ELSE)) {
          elseBranch = statement();
      }

      return new Stmt.If(condition, thenBranch, elseBranch);
  }
  ```
  When the parser enters the inner `if`, it runs `ifStatement()` recursively. Any trailing `else` token is immediately encountered and consumed by this inner `ifStatement()`, leaving nothing for the outer `ifStatement()` unless a second `else` is present.

## What breaks it (failure modes)
- Looking ahead beyond the current statement before binding `else`.
- Improperly synchronizing or discarding tokens when encountering nested control structures.

## Tradeoffs
- Parsing with eager greedy `else` match is simple and matches standard grammar rules, but requires programmers to use explicit braces `{ ... }` if they want an `else` bound to the outer `if` instead of the inner `if`.
