# Stage 10: Scanning - Whitespace

## In one line
Whitespace characters (spaces, carriage returns, tabs, and newlines) are lexical trivia that must be discarded without emitting tokens, with newlines uniquely tracked to keep line counters synchronized for accurate diagnostics.

## Self-test (cover the answers below and answer these first)
- Why are whitespace characters like spaces and tabs ignored during scanning instead of being emitted as tokens to the parser?
- What distinguishes `\n` from ` `, `\r`, and `\t` in the scanner's dispatch loop?

## The problem it solved
Before this stage, whitespace characters like spaces, tabs, and carriage returns would fall through to the default branch and trigger false lexical errors (`Unexpected character`). Handling whitespace allows source code formatting to be arbitrary and human-friendly without polluting the token stream passed to downstream compiler phases.

## Concepts (the transferable part)
- **Lexical Trivia Discarding** — Source characters that exist solely for human readability and code layout (spaces, tabs, carriage returns) carry no semantic meaning in free-form grammars and are dropped at the scanning phase.
- **Source Coordinates & Line Tracking** — Lexical analysis is the canonical place where 1D character streams are mapped into 2D line and column coordinates, essential for pinpoint error reporting throughout later compilation stages.
- **Handling OS Line Endings (CRLF vs LF)** — Treating `\r` as ignored whitespace and `\n` as the line-advancing character correctly normalizes both Unix (`\n`) and Windows (`\r\n`) line endings without double-incrementing the line counter.

## What breaks it (failure modes)
- Incrementing line on both `\r` and `\n` — On Windows/DOS CRLF files, incrementing on both `\r` and `\n` would double-increment the line counter on every line break, breaking diagnostic accuracy.
- Emitting whitespace tokens in free-form languages — Emitting tokens for spaces or tabs would force the parser grammar to handle whitespace between every terminal symbol, drastically complicating expression and statement productions.
- Missing `break` in switch cases — Forgetting `break` after whitespace cases would fall through to subsequent cases or the `default:` error branch, falsely reporting unexpected character errors.

## Tradeoffs
- Discarding trivia in scanner vs preserving trivia in AST (e.g., Roslyn/cst) — Discarding simplifies the token stream and downstream compiler phases. Retaining trivia (as leading/trailing trivia tokens) is required for full-fidelity concrete syntax trees used by formatters, refactoring tools, and IDEs.
- Centralized newline handling vs scattered newline increments — Keeping newline handling in `case '\n': line++; break;` ensures all line increments pass through a single, predictable branch rather than duplicating counter updates across various multi-line scanning routines.

## CLI / Protocol format
- Execution: `./your_program.sh tokenize <filename>`
- Output format: `<token_type> <lexeme> <literal>` on stdout for each emitted token (spaces, tabs, and newlines produce no output).
- Example for input `(\t \r\n )`:
  ```
  LEFT_PAREN ( null
  RIGHT_PAREN ) null
  EOF  null
  ```
- Exit code: `0` on clean lexical scan.

## Java specifics — lookup, don't memorize
- `case ' ': case '\r': case '\t': break;` — Switch case stacking in Java, grouping multiple character matches to execute the same empty discard block.
- `case '\n': line++; break;` — Advances line counter state before breaking out of token scanning.
