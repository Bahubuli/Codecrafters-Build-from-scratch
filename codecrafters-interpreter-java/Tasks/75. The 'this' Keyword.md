# Stage 75: The 'this' Keyword

## In one line
Binding method invocations to their receiving `LoxInstance` by wrapping methods in an environment with `"this"` and validating `this` usage in static scope analysis.

## Self-test (cover the answers below and answer these first)
- How does Lox bind `this` to a method when the method is extracted from an instance?
- What scope surrounds method execution to make `this` available inside nested functions defined inside methods?
- When does the resolver flag an error for `this`, and what is the exact error message?

## The problem it solved
Inside class methods, code needs a way to refer to the specific instance on which the method was called. Furthermore, if a method is stored in a variable or passed as a callback, it must retain its binding to the original receiver instance (`this`).

## Concepts (the transferable part)
- **Method Binding (`bind`)**:
  When a method is fetched from an instance (`instance.method`), the instance calls `method.bind(this)`. This creates a new `LoxFunction` whose closure contains a synthetic scope defining `"this" = instance`:
  ```java
  public LoxFunction bind(LoxInstance instance) {
      Environment environment = new Environment(closure);
      environment.define("this", instance);
      return new LoxFunction(declaration, environment);
  }
  ```
- **Nested Functions & Closures**:
  Because `"this"` lives in the closure environment of the method, any local function declared inside that method captures that environment, allowing inner functions to access `this` seamlessly.
- **Static Resolution (`Resolver`)**:
  - `Resolver` tracks `ClassType currentClass` (`NONE` or `CLASS`).
  - When resolving a class declaration, it pushes a new scope with `"this" = true` around method declarations.
  - When resolving `Expr.This`, it checks if `currentClass == ClassType.NONE`. If so, it reports: `Can't use 'this' outside of a class.`
  - Otherwise, it resolves `this` just like a local variable.

## What breaks it (failure modes)
- Dynamically binding `this` at call-site instead of property access: breaks first-class functions where `var m = dog.sound; m();` must still print dog's sound.
- Forgetting to nest method scopes inside the `"this"` scope during static resolution: causes resolver not to register the variable depth for `this`.

## Tradeoffs
- Allocating a new `Environment` and `LoxFunction` instance during `get` provides Python-style / JS-bound-method semantics cleanly without changing call dispatch bytecode or runtime stack conventions.

## CLI / Protocol format
- Input:
  ```lox
  class Animal {
    makeSound() {
      print this.sound;
    }
  }
  var dog = Animal();
  dog.sound = "Woof";
  dog.makeSound();
  ```
- Output:
  ```
  Woof
  ```

## Java specifics — lookup, don't memorize
- `scopes.peek().put("this", true)` initializes the synthetic variable in the current local scope without declaration-in-initializer check hazards.
