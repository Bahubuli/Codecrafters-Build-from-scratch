# Stage 34: Equality Operators

## In one line
Evaluating equality (`==`) and inequality (`!=`) across heterogeneous types using null-safe equality semantics.

## Self-test (cover the answers below and answer these first)

- How does Lox define equality across different types (e.g. number vs string)?

## The problem it solved
Unlike relational operators (`<`, `>`) which require both operands to be numbers, equality operators (`==`, `!=`) operate over any two operands, returning `false` for mismatched types rather than raising runtime errors.

## Concepts (the transferable part)
- **Null-Safe Equality**:
  ```java
  private boolean isEqual(Object a, Object b) {
      if (a == null && b == null) return true;
      if (a == null) return false;
      return a.equals(b);
  }
  ```
- **Heterogeneous Equality Semantics**:
  Comparing values of different types (such as `61 == "61"`) evaluates directly to `false`. Lox does not perform JavaScript-style loose type coercion with `==`.
- **Binary Evaluation Dispatch**:
  ```java
  case BANG_EQUAL:
      return !isEqual(left, right);
  case EQUAL_EQUAL:
      return isEqual(left, right);
  ```

## What breaks it (failure modes)
- Calling `.equals()` directly on a null reference causing `NullPointerException`.
- Throwing a type error on mismatched types instead of evaluating to `false`.
- Inadvertently coercing integers to strings prior to comparison.

## Tradeoffs
- Strict value equality vs implicit coercion — Strict type isolation prevents JavaScript-style `==` coercion bugs (e.g. `"" == 0 == false`).

## CLI / Protocol format
- Command: `./your_program.sh evaluate <file.lox>`
- Examples:
  - `"hello" == "world"` $\to$ `false`
  - `"foo" != "bar"` $\to$ `true`
  - `"foo" == "foo"` $\to$ `true`
  - `61 == "61"` $\to$ `false`
  - `156 == (89 + 67)` $\to$ `true`

## Java specifics — lookup, don't memorize
- `java.util.Objects.equals(a, b)` or explicit null check before `.equals()`.
