# Stage 04: Scanning - Other single-character tokens

## In one line
Punctuation and arithmetic operators (`,`, `.`, `-`, `+`, `;`, `*`) are scanned as distinct single-character tokens, expanding the lexical vocabulary without introducing lookahead or semantics.

## The problem it solved
Prior to this stage, encountering standard language punctuation like commas and semicolons, as well as arithmetic symbols (`+`, `-`, `*`), triggered `Unexpected character` errors and halted compilation with non-zero exit codes. Adding these cases allows the scanner to recognize all unambiguous single-character operators and punctuation.

## Concepts (the transferable part)
- **Lexical Homogeneity across Operator Categories** — The scanner does not differentiate between punctuation (`;`, `,`), member navigation (`.`), and arithmetic operators (`+`, `-`, `*`). They are all categorized as single-character tokens with `null` literals.
- **Syntactic Ambiguity Deferred to Parsing** — A minus sign `-` can be either binary subtraction (`a - b`) or unary negation (`-x`). The scanner never attempts to resolve this ambiguity; it simply produces a `MINUS` token and defers grammatical context to the parser.
- **Lookahead Deferral** — Operators that can prefix multi-character sequences or comments (such as `/` starting `//` comments, or `.` inside number literals `1.23`) require lookahead mechanisms (`peek()` / `match()`). Deferring `/` isolates pure 1-character tokenization from lookahead state machines.

## What breaks it (failure modes)
- Conflating `/` with single-character operators — Attempting to map `/` directly to `SLASH` breaks comment handling (`//`), causing comments to be tokenized as invalid slash operators rather than skipped trivia.
- Overloading `.` prematurely — Trying to inspect whether `.` is preceded or followed by digits at the single-character stage complicates the scanner. Number parsing will consume `.` as part of the number literal lexeme later.

## Tradeoffs
- Sequential `switch` dispatch vs Lookahead table — Individual `case` branches in a `switch` statement are straightforward, highly optimized by the JVM into jump tables or direct comparisons, and keep code clear without allocating helper maps.

## CLI / Protocol format
- Execution: `./your_program.sh tokenize <filename>`
- Output format: `<token_type> <lexeme> <literal>`
- Example for input `({*.,+*})`:
  ```
  LEFT_PAREN ( null
  LEFT_BRACE { null
  STAR * null
  DOT . null
  COMMA , null
  PLUS + null
  STAR * null
  RIGHT_BRACE } null
  RIGHT_PAREN ) null
  EOF  null
  ```

## Java specifics — lookup, don't memorize
- `switch` on `char` literals — `char` in Java is an unsigned 16-bit integer primitive (`\u0000` to `\uffff`), allowing fast dispatch without string heap allocations.
