# Stage 02: Scanning: Parentheses

## In one line
Single-character lexical tokens are extracted by matching characters directly to token types, intentionally ignoring structural constraints like delimiter balancing until parsing.

## Self-test (cover the answers below and answer these first)
- Why does the scanner emit tokens for unbalanced parentheses (e.g., `(()`) without raising an error?
- What is the architectural separation of concerns between lexical analysis (scanning) and syntactic analysis (parsing)?
- How do the `start` and `current` pointers isolate the lexeme slice without copying or altering source code?

## The problem it solved
Prior to this stage, any non-whitespace character in the source stream was flagged as an unexpected character error. This stage introduces tokenization for grouping symbols `(` and `)`, establishing the pattern for recognizing single-character punctuation in the language.

## Concepts (the transferable part)
- **Single-Character Token Recognition** — The simplest class of tokens where a single character uniquely determines the token identity without requiring lookahead or state machine transitions.
- **Separation of Concerns (Scanning vs. Parsing)** — The scanner answers *what words exist?* (lexical structure), not *do these words make a valid sentence?* (grammatical structure). Unbalanced parentheses are lexically valid tokens; the parser is responsible for verifying balanced matching.
- **Two-Pointer Lexeme Windowing** — Maintaining `start` (index marking the beginning of the token under evaluation) and `current` (index of the next character to inspect) allows exact lexeme slicing via `source.substring(start, current)`.

## What breaks it (failure modes)
- Precocious validation — Attempting to match or balance parentheses in the scanner breaks modularity and fails on valid language fragments, comments, or independent token tests.
- Pointer desynchronization — Forgetting to reset `start = current` before scanning the next token results in lexemes accumulating characters from previous tokens.

## Tradeoffs
- `switch` on `char` vs Hash Map / Lookup Table — A `switch` in Java compiles directly to `tableswitch` or `lookupswitch` bytecode instructions, offering zero-allocation O(1) branch dispatch and native handling of multi-character branches and side effects (e.g. incrementing `line`).

## CLI / Protocol format
- Execution: `./your_program.sh tokenize <filename>`
- Output format: `<token_type> <lexeme> <literal>`
- Example for input `(()`:
  ```
  LEFT_PAREN ( null
  LEFT_PAREN ( null
  RIGHT_PAREN ) null
  EOF  null
  ```

## Java specifics — lookup, don't memorize
- `String.substring(int beginIndex, int endIndex)` — Extracts a slice from `beginIndex` (inclusive) to `endIndex` (exclusive).
- `String.charAt(int index)` — Fetches the UTF-16 code unit `char` at the 0-based offset.
