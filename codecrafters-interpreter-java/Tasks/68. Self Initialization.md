# Stage 68: Self Initialization

## In one line
Compile-time detection and prohibition of local variables reading themselves in their own initializers via a 2-state (`false` = declared, `true` = defined) scope map.

## Self-test (cover the answers below and answer these first)
- Why is `var a = a;` allowed in global scope but prohibited in local block/function scopes?
- How does `Resolver` represent the state where a local variable has been declared but its initializer has not finished evaluating?
- What exit code is expected for compile-time resolution errors?

## The problem it solved
In dynamic languages, evaluating `var a = a;` in a local scope before `a` is defined is almost always a programmer mistake (intending to reference an outer `a` or self-referencing uninitialized state). Lox disallows reading a local variable within its own initializer at compile time, while still allowing global redeclaration/self-initialization for interactive/REPL compatibility.

## Concepts (the transferable part)
- **Two-Phase Variable Binding in Local Scopes**:
  1. `declare(Token name)`: Inserts the variable name into the innermost scope with value `Boolean.FALSE` (meaning declared but not yet ready to be read).
  2. `resolve(initializer)`: Recursively visits the initializer expression.
  3. `define(Token name)`: Marks the variable as `Boolean.TRUE` (meaning initialized and available).
- **Enforcing the Invariant**:
  In `Resolver.visitVariableExpr`:
  ```java
  if (!scopes.isEmpty() && scopes.peek().get(expr.name.lexeme) == Boolean.FALSE) {
      Main.error(expr.name, "Can't read local variable in its own initializer.");
  }
  ```
- **Global Exemption**:
  When `scopes.isEmpty()`, `declare()` and `define()` are no-ops because global variables in Lox have dynamic late-binding semantics. Thus `var a = a;` at top level correctly resolves to global `a`.

## What breaks it (failure modes)
- Inserting global variables into `scopes`, which would incorrectly reject valid global self-initialization.
- Checking all scopes in the stack instead of just the innermost scope (`scopes.peek()`) when checking for self-initialization (an inner variable reading an outer variable of the same name during its declaration would wrongly fail if outer scopes weren't distinguished).
- Emitting exit code `70` (runtime error) instead of `65` (compile-time semantic error).

## Tradeoffs
- Restricts recursive local functions defined via `var f = fun(...)` without a separate function statement syntax, but catches common shadowing and uninitialized variable bugs at compile time.

## CLI / Protocol format
- Command: `./your_program.sh run <file.lox>`
- Input:
  ```lox
  var a = "outer";
  {
    var a = a;
  }
  ```
- Stderr:
  ```
  [line 3] Error at 'a': Can't read local variable in its own initializer.
  ```
- Exit code: `65`

## Java specifics — lookup, don't memorize
- `Boolean.FALSE.equals(scope.get(name.lexeme))` or `scopes.peek().get(...) == Boolean.FALSE` safely checks boolean wrapper equality.
