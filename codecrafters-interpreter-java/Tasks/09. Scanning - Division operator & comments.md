# Stage 09: Scanning - Division operator & comments

## In one line
Introducing unconsumed lookahead (`peek`) allows distinguishing the division operator (`/`) from single-line comments (`//`) and skipping comments until newline without losing line-tracking semantics.

## Self-test (cover the answers below and answer these first)
- Why must the comment loop stop before consuming `\n` instead of consuming it as part of the comment?
- What does `peek()` return when the scanner is positioned at the end of the source string, and why is a sentinel like `\0` preferred over throwing an exception or returning `Optional<Character>`?
- Why does a comment not emit a `Token` at all, and what invariant does this maintain for downstream stages (parser, interpreter)?

## The problem it solved
Before this stage, `/` was unrecognized, causing lexical errors, and source code comments could not be filtered. Comments exist solely for human readability and must be stripped during lexical analysis so the parser only receives syntactically relevant tokens. Additionally, single-line comments share the initial `/` character with the division operator, requiring conditional lookahead to branch between emitting `SLASH` and discarding the rest of the line.

## Concepts (the transferable part)
- **Lookahead without Consumption (`peek`)** — Inspecting the upcoming character in the stream without advancing the read index (`current`), enabling arbitrary inspection before deciding whether or how to consume.
- **Trivia / Non-Token Discarding** — Comments and whitespace are lexical "trivia": source characters necessary for human readers that convey no semantic meaning to the grammar. The scanner drops them without calling `addToken()`.
- **Sentinel Value (`\0`)** — Returning a null character sentinel when indexing past EOF avoids throwing `StringIndexOutOfBoundsException` and eliminates repetitive bounds-checking boilerplate across lookahead routines.

## What breaks it (failure modes)
- Consuming `\n` inside the comment loop — If `advance()` consumes `\n` inside the comment discard loop, the outer `switch` never encounters `\n` and fails to increment `line`, desynchronizing line numbers for all subsequent error reporting.
- Infinite loop on EOF — A comment on the final line of a file without a trailing newline (`// end of file`) would cause an infinite loop if the loop only checked `peek() != '\n'` without checking `!isAtEnd()`.
- Accidentally swallowing following tokens — If `match('/')` fails, the scanner must emit `TokenType.SLASH` without consuming the subsequent character, ensuring tokens like `/(` or `/5` are preserved.

## Tradeoffs
- Leaving `\n` for the outer switch vs consuming and incrementing in comment loop — Stopping before `\n` keeps all line-increment logic centralized in `case '\n': line++; break;`. Consuming `\n` inside comments would duplicate line-tracking logic across multiple scanner states.
- Discarding comments in lexer vs emitting `COMMENT` tokens — Discarding simplifies the parser and AST since comments never pollute expression productions. Emitting comments or attaching them as syntax trivia is only needed for linters, formatters, and IDE tooling (e.g., Roslyn green/red trees).

## CLI / Protocol format
- Execution: `./your_program.sh tokenize <filename>`
- Output format: `<token_type> <lexeme> <literal>` on stdout for each token.
- Example for input `()// Comment`:
  ```
  LEFT_PAREN ( null
  RIGHT_PAREN ) null
  EOF  null
  ```
- Example for input `/()`:
  ```
  SLASH / null
  LEFT_PAREN ( null
  RIGHT_PAREN ) null
  EOF  null
  ```
- Exit code: `0` on clean lexical scan.

## Java specifics — lookup, don't memorize
- `source.charAt(current)` — Returns char at index `current` from the underlying `String`.
- `'\0'` — Null character literal in Java, used here as an in-band sentinel for EOF.
