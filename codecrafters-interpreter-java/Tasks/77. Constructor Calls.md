# Stage 77: Constructor Calls

## In one line
Invoking the `init()` method automatically upon class instantiation and forwarding call arguments to initialize instance properties.

## Self-test (cover the answers below and answer these first)
- What determines the arity of a class call in Lox?
- What does calling an instance's `init()` method directly return?
- What should happen if a return statement inside `init()` attempts to return an explicit value?

## The problem it solved
Creating objects without constructors requires manual field assignment on each instance, which is repetitive and error-prone. Lox provides automated initialization via the `init()` method, invoking it automatically upon class call with constructor arguments.

## Concepts (the transferable part)
- **Class Arity Delegation**:
  The class's `arity()` matches the `init` method if defined, or 0 if absent:
  ```java
  @Override
  public int arity() {
      LoxFunction initializer = findMethod("init");
      if (initializer == null) return 0;
      return initializer.arity();
  }
  ```
- **Constructor Dispatch in Class `call()`**:
  When a class is called as a constructor:
  ```java
  @Override
  public Object call(Interpreter interpreter, List<Object> arguments) {
      LoxInstance instance = new LoxInstance(this);
      LoxFunction initializer = findMethod("init");
      if (initializer != null) {
          initializer.bind(instance).call(interpreter, arguments);
      }
      return instance;
  }
  ```
- **Initializer Return Semantics (`isInitializer`)**:
  `init()` always returns `this`, even when called explicitly or exited via bare `return;`:
  ```java
  if (isInitializer) return closure.getAt(0, "this");
  ```
- **Static Validation of Initializer Returns**:
  `Resolver` marks `FunctionType.INITIALIZER` for methods named `"init"`. Returning an explicit value (`return x;`) inside an initializer is rejected at resolution time with:
  `Can't return a value from an initializer.`

## What breaks it (failure modes)
- Not checking arity of `init` on the class: allows calling `Foo(1, 2)` when `init` takes 0 arguments without argument count check.
- Not returning `this` from `init()` when called explicitly (`instance.init().foo`): causes `nil` dereference errors.

## Tradeoffs
- Reusing standard method dispatch for `init` simplifies the runtime architecture: constructors are regular methods with syntactic sugar at instance creation.

## CLI / Protocol format
- Input:
  ```lox
  class Robot {
    init(model, function) {
      this.model = model;
      this.function = function;
    }
  }
  print Robot("R2-D2", "Astromech").model;
  ```
- Output:
  ```
  R2-D2
  ```

## Java specifics — lookup, don't memorize
- `closure.getAt(0, "this")` fetches the bound instance directly from the outermost closure scope attached by `bind()`.
