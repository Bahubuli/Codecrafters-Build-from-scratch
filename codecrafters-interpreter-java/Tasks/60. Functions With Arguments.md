# Stage 60: Functions with arguments

## In one line
Passing arguments to user-defined functions and binding them to parameter names within the local function environment.

## Self-test (cover the answers below and answer these first)
- Where are function parameters bound when a function is invoked?
- How does Lox verify that the number of passed arguments matches the function's parameter count?
- What is the maximum number of parameters permitted by the Lox grammar?

## The problem it solved
Functions need input parameters to generalize computations. When a call expression is evaluated, positional argument values must be paired with parameter identifiers and bound inside a fresh local environment that encloses the function's declaration scope.

## Concepts (the transferable part)
- **Parsing Parameters vs Arguments**:
  - Parameters are identifiers in the function declaration: `fun f(a, b, c) { ... }`.
  - Arguments are arbitrary expressions evaluated at the call site: `f(1 + 2, x, "str")`.
  - Both enforce a 255-argument upper bound.
- **Arity Validation**:
  Before executing the function body, the interpreter compares argument count to `declaration.params.size()`:
  ```java
  if (arguments.size() != function.arity()) {
      throw new RuntimeError(expr.paren, "Expected " +
          function.arity() + " arguments but got " +
          arguments.size() + ".");
  }
  ```
- **Environment Binding**:
  In `LoxFunction.call()`:
  ```java
  Environment environment = new Environment(closure);
  for (int i = 0; i < declaration.params.size(); i++) {
      environment.define(declaration.params.get(i).lexeme, arguments.get(i));
  }
  ```
  Every parameter is defined in the freshly created local environment, shadowing any outer variables with the same names.

## What breaks it (failure modes)
- Binding arguments in the caller's environment rather than a dedicated new environment child of `closure`.
- Reusing the same environment across multiple calls (corrupting recursive or sequential calls).
- Mismatch between evaluation order of arguments (Lox requires left-to-right argument evaluation).

## Tradeoffs
- Creating a new `Environment` per function call allocates an environment map per activation record, cleanly separating call frames at minimal implementation complexity.

## CLI / Protocol format
- Command: `./your_program.sh run <file.lox>`
- Input:
  ```lox
  fun f3(a, b, c) { print a + b + c; }
  f3(24, 24, 24);
  ```
- Stdout:
  ```
  72
  ```
- Exit code: `0`

## Java specifics — lookup, don't memorize
- `declaration.params.get(i).lexeme` extracts parameter identifier strings.
