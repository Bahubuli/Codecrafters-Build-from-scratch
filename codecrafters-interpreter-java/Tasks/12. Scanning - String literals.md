# Stage 12: Scanning - String literals

## In one line
Scanning string literals requires consuming characters until a closing delimiter quote while handling multiline spans and detecting premature EOF as a syntax error.

## Self-test (cover the answers below and answer these first)
- What is the difference between a token's lexeme and its literal value for a string token?
- What happens if EOF is encountered before the closing quote delimiter?
- How should multiline string literals affect the scanner's internal line tracking?

## The problem it solved
Until now, source code containing double quotes caused unexpected character errors for each quote and tokenized or rejected whatever characters appeared inside. String literal scanning groups all characters between delimiters into a single token whose literal value strips away the quotes.

## Concepts (the transferable part)
- **Lexeme vs. Literal** — The lexeme is the exact sequence of raw source characters matched (including opening and closing quotes: `"hello"`), whereas the literal is the runtime value object produced by the scanner (raw string without quotes: `hello`).
- **Delimiter-Bounded Scanning** — Tokens enclosed by delimiters (quotes, regexes, block comments) use a loop scanning ahead until the closing delimiter is found, while guarding against end-of-input.
- **Lexical Multiline Support** — Strings can span multiple lines; encountering `\n` inside a string literal increments the line counter so subsequent compiler errors remain accurately located.

## What breaks it (failure modes)
- Unterminated string (`"hello` reaching EOF) — Must emit `[line N] Error: Unterminated string.` to stderr and flag `hasError = true`, without emitting a malformed `STRING` token.
- Off-by-one in literal extraction — Using `source.substring(start, current)` instead of `(start + 1, current - 1)` includes delimiter quotes in the literal value.
- Missing line counter increment on `\n` inside strings — Causes subsequent diagnostics in the source file to report erroneous line numbers.

## Tradeoffs
- Multiline string support by default vs single-line with escape sequences — Lox allows strings to span multiple lines naturally without requiring escapes (`\n`), simplifying scanning at the cost of less strict syntax error detection if an unclosed quote spans multiple lines.
- No escape character parsing (`\n`, `\"`, `\\`) in early scanning — Keeps the scanner pure and single-pass without complex state machines or string buffer copying, but limits string expressiveness until escape sequences are introduced.

## CLI / Protocol format
- Execution: `./your_program.sh tokenize <filename>`
- Output format:
  - `stdout`: `STRING "<raw_lexeme>" <literal_value>` followed by remaining tokens and `EOF  null`.
  - `stderr`: `[line N] Error: Unterminated string.` if the closing quote is missing.
- Exit code: `65` if unterminated string or lexical error occurs; `0` otherwise.

## Java specifics — lookup, don't memorize
- `source.substring(int beginIndex, int endIndex)` — Extracts a substring from `beginIndex` (inclusive) to `endIndex` (exclusive).
- `peek()` — Inspects the current character without advancing the pointer, returning `\0` if at EOF.
