# Stage 74: Instance Methods

## In one line
Storing method declarations in `LoxClass` and falling back to class method lookup when accessing a property on `LoxInstance`.

## Self-test (cover the answers below and answer these first)
- Where are methods physically stored: on the class or on each instance?
- What happens when a property name matches both an instance field and a method?
- How does the resolver treat returns inside methods compared to top-level returns?

## The problem it solved
Instances need shared behavior across objects of the same class. Methods defined inside a class block (`class C { method() { ... } }`) must be callable on instances of that class without copying method definitions into each instance object.

## Concepts (the transferable part)
- **Method Storage in `LoxClass`**:
  Methods are compiled into `LoxFunction` instances closed over the class declaration environment and stored in a lookup table inside `LoxClass`:
  ```java
  public class LoxClass implements LoxCallable {
      final String name;
      private final Map<String, LoxFunction> methods;

      public LoxFunction findMethod(String name) {
          return methods.get(name);
      }
  }
  ```
- **Property Resolution Priority (Fields before Methods)**:
  When accessing `instance.foo`, `LoxInstance` first inspects its own field table. If not found, it queries `klass.findMethod(name)`:
  ```java
  public Object get(Token name) {
      if (fields.containsKey(name.lexeme)) {
          return fields.get(name.lexeme);
      }

      LoxFunction method = klass.findMethod(name.lexeme);
      if (method != null) return method;

      throw new RuntimeError(name, "Undefined property '" + name.lexeme + "'.");
  }
  ```
- **Method Scoping in Resolver**:
  Methods are functions that can return values. In `Resolver.java`, `FunctionType.METHOD` is pushed during method resolution so that `return` statements inside methods do not trigger the top-level return error:
  ```java
  for (Stmt.Function method : stmt.methods) {
      FunctionType declaration = FunctionType.METHOD;
      resolveFunction(method, declaration);
  }
  ```

## What breaks it (failure modes)
- Storing methods in `LoxInstance.fields`: would cause memory bloat and prevent dynamic class method updates.
- Checking methods before fields: would violate Lox specification where shadowing an instance property hides the method.

## Tradeoffs
- Looking up methods in `LoxClass` at runtime gives classes dynamic behavior (dispatching via `findMethod`) while keeping instances lightweight.

## CLI / Protocol format
- Input:
  ```lox
  class Robot {
    beep() {
      print "Beep boop!";
    }
  }
  Robot().beep();
  ```
- Output:
  ```
  Beep boop!
  ```

## Java specifics — lookup, don't memorize
- HashMap lookup: `methods.containsKey(name)` followed by `methods.get(name)` ensures efficient lookup in amortized $O(1)$ time.
