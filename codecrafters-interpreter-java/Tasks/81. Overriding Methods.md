# Stage 81: Overriding Methods

## In one line
Enabling polymorphic method overriding by prioritizing subclass method tables over ancestor tables in method lookup while preserving dynamic dispatch on `this`.

## Self-test (cover the answers below and answer these first)
- Why does a subclass method override the superclass method without explicit `override` keywords in Lox?
- When an inherited method calls another method on `this`, which implementation is executed if a subclass overrides it?
- Can a subclass override `init` with a different arity?

## The problem it solved
Subclasses often need specialized behavior distinct from their parent classes (polymorphism). Without method overriding, all subclasses would be forced to use identical behavior from the superclass, limiting object-oriented modeling.

## Concepts (the transferable part)
- **Shadowing in Lookup Order**:
  In `LoxClass.findMethod`:
  ```java
  if (methods.containsKey(name)) {
      return methods.get(name);
  }
  if (superclass != null) {
      return superclass.findMethod(name);
  }
  return null;
  ```
  Checking the derived class first ensures that any method defined locally shadows/overrides any same-named method in ancestor classes.
- **Dynamic Dispatch via `this`**:
  When a method inherited from an ancestor calls `this.speak()`, `this` remains bound to the actual instance (e.g. `Puppy`). Property access `puppy.speak()` queries `puppy.klass.findMethod("speak")`, which starts the lookup from `Puppy` down to `Animal`, resolving `Puppy`'s version.
- **Constructor Overriding**:
  If a subclass defines its own `init(...)` with different arguments (e.g. `(a, b)` instead of `(a)`), `LoxClass.arity()` and `LoxClass.call()` query `findMethod("init")` and find the subclass's constructor directly.

## What breaks it (failure modes)
- Statically binding `this` to the class where the method was defined rather than the runtime instance receiver: breaks virtual method calls inside inherited methods.
- Superclass methods not being shadowed if table lookup is reversed (checking superclass first).

## Tradeoffs
- Duck typing / dynamic dispatch in Lox requires no type checking or virtual method tables (`vtable`), just recursive hash map lookups.

## CLI / Protocol format
- Input:
  ```lox
  class A {
    method() { print "A method"; }
  }
  class B < A {
    method() { print "B method"; }
  }
  B().method();
  ```
- Output:
  ```
  B method
  ```
  Exit code: 0

## Java specifics — lookup, don't memorize
- Dynamic dispatch in Java mirrors Lox's behavior: method invocations on `this` always invoke the most-derived override unless explicitly qualified with `super`.
