# Stage 41: Expression statements

## In one line
Parsing and executing standalone expression statements (`<expression>;`), evaluating their expressions for side effects (or runtime errors) while discarding results.

## Self-test (cover the answers below and answer these first)
- Does an expression statement output its evaluated result to `stdout`?
- What happens if an expression statement throws a `RuntimeError`?
- What grammar rule parses expression statements?

## The problem it solved
In imperative programs, expressions often perform side effects (such as function calls, assignments, or increments) rather than producing values consumed by an enclosing expression. Expression statements allow an expression to stand alone as a valid statement, ending with a semicolon.

## Concepts (the transferable part)
- **Expression Statement Grammar**:
  $$\text{statement} \to \text{exprStmt} \mid \text{printStmt}$$
  $$\text{exprStmt} \to \text{expression} \ ";"$$
- **Parsing Expression Statements (`Parser.java`)**:
  ```java
  private Stmt expressionStatement() {
      Expr expr = expression();
      consume(TokenType.SEMICOLON, "Expect ';' after expression.");
      return new Stmt.Expression(expr);
  }
  ```
- **Executing Expression Statements (`Interpreter.java`)**:
  ```java
  @Override
  public Void visitExpressionStmt(Stmt.Expression stmt) {
      evaluate(stmt.expression);
      return null;
  }
  ```
- **Halting on Runtime Error**:
  When an expression within an expression statement fails type checks (e.g. `49 + "baz"`), execution immediately stops, the error is printed to `stderr` with its source line number, and the interpreter terminates with exit code 70 without evaluating subsequent statements.

## What breaks it (failure modes)
- Printing expression statement evaluation results to stdout (only `print` statements should output).
- Swallowing runtime exceptions thrown during expression evaluation.
- Continuing execution of subsequent statements after a runtime error occurs.

## Tradeoffs
- Discarding the value of expression statements allows clean side-effect execution, but in interactive REPL environments users often expect bare expression evaluation to print results.

## CLI / Protocol format
- Command: `./your_program.sh run <file.lox>`
- Input:
  ```lox
  "foo" + "bar";
  print "baz";
  ```
- Stdout: `baz`
- Exit code: `0`

## Java specifics — lookup, don't memorize
- In Java, visitor method `visitExpressionStmt` returns `null` because `Stmt.Visitor<Void>` uses the `Void` wrapper type.
