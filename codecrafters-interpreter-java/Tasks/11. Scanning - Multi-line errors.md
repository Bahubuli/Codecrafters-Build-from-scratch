# Stage 11: Scanning - Multi-line errors

## In one line
Lexical error handling across multiple source lines requires preserving accurate line coordinate state across newlines while continuing scanning so developers receive all lexical diagnostics in a single pass.

## Self-test (cover the answers below and answer these first)
- Why must a scanner report all lexical errors across the whole file rather than halting at the first invalid character encountered?
- How does the scanner maintain the correct line coordinate when errors occur on lines separated by whitespace or comments?
- Why are valid tokens still emitted to stdout when errors are printed to stderr, and what should the overall process exit code be?

## The problem it solved
Compilers that fail-fast on the first syntax or lexical error force users into an agonizing edit-compile-fail loop fixing one syntax issue at a time. Continuing to scan after lexical errors while properly tracking line numbers across newlines provides all error locations up front while preserving valid tokens.

## Concepts (the transferable part)
- **Diagnostic Accumulation vs. Panic** — Instead of terminating immediately upon encountering invalid characters, the scanner logs diagnostic messages and records a persistent error flag (`hasError`), allowing the scan phase to finish and report all issues in a single compiler run.
- **Line State Invariant Across Errors** — Because newline characters increment the line counter regardless of prior or surrounding lexical errors, every subsequent diagnostic accurately reflects the true 1-based source line.
- **Stream Separation (POSIX stdout vs stderr)** — Emitting structured artifacts (valid tokens) to standard output while redirecting human-readable diagnostic messages to standard error keeps tooling and pipe-based workflows functional even in the presence of warnings or non-fatal inspection passes.

## What breaks it (failure modes)
- Halting on first error (`System.exit(65)` inside `scanToken`) — Breaks diagnostic accumulation by concealing subsequent errors on following lines.
- Forgetting to increment `line` in comments or strings spanning lines — Would cause subsequent line errors to be misattributed to earlier lines.
- Exiting with code 0 despite errors — Downstream toolchains assume a zero exit code means compilation succeeded, leading to cascading errors in the parser.

## Tradeoffs
- Immediate error reporting vs buffered diagnostic list — Printing immediately to `System.err` uses zero extra memory and is simple, but prevents reordering, deduplication, or attaching rich source context snippets that a structured diagnostic buffer would allow.
- Continuing to scan after unknown characters vs skipping to token boundaries — For single unexpected characters, advancing by one character and resuming scanning produces minimal cascading errors; for multi-character delimiters (e.g., unterminated multiline strings/comments), resynchronization or delimiter skipping is necessary.

## CLI / Protocol format
- Execution: `./your_program.sh tokenize <filename>`
- Output format:
  - `stderr`: `[line N] Error: Unexpected character: <character>` for each invalid character encountered.
  - `stdout`: `<token_type> <lexeme> <literal>` for each valid token scanned, ending with `EOF  null`.
- Exit code: `65` if any lexical errors were reported; `0` otherwise.

## Java specifics — lookup, don't memorize
- `System.err.println(...)` — Standard error stream in Java, used for diagnostics so standard output stream remains clean or machine-readable.
- `System.exit(65)` — Exits the JVM process with code 65 (the EX_DATAERR code in UNIX sysexits.h convention for input data format errors).

## Rebuild checklist
- [ ] Maintain an error tracking flag (`hasError = false`) set to `true` whenever an unexpected character is encountered.
- [ ] Track source line numbers using `line` incremented on `\n`.
- [ ] Print formatted errors `[line N] Error: Unexpected character: <c>` to `System.err`.
- [ ] Continue scanning after an unexpected character and emit all valid tokens including `EOF` to `System.out`.
- [ ] Check `hasError` in `Main.java` and exit with status code `65` if true.
