# Stage 66: Closures

## In one line
Closing over enclosing environments across function declarations so inner functions mutate and preserve surrounding local state across invocations.

## Self-test (cover the answers below and answer these first)
- Why does local variable `i` survive after `makeCounter()` finishes executing?
- If two different closures are created from the same factory function, do they share closed-over variables?
- How does assignment `i = i + 1` inside a closure find the correct variable binding?

## The problem it solved
Functions declared inside other functions frequently reference or mutate local variables from their enclosing functions. When the outer function returns, stack-allocated variables in languages like C would cease to exist. In Lox, these variables must remain alive and mutable for the lifetime of any closure referencing them.

## Concepts (the transferable part)
- **Heap-Allocated Environment Chains**:
  Because each `Environment` is a heap-allocated Java object, an outer environment remains reachable as long as an inner `LoxFunction` holds a reference to it in its `closure` field.
- **State Mutation through Enclosing Links**:
  When `count()` executes `i = i + 1;`:
  1. The call frame's `environment` does not define `i`.
  2. It delegates lookup and assignment up `environment.enclosing`.
  3. `i` is located in the environment created during the invocation of `makeCounter()`.
  4. Its value in that specific environment's `values` map is updated in place.
- **Closure Independence**:
  Each call to `makeCounter()` instantiates a distinct `Environment` instance. Thus, `var c1 = makeCounter();` and `var c2 = makeCounter();` close over separate `i` bindings and maintain independent state.

## What breaks it (failure modes)
- Storing environments on a call stack where they get popped and discarded when the outer function returns.
- Shallow copying environment values instead of retaining the live mutable `Environment` reference.
- Flattening scopes so distinct closures accidentally share the same variable slots.

## Tradeoffs
- Heap allocating environments for all function activations creates heap churn and garbage collection pressure, but provides clean, correct closure semantics without needing escape analysis.

## CLI / Protocol format
- Command: `./your_program.sh run <file.lox>`
- Input:
  ```lox
  fun makeCounter() {
    var i = 0;
    fun count() {
      i = i + 1;
      print i;
    }
    return count;
  }
  var counter = makeCounter();
  counter();
  counter();
  ```
- Stdout:
  ```
  1
  2
  ```
- Exit code: `0`

## Java specifics — lookup, don't memorize
- Passing outer `environment` into `new LoxFunction(stmt, environment)`.
