# Stage 08: Scanning - Relational operators

## In one line
Extending single-character lookahead (`match`) to `<` and `>` distinguishes strict inequality (`<`, `>`) from non-strict relational comparisons (`<=`, `>=`).

## Self-test (cover the answers below and answer these first)
- Why does relational operator scanning require looking ahead exactly one character rather than multiple characters?
- What sequence of tokens and lexemes is produced for the input `<<<==>>=`?
- If the lexer encounters `<` at the very end of the file, what prevents `match('=')` from throwing an `IndexOutOfBoundsException`?

## The problem it solved
In Lox and most C-family languages, relational operators share common prefixes: `<` prefixes both `LESS` and `LESS_EQUAL`, while `>` prefixes `GREATER` and `GREATER_EQUAL`. Without lookahead, the scanner would either prematurely classify every `<` as strict less-than or fail to bundle the trailing `=` into a single multi-character token. Using `match('=')` allows the lexer to greedily consume the `=` if present and emit the compound token, or leave the read pointer intact and emit the single-character operator.

## Concepts (the transferable part)
- **Maximal Munch (Greedy Lexing)** — When multiple lexical rules could match (e.g. `<` vs `<=`), the lexer always matches the longest possible sequence of characters that forms a valid token.
- **Relational vs Equality Comparisons** — Relational operators (`<`, `<=`, `>`, `>=`) express ordering comparisons between operands, distinct from equality checks (`==`, `!=`). At the scanning stage, both rely on identical lookahead disambiguation mechanics.
- **Atomic Lookahead and Consumption** — The `match` abstraction combines two fundamental scanner actions: inspecting the lookahead character (peeking) and conditionally advancing the stream pointer only if the expected character matches.

## What breaks it (failure modes)
- Unconditional character consumption — If `match()` advances even when the character is not `=`, an input like `<x` or `>y` would consume the identifier character `x` or `y`, destroying the token stream.
- EOF boundary overrun — Failing to check `isAtEnd()` prior to indexing `source.charAt(current)` causes crashes on trailing `<` or `>` at EOF.
- Lexeme substring misalignment — If `start` or `current` offsets are updated out of order, `source.substring(start, current)` will emit incomplete or corrupted lexemes (e.g. `<` instead of `<=`).

## Tradeoffs
- Reusing `match(char expected)` vs generalized lookahead `peek()` — For 1-character lookahead where the character is conditionally consumed immediately, `match()` is concise and avoids boilerplate `peek() == '=' ? advance() : ...`. However, generalized multi-character lookahead (like floating point numbers or comments) requires separate non-consuming `peek()` primitives.
- Distinct token types (`LESS_EQUAL`) vs generic binary operator token with attribute — Emitting specific enums like `TokenType.LESS_EQUAL` simplifies the parser's Pratt/recursive-descent precedence tables by avoiding string comparisons during grammar evaluation.

## CLI / Protocol format
- Execution: `./your_program.sh tokenize <filename>`
- Output format: `<token_type> <lexeme> <literal>` on stdout for each token.
- Example for input `<<=>>=`:
  ```
  LESS < null
  LESS_EQUAL <= null
  GREATER > null
  GREATER_EQUAL >= null
  EOF  null
  ```
- Exit code: `0` on clean lexical scan.

## Java specifics — lookup, don't memorize
- Ternary conditional expressions — `match('=') ? TokenType.LESS_EQUAL : TokenType.LESS` cleanly maps the boolean lookahead result to the target enum constant.
- Switch case branching — Dispatches on `<` and `>` with O(1) jump table efficiency.
