# Stage 16: Booleans & Nil

## The problem it solved
Up until this stage, our interpreter only recognized a linear sequence of isolated tokens (`TokenType`, `lexeme`, `literal`). It could not understand grammatical relationships or expression hierarchies. This stage introduces the `parse` command, building our first AST nodes (`Expr.Literal`) and rendering them back to standard output via an `AstPrinter` visitor.

## Concepts (the transferable part)
- **Syntactic Analysis (Parsing)** — Transforming a linear stream of tokens into a hierarchical tree structure (AST) that mirrors the nested grammatical structure of the language defined by a formal grammar.
- **Abstract Syntax Tree (AST)** — An intermediate tree representation where interior nodes represent operations (e.g. binary operations, groupings) and leaf nodes represent atomic operands/literals (e.g. booleans, numbers, strings).
- **The Visitor Pattern** — Decouples AST data structures from the operations performed on them. Instead of polluting `Expr` subclasses with printer, interpreter, and type checker methods, each operation is encapsulated in its own visitor class implementing `Expr.Visitor<R>`, invoking `expr.accept(this)`.
- **Recursive Descent Parsing** — A top-down parser where each grammar production rule (e.g., `expression`, `equality`, `comparison`, `term`, `factor`, `unary`, `primary`) corresponds to a method in the parser class. The lowest precedence rules appear near the top of the call stack, while atomic primaries are parsed at the base.

## What breaks it (failure modes)
- **Trailing Unconsumed Tokens** — If the parser consumes a literal but ignores remaining garbage or incomplete expressions without validating EOF or emitting syntax errors.
- **Null Reference on Nil Literal** — In Lox, `nil` has a Java value of `null`. If `AstPrinter` or string converters call `.toString()` on `expr.value` without checking for `null`, a `NullPointerException` crashes the process. Handling `expr.value == null ? "nil" : expr.value.toString()` ensures robust formatting.
- **Incorrect Exit Codes on Parse Error** — Syntactic errors during parsing must report the error location to `System.err` and exit with code `65`.

## Tradeoffs
- **Visitor Pattern vs Pattern Matching / Switch on Type** — Modern Java (Java 21+) supports sealed interfaces and pattern matching switches over records. However, the classic Visitor pattern mirrors Bob Nystrom's Crafting Interpreters reference design, maintaining strict type safety and cross-version portability.
- **Direct Interpretation vs AST Construction** — While simple calculators can evaluate during parsing, building an explicit AST is mandatory for tree-walk interpreters, allowing multiple passes (resolving, binding, optimization, interpretation).

## CLI / Protocol format
- Execution: `./your_program.sh parse <filename>`
- Output format:
  - `stdout`: String representation of the parsed expression AST.
  - Examples:
    - Input `true` $\to$ Output `true`
    - Input `false` $\to$ Output `false`
    - Input `nil` $\to$ Output `nil`
- Exit code: `0` on success, `65` on lexical or syntactic errors.

## Java specifics — lookup, don't memorize
- `interface Visitor<R>` — Generic visitor interface with parameterized return type `R`.
- `public abstract <R> R accept(Visitor<R> visitor);` — Double-dispatch entry point implemented by each AST node subclass.
- `Expr.Literal(Object value)` — AST leaf node carrying boolean (`Boolean.TRUE`/`Boolean.FALSE`) or `null` for `nil`.
