# Stage 12: Let the model choose a skill

## In one line
Empowering autonomous skill discovery by exposing the `Skill` function tool to the LLM so it can load appropriate skill bodies based on semantic user intent.

## Self-test (cover the answers below and answer these first)
- How does model-invoked skill selection differ from user-invoked slash commands?
- What schema properties are defined for the `Skill` tool?
- How is the system prompt augmented to guide the model when to invoke the `Skill` tool?

## The problem it solved
Prompting with explicit slash commands (like `/apple` or `/deploy`) requires the user to know every skill's name and exact purpose upfront. Real-world agents must interpret conversational user requests (e.g. "What is the database migration status?"), autonomously evaluate which specialized capability applies, and fetch the corresponding skill instructions dynamically without explicit user direction.

## Concepts (the transferable part)
- **Model-Initiated Dynamic Context Loading**:
  - The model inspects the advertised skills catalogue in its system prompt.
  - When user input aligns with a skill description, the model emits a tool call for `Skill` passing `name` and optional `args`.
- **System Prompt Router Framing**:
  - Appending explicit routing instructions:
    ```
    If a skill matches the user's request, call the Skill tool with its name and follow the instructions it returns.
    ```
  - Guides the model's policy to prefer tool-based instruction lookup over ungrounded generation.
- **Dynamic Context Injection via Tool Results**:
  - Supplying the skill instructions directly in the tool response message gives the model actionable context within the same ongoing multi-turn exchange.

## What breaks it (failure modes)
- **Vague Skill Descriptions**: Descriptions stating only what a skill is rather than when to use it prevent accurate semantic matching by the LLM.
- **Missing Skill Fallback**: Failing to return a clean error message when an invalid skill name is requested.
- **Double Invocation / Decoy Leakage**: Model invoking multiple skills or the wrong skill when descriptions overlap or lack discrimination.

## Tradeoffs
- **Tool-Based Skill Invocation vs Static Injection**: Dynamically loading instructions via tools keeps the initial context footprint tiny (~100 tokens per advertised skill) while supporting hundreds of modular skills.

## CLI / Protocol format
- User Invocation:
  ```bash
  $ ./your_program.sh -p "What is the database migration status?"
  ```
- Tool Call Generated by Model:
  ```json
  {
    "name": "Skill",
    "arguments": "{\"name\":\"apple\"}"
  }
  ```
- Tool Result Returned to Model:
  ```
  Skill: apple (located at .claude/skills/apple)
  Paths in the instructions below are relative to that folder.

  <body instructions>
  ```
- Final Model Output:
  ```
  blueberry
  ```

## Java specifics — lookup, don't memorize
- `FunctionDefinition.builder().name("Skill")` — Declares the function tool specification for skill dispatch.
- `argsNode.get("name").asText()` — Extracts the target skill identifier from the arguments payload.
