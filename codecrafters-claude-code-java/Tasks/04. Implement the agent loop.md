# Stage 04: Implement the agent loop

## In one line
Orchestrating an iterative multi-turn agent loop that sends user prompts, records assistant tool calls in conversation history, executes requested functions, and returns structured `tool` messages until the model reaches completion.

## Self-test (cover the answers below and answer these first)
- Why must the assistant message containing the `tool_calls` array be appended to the conversation history before appending the `tool` message?
- How does `tool_call_id` maintain causality and linkage between an LLM's tool invocation and the host's returned result?
- What is the termination condition for the agent loop?

## The problem it solved
Real-world coding tasks require multi-step reasoning (e.g. reading a file, analyzing its content, and synthesizing an answer). A single request-response cycle can only either ask for a tool call or give a final answer. This stage implements the autonomous agent loop: wrapping completions in a `while (true)` cycle that executes all returned tool calls, adds `ChatCompletionToolMessageParam` objects back to the prompt builder, and exits only when the model outputs text with no pending tool calls.

## Concepts (the transferable part)
- **The Agent Loop (ReAct / Action-Observation Cycle)** — The core architectural loop of modern AI agents: Prompt -> Thought/Action (Tool Call) -> Environment Observation (Tool Result) -> Next Action or Final Synthesis.
- **Message Role Topology (`user`, `assistant`, `tool`)** — A strictly ordered message sequence where an `assistant` tool-call turn must be immediately followed by corresponding `tool` observation messages tagged with matching `tool_call_id`s.
- **Agent Termination Semantics** — Detecting loop completion when `assistantMessage.toolCalls()` is empty or missing, indicating that the LLM has gathered all required context and emitted the final conversational response.

## What breaks it (failure modes)
- Out-of-order messages — Appending tool results without first recording the preceding assistant message violates the OpenAI wire protocol, resulting in a 400 Bad Request error.
- Mismatched or missing `tool_call_id` — The API requires each `role: "tool"` entry to explicitly match the `id` emitted by the assistant.
- Infinite loops — If tool errors are not handled or if the model oscillates without making progress, an agent loop without a max-iteration ceiling can loop indefinitely.

## Tradeoffs
- Mutation of message builder vs Immutable history lists — Mutating `ChatCompletionCreateParams.Builder` via `.addMessage()` keeps memory usage and serialization minimal in Java, while maintaining full multi-turn context across iterations.

## CLI / Protocol format
- Multi-Turn Conversation Protocol:
  1. `role: "user"`, `content: "Use README.md to determine the chemical expiry period in months. Number only."`
  2. `role: "assistant"`, `tool_calls: [{ "id": "call_123", "function": { "name": "Read", "arguments": "{\"file_path\": \"README.md\"}" } }]`
  3. `role: "tool"`, `tool_call_id: "call_123"`, `content: "<README content>"`
  4. `role: "assistant"`, `content: "6"`
- Exit: Standard output receives the final model text, exiting with code 0.

## Java specifics — lookup, don't memorize
- `createParamsBuilder.addMessage(ChatCompletionMessage)` — Automatically appends an assistant message turn into the builder context.
- `ChatCompletionToolMessageParam.builder().toolCallId(id).content(result).build()` — Constructs a tool result turn conforming to the OpenAI schema.
- `assistantMessage.toolCalls().isEmpty()` — Verifies absence of pending function dispatches.

## Rebuild checklist
- [ ] Initialize `ChatCompletionCreateParams.Builder` with model, tools, and initial user message.
- [ ] Enter `while (true)` loop and dispatch completion request.
- [ ] Add `assistantMessage` to builder history.
- [ ] If `toolCalls` is absent or empty, print content and break.
- [ ] Iterate through all `toolCalls`, execute each, and add `ChatCompletionToolMessageParam` to builder.
- [ ] Repeat loop until convergence.
