# Stage 03: Execute the read tool

## In one line
Detecting function tool calls in the LLM response payload, extracting JSON-encoded arguments using Jackson `ObjectMapper`, and executing the `Read` tool by reading file contents from disk directly to stdout.

## Self-test (cover the answers below and answer these first)
- Why does the model return `finish_reason: "tool_calls"` with null `content` instead of answering the user's question directly?
- How is the tool invocation represented in the response payload (`id`, `type`, `function.name`, `function.arguments`)?
- Why must tool arguments be parsed from a JSON string rather than accessed as native strongly-typed fields in the outer response?

## The problem it solved
Once an LLM has been made aware of available tools, it emits structured tool requests when it requires ground-truth data from the local environment (e.g., retrieving the contents of a source file). Previously, the program only handled plain text content, discarding tool call directives. This stage adds detection of `response.choices().get(0).message().toolCalls()`, decodes the `file_path` JSON argument, and executes file reading via `java.nio.file.Files.readString(Path.of(filePath))`.

## Concepts (the transferable part)
- **Model Inversion of Control (Tool Calling)** — The LLM pauses its text generation stream to delegate execution back to the host environment, passing structured parameters for external execution.
- **Tool Dispatcher Pattern** — Inspecting `toolCall.function().name()` to route the request to the matching local handler (`Read` -> filesystem read).
- **Stringified Arguments Protocol** — In the OpenAI specification, `arguments` is transmitted as an escaped JSON string to allow arbitrary schema payloads without altering the outer message format.

## What breaks it (failure modes)
- Non-existent or inaccessible file — Attempting to read a file path that does not exist or lacks read permissions throws `NoSuchFileException` or `AccessDeniedException`.
- Invalid JSON in `function.arguments` — While modern models usually generate valid JSON, edge cases or truncation require safe parsing via `ObjectMapper.readTree()`.
- Unhandled tool calls — If multiple tools or unrecognized tool names are returned without a fallback handler, the agent fails silently or crashes.

## Tradeoffs
- Direct execution & stdout dump vs Re-entrant conversation loop — Printing file contents directly to stdout satisfies single-stage CLI evaluation, but a complete agent requires feeding execution results back to the LLM in a multi-turn message history loop.

## CLI / Protocol format
- Model Response Structure:
  ```json
  {
    "choices": [
      {
        "index": 0,
        "message": {
          "role": "assistant",
          "content": null,
          "tool_calls": [
            {
              "id": "call_abc123",
              "type": "function",
              "function": {
                "name": "Read",
                "arguments": "{\"file_path\": \"apple.py\"}"
              }
            }
          ]
        },
        "finish_reason": "tool_calls"
      }
    ]
  }
  ```
- Command: `./your_program.sh -p "What is the content of apple.py? Print exact file contents without backticks."`
- Output: Exact file contents printed to stdout with exit code 0.

## Java specifics — lookup, don't memorize
- `message.toolCalls()` — Returns `Optional<List<ChatCompletionMessageToolCall>>`.
- `ObjectMapper.readTree(String)` — Jackson method parsing raw JSON string into a queryable `JsonNode` tree.
- `JsonNode.get("file_path").asText()` — Extracts the string value associated with a JSON property key.
- `Files.readString(Path.of(filePath))` — Java NIO utility reading entire file contents into a String using UTF-8 encoding.
