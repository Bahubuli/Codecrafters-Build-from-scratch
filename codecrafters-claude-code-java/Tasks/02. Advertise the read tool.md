# Stage 02: Advertise the read tool

## In one line
Registering tool definitions in the chat completion request payload using `FunctionDefinition` and `FunctionParameters` (JSON Schema) to expose the `Read` file capability to the LLM.

## Self-test (cover the answers below and answer these first)
- Why does an LLM need explicit tool advertising with JSON Schema before it can perform actions on the local filesystem?
- What are the mandatory fields in a tool schema, and how do `properties` and `required` instruct the model on valid argument construction?
- How does advertising a tool change the model's awareness without immediately executing any local code?

## The problem it solved
Language models are pure next-token predictors operating in isolated inference runtimes without direct access to the user's host environment. To allow an agent like Claude Code to inspect files, the application must advertise available functions along with strict parameter schemas. This stage defines the `Read` tool structure and passes it to the completion request via `.addTool(readTool)`.

## Concepts (the transferable part)
- **Tool Schema Definition (JSON Schema)** — Providing machine-readable signatures (`name`, `description`, and `parameters` conforming to JSON Schema) that define valid function inputs.
- **Model Grounding & Tool Awareness** — When tools are advertised in the request envelope (`tools: [...]`), the model factors available capabilities into its attention layers, allowing it to determine whether to respond with conversational text or emit a structured tool call.
- **Parameter Validation Contract** — Declaring parameter types (`type: "string"`) and enforcement arrays (`required: ["file_path"]`) constrains model outputs to well-formed argument objects.

## What breaks it (failure modes)
- Malformed JSON Schema — Failing to specify `"type": "object"` at the root of `parameters` causes provider validation errors (400 Bad Request).
- Missing `required` array — Allowing the model to emit tool calls without essential arguments like `file_path`.
- Overly strict vs ambiguous descriptions — Inaccurate or missing tool descriptions prevent the model from identifying the correct tool for file-reading tasks.

## Tradeoffs
- Static in-code tool definitions vs Dynamic tool registries — Hardcoding schemas inline is simple for small toolsets, but as tools expand (Write, Bash, Grep), an extensible `Tool` interface and registry pattern cleanly decouples schema definitions from the execution dispatcher.

## CLI / Protocol format
- Request Payload addition:
  ```json
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "Read",
        "description": "Read and return the contents of a file",
        "parameters": {
          "type": "object",
          "properties": {
            "file_path": {
              "type": "string",
              "description": "The path to the file to read"
            }
          },
          "required": ["file_path"]
        }
      }
    }
  ]
  ```
- Command: `./your_program.sh -p "How many tools are available to you in this request? Number only."`
- Verification: Model responds with `1` (positive number of available tools).

## Java specifics — lookup, don't memorize
- `FunctionParameters.builder()` — Builder for defining JSON Schema objects for tool argument validation.
- `JsonValue.from(Object)` — Wraps arbitrary Java primitives, Maps, or Collections into OpenAI SDK JSON AST values.
- `FunctionDefinition.builder()` — Constructs the function descriptor (`name`, `description`, `parameters`).
- `ChatCompletionTool.builder().function(...)` — Wraps a function into an API tool instance.
