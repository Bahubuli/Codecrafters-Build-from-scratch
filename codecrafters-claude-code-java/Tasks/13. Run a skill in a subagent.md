# Stage 13: Run a skill in a subagent

## In one line
Isolating complex skill execution in independent subagent loops via `context: fork` to prevent prompt pollution and return focused results.

## Self-test (cover the answers below and answer these first)
- What frontmatter key/value designates that a skill must execute inside a subagent?
- How does a subagent conversation differ in structure from the main agent conversation?
- Does the subagent receive the user's original query that prompted the skill invocation?
- How does the primary agent receive and incorporate the subagent's result?

## The problem it solved
When a skill performs an intensive multi-step sub-task (e.g. running multiple scripts, checking logs, examining dozens of files), placing all of those intermediate reasoning steps and tool outputs directly into the main conversation pollutes the model's context window. This increases latency, consumes tokens, and risks derailing long-running conversational memory. Forking to an isolated subagent keeps the main conversation clean, receiving only the synthesized final outcome.

## Concepts (the transferable part)
- **Hierarchical Agent Recursion (Forked Subagents)**:
  - Invoking the same fundamental agent loop over a sandboxed conversation stack.
  - The subagent receives strictly the skill instructions (`SKILL.md` body with arguments substituted) as a clean user message.
  - It does not inherit the primary conversational history or trigger prompt.
- **Context Isolation & Stack Boundary**:
  - Main Agent $\to$ Emits `Skill(name="...", ...)` tool call.
  - Runtime detects `context: fork` in the skill's manifest.
  - Runtime initiates child loop with isolated `ChatCompletionCreateParams`.
  - Child runs to completion, returning only its final textual output.
  - Runtime responds to the parent's tool call:
    `Skill <name> ran in a separate context and returned: <subagent_output>`
  - Main agent incorporates this result and delivers the final user response.
- **Termination of Command Stacking**:
  - A skill with `context: fork` terminates a slash command expansion sequence, preventing ambiguous cross-context chaining.

## What breaks it (failure modes)
- **Context Leaks**: Passing the main conversation history or original question to the subagent, violating prompt isolation requirements.
- **Infinite Recursion**: Subagents attempting to recursively invoke fork skills without depth limits or termination guards.
- **Missing Frontmatter Parser Support**: Failing to extract `context: fork` from the YAML header.

## Tradeoffs
- **Context Cleanliness vs Multi-turn Subagent Interaction**: One-shot subagent execution returns a concise result but cannot easily ask the parent agent follow-up clarifying questions without bidirectional inter-agent protocols.

## CLI / Protocol format
- User Invocation:
  ```bash
  $ ./your_program.sh -p "Who is on the on-call rotation right now?"
  ```
- Subagent Conversation:
  ```json
  [
    { "role": "user", "content": "Respond with exactly one word: blueberry" }
  ]
  ```
- Tool Result to Main Conversation:
  ```
  Skill apple ran in a separate context and returned: blueberry
  ```
- Final Agent Output:
  ```
  The on-call engineer is blueberry.
  ```

## Java specifics — lookup, don't memorize

- YAML parsing — Matching `context` in frontmatter keys and checking `"fork".equalsIgnoreCase(val)`.
