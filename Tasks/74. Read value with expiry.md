# Stage 74: Read Value with Expiry

## In one line
RDB keys with expiry timestamps (`0xFC` milliseconds, `0xFD` seconds) are loaded and respected: expired keys return `$-1`, non-expired keys return their value.

## The problem it solved
Persistent data often has TTLs. Without parsing `0xFC`/`0xFD` opcodes, the server would ignore expiry information and serve stale keys forever after a restart. This stage correctly reads expiry bytes before the value and stores them in `Entry.expiresAt`.

## Concepts (the transferable part)
- **Little-endian byte order** — RDB stores expiry as little-endian integers. The least significant byte comes first. Reconstruct with: `for (int i = 0; i < 8; i++) val |= ((long) in.read()) << (i * 8);` Note `i*8` (not `(7-i)*8`).
- **Expiry delegation to existing infrastructure** — `Entry.isExpired()` compares `System.currentTimeMillis() > expiresAt`. Storing the expiry from RDB in the same `Entry` means the existing `GET` expiry logic works without changes.
- **Don't load already-expired keys** — check `expiresAt <= System.currentTimeMillis()` at load time; skip the `store.put` if true. This avoids serving stale data even briefly.

## Wire format / protocol
RDB expiry opcodes precede the value type byte:
- `0xFC` + 8 bytes LE (milliseconds) + `0x00` (type) + key string + value string
- `0xFD` + 4 bytes LE (seconds) + `0x00` (type) + key string + value string

For `0xFD`, convert to milliseconds: `expirySec * 1000L` (use `L` suffix to avoid int overflow).

## What breaks it (failure modes)
- **Big-endian vs little-endian confusion** — using `(val << 8) | in.read()` instead of `val |= ((long)in.read()) << (i*8)` reads bytes in the wrong order; all expiry timestamps will be garbage.
- **int overflow in seconds-to-ms conversion** — `expirySec * 1000` without `L` overflows if `expirySec > 2_147_483`. Always multiply `long * 1000L`.
- **Missing value type byte** — after the 8/4 expiry bytes, there's always a 1-byte value type before key+value. Must consume with `in.read()` before calling `readRdbString`.

## Tradeoffs
- **Skip expired at load time** vs load and let `isExpired()` catch it — skipping at load keeps the store lean; the existing GET expiry check is a second safety net.

## Java specifics — lookup, don't memorize
- `((long) in.read()) << (i * 8)` — cast to `long` before shifting; otherwise shifts > 31 bits are undefined for `int`.
- `expiresAt <= System.currentTimeMillis()` — returns `true` for already-expired keys at load time.

## Rebuild checklist
- [ ] Handle `0xFC`: read 8 bytes LE into `long`, read value type byte, read key + value strings, skip if expired
- [ ] Handle `0xFD`: read 4 bytes LE into `long`, multiply by 1000L, read value type byte, read key + value, skip if expired
- [ ] Store non-expired keys as `new Entry(value, expiresAt)`
- [ ] Confirm `Entry.isExpired()` uses `System.currentTimeMillis() > expiresAt`
- [ ] GET returns `$-1\r\n` for expired/missing keys
