# Stage 72: Read Multiple Keys

## In one line
`KEYS *` returns all keys in the RDB file, not just the first one.

## The problem it solved
The RDB parser was already iterating through all key-value entries in a loop; Stage 70 could produce multiple `store.put()` calls. This stage confirms the `KEYS` handler correctly enumerates all entries in the map, not just one.

## Concepts (the transferable part)
- **Loop parsing until EOF opcode** — the `while(true)` loop in `loadRdb()` processes every key in the RDB file because it loops until `0xFF`. There's no one-key-only code path to fix.
- **`ConcurrentHashMap` iteration** — `store.entrySet()` gives a snapshot-consistent view of all keys; safe to iterate while other threads may be writing (from new `SET` commands).

## Wire format / protocol
`KEYS *` returns a RESP array of bulk strings:
`*<count>\r\n$<len1>\r\nkey1\r\n$<len2>\r\nkey2\r\n...`
Order is not guaranteed (`ConcurrentHashMap` doesn't preserve insertion order).

## What breaks it (failure modes)
- **Expired keys appearing in KEYS output** — filter with `!e.getValue().isExpired()` before adding to the list.
- **Keys with binary data** — getting byte length via `key.getBytes(StandardCharsets.UTF_8).length` rather than `key.length()` handles multi-byte UTF-8 characters.

## Tradeoffs
- **Eagerly filtering expired keys in KEYS** vs returning all and letting clients deal — Redis semantics require expired keys to be invisible; filter eagerly.

## Java specifics — lookup, don't memorize
- `store.entrySet()` — returns `Set<Map.Entry<String,Entry>>`; iterate with enhanced for-loop.
- `ConcurrentHashMap` iteration is weakly consistent — safe but may miss or include keys modified concurrently.

## Rebuild checklist
- [ ] `KEYS` handler iterates all `store.entrySet()` entries
- [ ] Filter out `e.getValue().isExpired()`
- [ ] Build RESP `*<n>` array with one `$<len>\r\n<key>\r\n` per key
- [ ] Confirm `loadRdb()` loop continues past first key (no early `return` or `break` after first entry)
