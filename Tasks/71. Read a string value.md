# Stage 71: Read a String Value

## In one line
`GET <key>` now returns values loaded from the RDB file, not just from in-session `SET` commands.

## The problem it solved
`KEYS *` could list keys from the RDB file (Stage 70), but `GET` was only looking at the in-memory store populated by `SET`. Since `loadRdb()` already populates the same `store` map, `GET` works for free — this stage confirms that the RDB load path and the `GET` handler share the same data structure.

## Concepts (the transferable part)
- **Single source of truth** — both `SET` (runtime) and `loadRdb()` (startup) write into the same `ConcurrentHashMap<String, Entry> store`. `GET` doesn't need to know which path created the entry.
- **Length-prefixed strings** — RDB stores strings as a size-encoded length followed by raw bytes. The length is decoded first, then exactly that many bytes are read. No null terminators, no delimiters.

## Wire format / protocol
Same as existing `GET` response:
- Found: `$<len>\r\n<value>\r\n`
- Not found / expired: `$-1\r\n`

## What breaks it (failure modes)
- **Integer-encoded string values** — RDB can store `"123"` as a 1-byte integer (`0xC0 0x7B`) rather than a 3-byte string. `readRdbString` must detect type==3 and return `String.valueOf(val)`.
- **Reusing `store` for RDB data** — expired check logic (`entry.isExpired()`) already works since `Entry` carries `expiresAt`.

## Tradeoffs
- **Sharing `store`** vs a separate `rdbStore` — sharing avoids duplication and means all commands (`GET`, `KEYS`, `TYPE`, `INCR`) see RDB data automatically.

## Java specifics — lookup, don't memorize
- `new String(bytes, StandardCharsets.UTF_8)` — decodes raw RDB bytes to Java string; always specify charset explicitly.

## Rebuild checklist
- [ ] Confirm `loadRdb()` calls `store.put(key, new Entry(value, null))` for non-expiring keys
- [ ] Confirm `GET` handler reads from `store` and checks `entry.isExpired()`
- [ ] Confirm `readRdbString` handles integer-encoded strings (type == 3)
