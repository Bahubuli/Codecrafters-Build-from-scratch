# Stage 4: Read a tree object

## In one line
Decompressing a `tree <size>\0` object and parsing the binary entries of format `<mode> <name>\0<20-byte-sha>` to list directory contents alphabetically.

## Self-test (cover the answers below and answer these first)
- How is the SHA-1 hash stored inside a tree object entry (hex string vs raw binary)?
- What distinguishes a directory entry from a file entry in the tree object's `<mode>` field?
- Where does the next entry in a tree object begin relative to the null byte after the entry name?

## The problem it solved
While blobs record file contents, they store neither filenames nor directory hierarchies. Git uses tree objects as the equivalent of filesystem inodes/directories, binding filenames, permissions (modes), and child SHA-1 hashes into a deterministic, queryable Merkle DAG.

## Concepts (the transferable part)
- **Merkle Tree Directory Structuring**: A tree references child trees and blobs strictly by hash. Modifying any nested file changes its blob hash, which propagates up to change the parent tree's hash, making the entire filesystem state cryptographically authenticated.
- **Hybrid Text/Binary Serialization**: To conserve storage in trees with thousands of entries, Git packs modes and filenames as variable-length null-terminated ASCII strings (`<mode> <name>\0`), immediately followed by a fixed 20-byte raw binary SHA-1 digest rather than a 40-byte hex string (saving 20 bytes per entry).
- **Mode Encodings**: Octal representations denote object classifications:
  - `100644` $\to$ Regular non-executable file (blob)
  - `100755` $\to$ Executable file (blob)
  - `120000` $\to$ Symbolic link (blob)
  - `040000` or `40000` $\to$ Subdirectory (tree)

## What breaks it (failure modes)
- Reading the SHA-1 as 40 ASCII characters instead of 20 raw binary bytes, shifting the byte pointer and corrupting all subsequent entry parses.
- Splitting entries on newlines: tree entries contain no newlines; parsing must rely strictly on spaces, null bytes, and 20-byte offsets.
- Forgetting that directory mode in tree objects is often stored as `40000` without a leading `0`, whereas `ls-tree` formats it as `040000`.

## Tradeoffs
- Raw 20-byte Binary Hashes vs 40-byte Hex Strings — 50% space reduction per tree entry, trading slight deserialization complexity for compact repository size.

## CLI / Protocol format
- Command: `./your_program.sh ls-tree --name-only <tree_sha>`
- Tree entry binary format:
  ```
  +--------+---+--------+----+------------------+
  | <mode> |   | <name> | \0 | 20-byte raw SHA1 |
  +--------+---+--------+----+------------------+
  ```

## Java specifics — lookup, don't memorize
- `System.arraycopy(decompressed, entryNullIdx + 1, shaBytes, 0, 20)` — extracts raw 20-byte binary hash.
- `ptr = entryNullIdx + 1 + 20` — advances pointer exactly 20 bytes past the null byte.
