# Stage 3: Create a blob object

## In one line
Framing a file's raw payload with `blob <size>\0`, computing its cryptographic SHA-1 digest to derive its immutable CAS identifier, and deflating the bytes via Zlib into `.git/objects/<sha[0..2]>/<sha[2..40]>`.

## Self-test (cover the answers below and answer these first)
- Is the SHA-1 hash computed over the raw file contents, or over `blob <size>\0` + contents?
- Is the SHA-1 hash computed before or after Zlib compression?
- What does the `-w` flag signify in `git hash-object -w <file>`?

## The problem it solved
To track changes and construct higher-level directory trees, Git needs a mechanism to ingest files from the working directory into the object database. Computing the content hash guarantees tamper-evidence and deduplication before writing to disk.

## Concepts (the transferable part)
- **Content-Addressable Hashing Envelope**: The canonical hash of any Git object is computed over the uncompressed framed payload:
  $$\text{SHA-1}("blob " + \text{size} + "\0" + \text{content})$$
  Because the type and size are baked into the hash prefix, different object types with identical payloads yield different hashes, preventing type confusion attacks.
- **Pre-compression Hashing**: Hashing the uncompressed stream ensures hash stability across different zlib implementations, compression levels, or dictionary configurations.
- **Write Flag Separation**: `hash-object` without `-w` acts as a pure read-only hash calculator (dry-run); `-w` persists the compressed object into `.git/objects/`.

## What breaks it (failure modes)
- Hashing the compressed bytes instead of the uncompressed framed payload.
- Omitting the null byte separator `\0` between header and content.
- Computing the length using characters rather than byte length (breaking on multi-byte UTF-8 files).
- Failing to create the 2-character hex subdirectory prior to writing the object file.

## Tradeoffs
- SHA-1 vs Modern Cryptographic Hashes (SHA-256) — Git historically adopted SHA-1 in 2005 for speed and 160-bit compact representation; Git 2.29+ supports SHA-256 via object format extensions, but SHA-1 remains standard for legacy compatibility.

## CLI / Protocol format
- Command: `./your_program.sh hash-object -w <file>`
- Output: `<40-character-hex-sha>\n`
- On-disk location: `.git/objects/<sha[0..2]>/<sha[2..40]>` (Zlib deflated).

## Java specifics — lookup, don't memorize
- `MessageDigest.getInstance("SHA-1")` — computes 160-bit digest.
- `new DeflaterOutputStream(new FileOutputStream(objectFile))` — zlib compresses byte stream.
- `String.format("%02x", b)` — formats byte as 2 lowercase hex digits.
