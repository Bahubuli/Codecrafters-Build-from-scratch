# Stage 7: Clone a repository

## In one line
Discovering remote references via Git's Smart HTTP `info/refs`, requesting target commit objects via `git-upload-pack`, parsing the binary PACK stream (decoding variable-length object headers, zlib payloads, and delta compressions), and recursively checking out the root commit tree.

## The problem it solved
Distributed version control requires synchronizing complete project histories over network transport efficiently. `git clone` implements the Smart HTTP negotiation protocol to discover server state, negotiate objects, and transfer thousands of commits, trees, and blobs inside a single compact, delta-compressed packfile stream.

## Concepts (the transferable part)
- **Smart HTTP Protocol & pkt-line Framing**: Network lines are prefixed by 4 hex characters encoding total packet length (`0000` signals a flush pkt). Reference discovery queries `GET /info/refs?service=git-upload-pack`, followed by negotiating requested tips via `POST /git-upload-pack` (`want <sha> ... done`).
- **Git Packfile Architecture**:
  - Magic signature: `PACK` (4 bytes).
  - Version: `0x00000002` (4 bytes).
  - Object count: 32-bit big-endian unsigned integer (4 bytes).
  - Packed object entries:
    - Byte 0: MSB (continuation), bits 4..6 (type: `OBJ_COMMIT=1`, `OBJ_TREE=2`, `OBJ_BLOB=3`, `OBJ_TAG=4`, `OBJ_OFS_DELTA=6`, `OBJ_REF_DELTA=7`), bits 0..3 (low 4 bits of uncompressed size).
    - Subsequent bytes: 7 bits of size per byte with MSB indicating continuation.
- **Delta Compression Resolution**:
  - `OBJ_REF_DELTA` (type 7): specifies the 20-byte raw SHA-1 of the base object.
  - `OBJ_OFS_DELTA` (type 6): specifies a variable-length negative byte offset to the base object earlier in the pack stream.
  - Delta instruction stream applies copies (`op & 0x80 != 0`) from base object slices and literal byte insertions (`op > 0`).

## What breaks it (failure modes)
- Skipping the `0000` flush-pkt or failing to handle pkt-line length prefixes properly when parsing `info/refs`.
- Misidentifying the start of the `PACK` stream after the server's `0008NAK\n` acknowledgement.
- Miscalculating the consumed compressed bytes from `Inflater` (leading to corrupted offsets for all subsequent packed objects).
- Not resolving deferred deltas where delta objects appear before their base objects in the pack stream.

## Tradeoffs
- Loose Objects vs Packfiles — Loose objects store one uncompressed file per object with high filesystem overhead; packfiles aggregate millions of objects into a single compressed stream using delta encoding, saving up to 90% bandwidth and disk space.

## CLI / Protocol format
- Command: `./your_program.sh clone <repo_url> <target_dir>`
- Protocol exchanges:
  ```
  Client                          Server
    |                               |
    | GET /info/refs?service=...    |
    |------------------------------>|
    | pkt-lines: HEAD, refs, caps   |
    |<------------------------------|
    |                               |
    | POST /git-upload-pack (want)  |
    |------------------------------>|
    | NAK + PACK (stream of objs)   |
    |<------------------------------|
  ```

## Java specifics — lookup, don't memorize
- `java.net.http.HttpClient` — native modern HTTP client for GET and POST byte transfers.
- `Inflater.getBytesRead()` — tracks exact number of compressed bytes consumed from the pack byte array.
- `Inflater.inflate(buf)` — decompresses stream until `inflater.finished()`.
