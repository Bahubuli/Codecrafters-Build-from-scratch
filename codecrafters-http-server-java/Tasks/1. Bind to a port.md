# Stage 1: Bind to a port

## Problem Solved

The server must create a listening TCP endpoint on `127.0.0.1:4221`.

It must stay alive while waiting for one client connection, accept that connection, and then finish because this stage does not require request handling yet.

## Concepts

- **TCP byte stream** - TCP provides an ordered, reliable stream of bytes between two endpoints.

- **Binding** - Binding associates a local IP address and port with the server process so the operating system can route incoming connection attempts to it.

- **Listening** - A listening socket represents a service endpoint that is ready to receive connection attempts.

- **`accept()`** - Accepting removes one completed connection from the listener's pending queue and returns a connected socket for that client.

- **HTTP is a later layer** - A successful TCP connection only establishes transport. No HTTP request has been received or parsed in this stage.

## Wire Format / Protocol

There is no HTTP wire format in this stage.

The only observable protocol behavior is a TCP connection accepted at `127.0.0.1:4221`.

The client and server exchange no application bytes before the server exits after the one accepted connection.

## Failure Modes

- **The process exits before binding** - Clients receive a connection-refused error or retry until their timeout expires.

- **Port 4221 is already in use** - The `ServerSocket` constructor throws `IOException`, which is reported to standard error.

- **The process binds the wrong address or port** - A client probing `127.0.0.1:4221` cannot connect even though another endpoint might be listening.

- **The listener is never accepted** - The server can remain blocked indefinitely, so the integration test terminates it in cleanup after its deadline.

- **The listener is not closed** - Repeated test runs can leave resources open or make restart behavior unreliable.

## Tradeoffs

- **One `accept()` vs. a loop** - One accept is sufficient for this stage and keeps the lifecycle explicit; a real server would loop to handle multiple connections.

- **Blocking I/O vs. asynchronous I/O** - Blocking `accept()` is the smallest correct model for one connection; asynchronous designs become useful when many connections or other work must progress concurrently.

- **`SO_REUSEADDR` vs. default socket behavior** - Reuse reduces restart failures during rapid test cycles; it does not replace correct ownership and cleanup of sockets.

- **No response vs. an HTTP response** - Sending bytes now would introduce behavior from later stages and obscure the transport-only requirement.

## Java Specifics

- `java.net.ServerSocket` - Creates a server-side TCP socket and can bind it to a local port.

- `new ServerSocket(4221)` - Binds and starts listening on port 4221 using the local host's address configuration.

- `setReuseAddress(true)` - Requests address reuse to make rapid restarts less likely to fail with an address-in-use error.

- `accept()` - Blocks until a client connection is ready, then returns the connected client socket.

- `try (...)` - The try-with-resources statement closes the `ServerSocket` automatically when the block exits.

- `System.err.println(...)` - Writes I/O failure details to standard error instead of treating an operational error as normal output.
