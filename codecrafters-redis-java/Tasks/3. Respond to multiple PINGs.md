# Stage 3: Respond to Multiple PINGs

---

## What You Have to Do

One client sends `PING` several times on the same connection and expects a `PONG` each time. The connection must stay open between commands.

---

## Thought Process

**The gap after stage 2:** we write one `+PONG\r\n`, fall into `finally`, close the socket — done after a single command. The client's second `PING` hits a closed connection.

**What's missing:** a loop that keeps servicing this connection until the client goes away. The questions that fall out of that: *when does the loop stop?* and *how does the server know the client is gone?*

---

## The Solution

```java
import java.io.IOException;
import java.io.InputStream;
import java.io.OutputStream;
import java.net.ServerSocket;
import java.net.Socket;
import java.nio.charset.StandardCharsets;

public class Main {
  public static void main(String[] args) {

    ServerSocket serverSocket = null;
    Socket clientSocket = null;
    int port = 6379;

    try {
      serverSocket = new ServerSocket(port);
      serverSocket.setReuseAddress(true);
      clientSocket = serverSocket.accept();

      OutputStream out = clientSocket.getOutputStream();
      InputStream in = clientSocket.getInputStream();
      byte[] buffer = new byte[1024];

      while (true) {
        int bytesRead = in.read(buffer);
        if (bytesRead == -1) break;

        out.write("+PONG\r\n".getBytes(StandardCharsets.UTF_8));
        out.flush();
      }

    } catch (IOException e) {
      System.out.println("IOException: " + e.getMessage());

    } finally {
      try {
        if (clientSocket != null) clientSocket.close();
      } catch (IOException e) {
        System.out.println("IOException: " + e.getMessage());
      }
    }
  }
}
```

## New Concepts in This Stage

**[CONCEPT] `read()` returning `-1` means the peer closed — EOF on the stream**  
When the client closes its side, TCP delivers a FIN. Your next `read()` drains any remaining bytes, and once there are none, returns `-1`. `-1` is **end-of-stream**, not an error and not "zero bytes right now." It's the in-band signal "this peer will never send another byte." That's why `-1` is your loop's exit condition. (Distinct from a count of `0`, which a blocking stream read won't normally hand you anyway.)

**[CONCEPT] A blocking read pins one thread to one connection**  
`in.read(buffer)` **blocks** — the thread parks until bytes arrive or the peer closes. Sit with what that means: while this thread is blocked waiting on *this* client, it can do nothing else. It cannot accept a new client, cannot service another connection. One thread is fully committed to one conversation. **Hold this thought — it's the entire problem of Stage 4.**

**[CONCEPT] A read is a chunk of bytes, not a command**  
`read()` hands you whatever bytes happen to have arrived — could be a partial command, could be several commands jammed together (the byte-stream truth from Stage 2). We dodge it here because we ignore the content and blindly answer `PONG` per read. That's a temporary cheat: a client sending two `PING`s in one packet might get a single read, and we'd reply once, not twice. It passes this stage's tester but is **not** a correct command loop. Flag it; we pay it off when we write the parser.

**[SYNTAX] The Java mechanics — lookup, don't memorize**  
- `getInputStream()` — the read half of the socket.
- `read(byte[])` — fills the array, returns count read, or `-1` at end-of-stream. Blocking.
- `byte[] buffer = new byte[1024]` — scratch space the read fills. Size is arbitrary here; not a protocol constant.
- `while (true) { … break; }` — loop until the exit condition fires.

---

## Failure Modes

- **No `-1` check / wrong check** — loop forever on a dead connection, or busy-spin. `-1` is the contract; honor it exactly.
- **Two commands in one read** — as above, our reply count won't match the command count. Correct only once a real parser counts commands instead of reads.
- **Assuming one `read` == one `PING`** — same root cause. Works for this tester, false in general.

---

## How the Loop Flows

```
client sends PING   →  read() > 0   →  write PONG  →  loop
client sends PING   →  read() > 0   →  write PONG  →  loop
client closes (FIN) →  read() == -1 →  break       →  close, done
```
