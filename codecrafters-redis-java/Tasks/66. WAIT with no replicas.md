# Stage 66: WAIT with no replicas

---

## In one line
Introduce the `WAIT <numreplicas> <timeout>` command on the Redis master to provide durability checkpoints, returning a RESP integer `:0\r\n` immediately when no replicas are connected.

---

## Self-test (cover the answers below and answer these first)
1. **What is the distributed systems purpose of the `WAIT` command in Redis, and what guarantee does it provide to clients?**
   - *Answer*: Redis uses asynchronous replication by default, meaning writes return `+OK` on the master before replicas acknowledge or even receive them. `WAIT numreplicas timeout` turns asynchronous replication into an optional semi-synchronous durability barrier for a specific client: it blocks the client until all prior write commands sent on this connection have been acknowledged by at least `numreplicas` replicas, or until `timeout` milliseconds elapse.
2. **Why does `WAIT` immediately return `:0\r\n` when `replicas.isEmpty()` or when `numreplicas == 0`?**
   - *Answer*: If no replicas are connected to the master, it is physically impossible for any replica to acknowledge writes. Rather than blocking the client until the full `timeout` expires (which could be tens of seconds), the master evaluates the precondition immediately: with zero replicas in existence, zero replicas have acknowledged writes. It terminates the barrier at once and returns integer 0 (`:0\r\n`).
3. **How does `WAIT` handle the timeout parameter when no replicas are connected?**
   - *Answer*: The timeout specifies the *maximum* time a client is willing to wait if the requested condition is not yet satisfied. When the master determines that zero replicas are present, it does not sleep or block for the timeout; it immediately sends `:0\r\n`.
4. **What RESP data type must `WAIT` return, and what is its exact wire representation?**
   - *Answer*: A RESP Integer, prefixed by a colon `:` and terminated by `\r\n`. For zero acknowledged replicas, the exact wire frame is `:0\r\n` (4 bytes).
5. **Does `WAIT` mutate database state, and should it be propagated to replicas?**
   - *Answer*: No. `WAIT` is a read-only coordination barrier command for client session durability. It does not alter key-value or list/stream data, and must *never* be appended to the master replication stream or sent to replicas.
6. **What is the time complexity of `WAIT 0 <timeout>` when no replicas are connected?**
   - *Answer*: $\mathcal{O}(1)$. The master performs an $\mathcal{O}(1)$ check on the connected replicas collection and writes a 4-byte RESP integer to the client socket.

## Problem Solved

Up to Stage 65, our Redis master propagated write commands to replicas purely asynchronously:
1. When a client executes `SET foo bar`, the master updates its in-memory database and writes the command to all replica sockets in `propagate()`.
2. The client receives `+OK\r\n` immediately, without waiting for replicas to read, process, or acknowledge the write.
3. If the master were to crash immediately following that write, any replica promoted to master during failover might lose that write (split-brain or data loss window).

In real-world Redis, clients that require strict durability guarantees (such as payment processing or consensus operations) call `WAIT <numreplicas> <timeout>` directly after a write. This instructs the master to pause the client until the specified number of replicas have confirmed processing all preceding write commands.

Stage 66 implements the initial foundation of `WAIT` on the master. Before handling complex replica handshakes, asynchronous `GETACK` polling, and timeout loops (coming in subsequent stages), the master must parse `WAIT <numreplicas> <timeout>`. When no replicas are connected (`replicas.isEmpty()`), the master recognizes that no replicas can acknowledge writes and immediately returns `:0\r\n`.

## Thought Process & Architectural Model

### 1. Redis Replication Durability Spectrum

Replication models in distributed datastores span a spectrum from fully asynchronous to fully synchronous:

```text
Asynchronous (Default Redis)          Semi-Synchronous (Redis WAIT)           Fully Synchronous (2PC / Paxos)
Master writes -> ack client -> repl    Master writes -> repl -> wait ACKs     Master & All Replicas consensus
Latency: Low (RAM speed)               Latency: Configurable per-command       Latency: High (network roundtrip)
Durability: Weak (potential loss)      Durability: High (client-controlled)    Durability: Strict
```

`WAIT` allows individual clients to selectively opt into semi-synchronous durability without penalizing other asynchronous clients sharing the same server.

### 2. WAIT Command Anatomy

The command format is:
```text
WAIT <numreplicas> <timeout>
```
- `<numreplicas>`: The target threshold of replicas that must have acknowledged the replication offset corresponding to the client's last write command.
- `<timeout>`: The maximum threshold in milliseconds to block waiting for replicas. A timeout of `0` means block indefinitely until `numreplicas` acknowledge.

When no replicas exist:
- Target count: 0 or more.
- Actual replicas connected: 0.
- Result: 0 replicas have acknowledged.
- Decision: Immediate return `:0\r\n`.

## Full Solution

In `codecrafters-redis-java/src/main/java/Main.java`, the command dispatcher `handleCommand` is extended to recognize `WAIT`:

```java
    } else if (command.equalsIgnoreCase("WAIT")) {
      // Stage 66: WAIT <numreplicas> <timeout>
      // The WAIT command checks how many replicas have acknowledged all previous write commands.
      // Format: WAIT <numreplicas> <timeout>
      // When no replicas are connected (replicas.isEmpty()), immediately return :0
.
      int numReplicas = parts.length > 1 ? Integer.parseInt(parts[1]) : 0;
      long timeout = parts.length > 2 ? Long.parseLong(parts[2]) : 0;
      if (replicas.isEmpty()) {
        out.write(":0
".getBytes(StandardCharsets.UTF_8));
      } else {
        out.write((":" + replicas.size() + "
").getBytes(StandardCharsets.UTF_8));
      }
    }
```

### Flow Breakdown:
1. **Token Extraction**:
   - `parts[0]` is `"WAIT"`.
   - `parts[1]` is parsed as `numReplicas` (e.g., `0`).
   - `parts[2]` is parsed as `timeout` in milliseconds (e.g., `60000`).
2. **Immediate Condition Check**:
   - `replicas` is our thread-safe `CopyOnWriteArrayList<OutputStream>` storing active replica output streams (registered during `PSYNC`).
   - When `replicas.isEmpty()` is true, 0 replicas are connected.
3. **RESP Wire Emission**:
   - Emits `:0
` directly to the client's `OutputStream`.
   - The caller loop performs `out.flush()`, delivering the byte sequence immediately across TCP.

## Concepts (the transferable part)

- **Durability Barriers**: In event-driven or distributed systems, durability barriers allow callers to pause execution until asynchronous background replication pipelines synchronize to a specific sequence number or high-water mark.
- **Precondition Fast-Path**: When evaluating blocking or asynchronous operations with timeouts, always test boundary preconditions first. If the precondition can never be met (e.g., zero available workers/replicas) or is trivially met, returning immediately avoids blocking threads, scheduling timers, or holding connection pools.
- **Separation of Control Commands from Data Commands**: Control barrier commands (`WAIT`, `PING`, `INFO`, `CLIENT LIST`) coordinate client connections or server topology. Unlike data mutation commands (`SET`, `DEL`, `INCR`), they must not mutate the state machine or replicate down the pipeline.

## Failure Modes

- **Blocking on Timeout When No Replicas Exist**:
  - *Hazard*: Naively calling `Thread.sleep(timeout)` before returning `0`.
  - *Consequence*: The client blocks for 60,000 milliseconds (1 minute), causing tests to fail due to timeout.
  - *Mitigation*: Verify `replicas.isEmpty()` and return `:0
` immediately.
- **Returning Bulk String Instead of RESP Integer**:
  - *Hazard*: Writing `$1
0
` instead of `:0
`.
  - *Consequence*: Redis clients parse `$1
0
` as string `"0"`, triggering type assertion errors in client libraries and CodeCrafters test runners.
- **Replicating `WAIT` Command**:
  - *Hazard*: Calling `propagate(parts)` on `WAIT`.
  - *Consequence*: Master sends `WAIT` to replicas over the replication link. Replicas would attempt to parse `WAIT`, potentially stalling or throwing syntax errors.

---

## Tradeoffs

- **Synchronous Master-Side Evaluation vs Timed Future/Poller**:
  - *Evaluation*: When no replicas are connected, no asynchronous polling or timer scheduling is needed. Synchronous $\mathcal{O}(1)$ dispatch avoids allocating timer threads or scheduling futures in Java's `ScheduledExecutorService`.
- **`CopyOnWriteArrayList<OutputStream>` for Replicas**:
  - *Evaluation*: Reads (`replicas.isEmpty()`, iterations during command propagation) require zero locking and are blazing fast. Writes (adding a replica during `PSYNC`, removing on disconnect) create a copy of the underlying array, which is completely acceptable since replica connections occur infrequently compared to high-frequency command execution.

---

## Java Specifics - lookup, don't memorize

- `CopyOnWriteArrayList.isEmpty()`: Returns `true` if the list contains no elements, without acquiring coarse synchronization locks.
- `Integer.parseInt(String)` / `Long.parseLong(String)`: Parses standard decimal numbers from command arguments into signed primitives.
- `StandardCharsets.UTF_8`: Thread-safe constant representing UTF-8 character encoding, preventing per-call charset lookup overhead.
