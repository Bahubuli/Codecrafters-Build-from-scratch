# Stage 5: Implement the ECHO command

---

## What You Have to Do

Support the `ECHO` command. It takes one argument and sends it straight back, encoded as a RESP **bulk string**. The argument is random each run — no hardcoding. Command names are case-insensitive (`ECHO`, `echo`, `EcHo`).

```
$ redis-cli ECHO hey
hey
```

**In** (what the client sends — a RESP array of bulk strings):
```
*2\r\n$4\r\nECHO\r\n$3\r\nhey\r\n      ==  ["ECHO", "hey"]
```
**Out** (the argument as a bulk string):
```
$3\r\nhey\r\n
```

---

## Thought Process

**The gap after stage 4:** every stage so far ignored the client's bytes and blindly wrote `+PONG\r\n`. PING needs no input. ECHO does — the argument is random, so the only way to return it is to actually *read and understand* what the client sent. That means parsing RESP for the first time, and this parser is the foundation every later command (GET, SET, …) is built on.

**The realization:** RESP is **length-prefixed**. You never scan for a keyword or split on spaces — every part announces its own size, and you obey that size. The array says how many elements; each bulk string says how many bytes. Parse by structure, not by searching.

## The Solution

```java
import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStream;
import java.io.InputStreamReader;
import java.io.OutputStream;
import java.net.ServerSocket;
import java.net.Socket;
import java.nio.charset.StandardCharsets;

public class Main {
  public static void main(String[] args) {
    int port = 6379;

    try {
      ServerSocket serverSocket = new ServerSocket(port);
      serverSocket.setReuseAddress(true);

      while (true) {
        Socket clientSocket = serverSocket.accept();

        new Thread(() -> {
          try {
            OutputStream out = clientSocket.getOutputStream();
            InputStream in = clientSocket.getInputStream();
            BufferedReader reader = new BufferedReader(new InputStreamReader(in));

            while (true) {
              String line = reader.readLine();
              if (line == null) break; // client closed

              int n = Integer.parseInt(line.substring(1)); // "*2" -> 2

              String[] parts = new String[n];
              for (int i = 0; i < n; i++) {
                reader.readLine();            // "$4" length line — skipped
                parts[i] = reader.readLine(); // payload: "ECHO", "hey"
              }

              String command = parts[0];
              if (command.equalsIgnoreCase("ECHO")) {
                String arg = parts[1];
                String response = "$" + arg.length() + "\r\n" + arg + "\r\n";
                out.write(response.getBytes(StandardCharsets.UTF_8));
                out.flush();
              } else if (command.equalsIgnoreCase("PING")) {
                out.write("+PONG\r\n".getBytes(StandardCharsets.UTF_8));
                out.flush();
              }
            }
          } catch (IOException e) {
            System.out.println("IOException: " + e.getMessage());
          }
        }).start();
      }
    } catch (IOException e) {
      System.out.println("IOException: " + e.getMessage());
    }
  }
}
```

## New Concepts in This Stage

**[CONCEPT] RESP is length-prefixed, not delimiter-scanned**  
Every RESP value starts with a one-byte type marker (`*` array, `$` bulk string, `+` simple string) and states its own size. `*2` = "2 elements follow." `$4` = "the next 4 bytes are the payload." You read the count/length, then read exactly that much — you never search the bytes for a keyword or split on spaces. This is the whole point: a bulk string can contain **anything**, including spaces or the literal bytes `ECHO`, and the parser is never fooled, because it counts bytes instead of matching patterns. (Contrast: scanning for `"ECHO"` breaks the instant the *argument* is `ECHO`, e.g. `ECHO ECHO`.)

**[CONCEPT] The wire is RESP in both directions**  
You read a RESP array in and write a RESP bulk string out. `+PONG\r\n` was always RESP too — you just hadn't had to *decode* any before. Encoding the reply is the mirror of parsing: `$<length>\r\n<bytes>\r\n`, where the length you emit is the argument's byte count.

**[CONCEPT] Parsing means structure, then dispatch**  
The parser's job is to turn a flat byte stream into structured data — here, `["ECHO", "hey"]`, an ordered list of strings. Only *then* does the caller branch: look at element 0 (the command), act on the rest (the arguments). Separating "decode the bytes" from "decide what to do" is the shape every command handler will follow.

**[SYNTAX] The Java mechanics — lookup, don't memorize**  
- `new BufferedReader(new InputStreamReader(in))` — wraps the raw byte stream so you can read whole CRLF-terminated lines.
- `readLine()` — reads up to `\r\n` and returns the line **without** the terminator; returns `null` at end-of-stream (the reader's version of `read() == -1`).
- `line.substring(1)` — drops the leading type marker (`*`, `$`), leaving just the number to parse.
- `arg.length()` — String length is a **method** (parentheses); array length (`buffer.length`) is a **field** (no parentheses). Easy trap.
- `equalsIgnoreCase("echo")` — case-insensitive compare, because Redis command names are case-insensitive.

---

## Failure Modes

- **Scanning for `"ECHO"` / grabbing "the next word"** — breaks when the argument is `ECHO` or contains spaces. RESP is length-prefixed precisely so you don't do this. Parse by structure.
- **`arg.length` vs `arg.length()`** — the missing parentheses is a compile error on String; a real trap because arrays go the other way.
- **Forgetting `equalsIgnoreCase`** — `echo` or `EcHo` from the tester would silently fall through and get no reply.
- **Wrong bulk-string length** — emitting a length that doesn't match the byte count produces a malformed reply the client can't frame. Here `arg.length()` works for ASCII; for multi-byte UTF-8 it would be wrong (character count ≠ byte count) — a latent bug, see tradeoffs.
- **Off-by-one in `substring`** — `substring(0)` keeps the `*`, and `Integer.parseInt("*2")` throws. Must be `substring(1)`.

---

## Tradeoffs / What We Cut Corners On

This parser passes the stage but leans on two shortcuts worth naming — we pay them off later:

- **`readLine()` re-introduces delimiter-thinking.** We taught "obey the length prefix," but `readLine()` actually ignores `$4` and scans for `\r\n`. That works only because the tester sends text with no embedded CRLF. A **strict** parser reads the `$` length, then reads *exactly* that many bytes — which is the only correct approach once bulk strings can contain arbitrary binary (including `\r\n`). We skip the `$` length line for now (`reader.readLine();` with no assignment) on purpose.
- **`arg.length()` counts characters, not bytes.** Correct for ASCII, wrong for multi-byte UTF-8. The RESP length is a *byte* count, so the byte-exact version is `arg.getBytes(UTF_8).length`.
- **No command abstraction yet.** An `if/else if` chain is fine for two commands; it won't scale. Later we refactor parse → dispatch into something cleaner.

## How It Flows

```
read "*2"          → n = 2, expect 2 elements
  read "$4","ECHO" → parts[0] = "ECHO"
  read "$3","hey"  → parts[1] = "hey"
command = "ECHO"   → arg = "hey"
write "$3\r\nhey\r\n"
```
