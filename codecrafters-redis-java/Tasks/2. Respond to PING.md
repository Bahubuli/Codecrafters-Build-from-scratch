# Stage 2: Respond to PING

---

## What You Have to Do

When a client sends `PING`, reply with `+PONG\r\n`. You may ignore what they sent and hardcode the response.

---

## Thought Process

**The gap after stage 1:** we accept a connection and then go silent. The client is waiting to hear something back.

**What does the client actually expect on the wire?** Not the text `PONG`. It expects bytes in a specific framing: `+PONG\r\n`. That framing is **RESP** (Redis Serialization Protocol).

**Why does RESP exist at all?** This is the load-bearing idea of the whole project — see the concept below.

---

## The Solution

```java
import java.io.IOException;
import java.io.OutputStream;
import java.net.ServerSocket;
import java.net.Socket;
import java.nio.charset.StandardCharsets;

public class Main {
  public static void main(String[] args) {

    ServerSocket serverSocket = null;
    Socket clientSocket = null;
    int port = 6379;

    try {
      serverSocket = new ServerSocket(port);
      serverSocket.setReuseAddress(true);
      clientSocket = serverSocket.accept();

      OutputStream out = clientSocket.getOutputStream();
      out.write("+PONG\r\n".getBytes(StandardCharsets.UTF_8));
      out.flush();

    } catch (IOException e) {
      System.out.println("IOException: " + e.getMessage());

    } finally {
      try {
        if (clientSocket != null) clientSocket.close();
      } catch (IOException e) {
        System.out.println("IOException: " + e.getMessage());
      }
    }
  }
}
```

## New Concepts in This Stage

**[CONCEPT] TCP is a byte stream with no message boundaries**  
This is the most important idea in the project, so internalize it now while it's harmless. TCP guarantees your bytes arrive **in order** and **without loss**. It guarantees **nothing** about chunking. If a peer writes `PING` then `PONG`, the other side might read `PINGPONG` in one shot, or `PIN` then `GPONG`. TCP has no concept of "a message."

So if you want messages, *you* impose them. That's what RESP is: a framing convention on top of the raw stream. `+PONG\r\n` is us telling the client "a simple-string message starts at `+` and ends at `\r\n`." The `\r\n` isn't decoration — it's the boundary marker that makes the stream parseable. You'll feel the pain of this directly once you have to *parse* input (later stage); right now you only have to *produce* well-framed output.

**[CONCEPT] Bytes are the wire currency; strings are a local convenience**  
The socket moves bytes. A Java `String` is an in-memory abstraction. The boundary between them is an **encoding** — a rule mapping characters to byte values. You cross that boundary explicitly with `getBytes(UTF_8)`. Forgetting that strings and bytes are different things is a classic source of protocol bugs.

**[CONCEPT] Buffering and flush**  
Writes don't necessarily hit the network immediately — they may sit in a buffer so the OS can batch them into fewer, larger sends (syscalls are expensive; batching amortizes them). `flush()` forces the buffer out *now*. Skip it and the client may wait for bytes that are still parked in your process. This is the same family of idea as backpressure: data in flight is data sitting in buffers somewhere.

**[SYNTAX] The Java mechanics — lookup, don't memorize**  
- `getOutputStream()` — the write half of the connected socket.
- `getBytes(StandardCharsets.UTF_8)` — String → `byte[]` using UTF-8.
- `write(byte[])` / `flush()` — push bytes, then force them out.
- `\r` = CR (13), `\n` = LF (10). RESP terminates every message with the pair `\r\n` (CRLF).

---

## Failure Modes

- **Forgot `flush()`** — with a raw `OutputStream` from a socket this often still works (it's unbuffered), but the instant you wrap it in a `BufferedOutputStream` or `BufferedWriter`, a missing flush means the client hangs. Flush is cheap insurance.
- **Wrong terminator** — `+PONG\n` (LF only) or `+PONG` (none) is malformed RESP. A real `redis-cli` would hang waiting for the boundary or error.
- **Assuming one write = one read on the client** — it doesn't (see the byte-stream concept). For a single tiny response you'll get away with it; don't build a mental model that relies on it.

## Wire Format

| Prefix | RESP type | Example |
|--------|-----------|---------|
| `+` | Simple String | `+PONG\r\n` |
| `-` | Error | `-ERR unknown command\r\n` |
| `:` | Integer | `:42\r\n` |
| `$` | Bulk String | `$4\r\nPING\r\n` |
| `*` | Array | `*1\r\n$4\r\nPING\r\n` |

We hardcode `+PONG\r\n` now; real parsing comes later.
