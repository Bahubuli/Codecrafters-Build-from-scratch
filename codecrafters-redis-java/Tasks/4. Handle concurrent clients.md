# Stage 4: Handle Concurrent Clients

---

## What You Have to Do

The tester opens **two connections at the same time** and sends `PING` on each. It expects **two** separate `+PONG\r\n` responses. You may still ignore the payload and hardcode the reply — this stage is purely about serving more than one client at once.

---

## Thought Process

**The gap after stage 3:** the server `accept()`s **once**, then enters a `while` loop that **blocks on `read()`**, serving that one client until it disconnects. While the thread is parked inside `read()` for client A, it is doing nothing else — it cannot loop back to `accept()`, so client B never gets in.

**The contradiction that defines the stage:** to serve A and B at once you need **two `read()` calls blocked simultaneously** — one waiting on A, one on B. But a single thread is a single point of execution; it can only be blocked in one place. One thread, two simultaneous waits — impossible.

**The fix that falls out:** stop making one thread do everything. Give each connection its own thread, so each can block on its own `read()` independently. The main thread is freed to do nothing but `accept()`.

---

## The Solution

```java
import java.io.IOException;
import java.io.InputStream;
import java.io.OutputStream;
import java.net.ServerSocket;
import java.net.Socket;
import java.nio.charset.StandardCharsets;

public class Main {
  public static void main(String[] args) {

    ServerSocket serverSocket = null;
    int port = 6379;

    try {
      serverSocket = new ServerSocket(port);
      serverSocket.setReuseAddress(true);

      while (true) {
        // main thread does ONLY this — accept, hand off, loop back immediately
        Socket clientSocket = serverSocket.accept();

        new Thread(() -> {
          try {
            OutputStream out = clientSocket.getOutputStream();
            InputStream in = clientSocket.getInputStream();
            byte[] buffer = new byte[1024];

            while (true) {
              int bytesRead = in.read(buffer);
              if (bytesRead == -1) break;

              out.write("+PONG\r\n".getBytes(StandardCharsets.UTF_8));
              out.flush();
            }
          } catch (IOException e) {
            System.out.println("IOException: " + e.getMessage());
          }
        }).start();
      }

    } catch (IOException e) {
      System.out.println("IOException: " + e.getMessage());
    }
  }
}
```

## New Concepts in This Stage

**[CONCEPT] A thread is an independent point of execution**  
A thread has its own *cursor through the code* and its own *call stack*. Your program starts with one (the main thread). When you spawn a second and hand it a block of code, you have **two cursors moving at once**, interleaved by the OS scheduler. The payoff: when one thread parks on `read()`, **only that thread parks** — the others keep running on their own `read()`s. That's what dissolves the one-thread contradiction. One thread can't be blocked in two places; N threads can each be blocked in one.

**[CONCEPT] Separation of roles: acceptor vs worker**  
The main thread's *only* job becomes accepting connections — it must never block on a client itself, or it stops accepting. Each accepted socket is handed to a **worker thread** that owns that one conversation end-to-end (its streams, its serve loop). Main accepts and immediately loops back; workers do the talking.

**[CONCEPT] Variable capture must be per-connection**  
`clientSocket` is declared **inside** the `while` loop on purpose. Each iteration creates a fresh variable, so each lambda captures *its own* socket. If you hoisted it above the loop and reused one variable, the next `accept()` would overwrite it and threads would race on the same reference — cross-talk between clients. (Java enforces a hint of this: a lambda may only capture an *effectively final* variable, which the loop-local one is.)

**[SYNTAX] The Java mechanics — lookup, don't memorize**  
- `new Thread(Runnable)` — a `Runnable` is "a block of code to run"; the `() -> { … }` lambda is that block.
- `.start()` — runs the block on a **new** thread. `.run()` would run it on the **current** thread — a classic trap that silently kills your concurrency.
- A lambda captures only **effectively final** local variables — declare the socket inside the loop to satisfy this and to give each worker its own.

---

## Failure Modes

- **Calling `.run()` instead of `.start()`** — no new thread is created; the serve loop runs on the main thread, which then blocks on the first client. Back to the Stage 3 problem, silently.
- **Socket variable declared outside the loop** — every worker captures the same reference; a new `accept()` clobbers it. Won't even compile if declared once and reassigned (not effectively final); if worked around, it's a data race.
- **Worker socket never closed** — when `read()` returns `-1` we `break` and the lambda ends, leaking the socket until GC. Tidier: wrap the socket in try-with-resources so it closes on exit even if an exception fires. Doesn't fail this tester, but it's a leak under real load.
- **Unbounded thread creation** — one thread per connection means 10k clients = 10k threads. Passes here; is precisely the model real Redis rejected (see tradeoffs).

---

## Tradeoffs — thread-per-client vs the event loop

This stage has you build **thread-per-client**, and **real Redis deliberately did not**. Worth knowing why each wins:

| | Thread-per-client (what we built) | Single-threaded event loop (real Redis) |
|---|---|---|
| Model | One blocking thread per connection | One thread, non-blocking sockets, an OS readiness primitive (`epoll`/`kqueue`/`Selector`) multiplexing all of them |
| Mental cost | Simple — blocking code, linear to read | Harder — you invert control into "react when a socket is ready" |
| Scaling | Each thread costs memory (stack) + scheduler/context-switch overhead; thousands of mostly-idle connections waste a lot | One thread handles tens of thousands of connections cheaply |
| Shared state | Needs locking — multiple threads touching the same keyspace race | **No locks needed** — one thread owns all state, commands run one at a time |

That last row is the real reason. Redis is an in-memory store where most commands are tiny and fast; a single thread can rip through them, and by being single-threaded it gets **atomicity for free** — no locks, no races on the keyspace. Threads would buy parallelism it doesn't need while adding locking it doesn't want. We build threads here because it's the smaller leap from Stage 3 and needs no non-blocking machinery; the event loop is the senior choice for *this specific* workload.

---

## How It Flows

```
main thread:  accept() → got A → spawn worker-A → loop
              accept() → got B → spawn worker-B → loop  (never blocks on a client)

worker-A:     read A → write PONG → … → read == -1 → break, thread ends
worker-B:     read B → write PONG → … → read == -1 → break, thread ends
              (A and B run at the same time, each blocked only on its own read)
```
