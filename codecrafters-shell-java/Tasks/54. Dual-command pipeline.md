# Stage 54: Dual-command pipeline

## In one line
Connect standard output of an upstream command directly to standard input of a downstream command using Unix anonymous pipes (`|`).

## The problem it solved
Previously, commands executed strictly in isolation or redirected I/O to disk files. Processes could not stream data directly from one to another in real time without creating intermediate files. This stage adds support for the pipeline control operator (`|`), allowing concurrent execution where the upstream process streams its standard output directly into the downstream process's standard input via kernel pipes.

## Concepts (the transferable part)
- **Anonymous Pipe (`pipe(2)`)** — A unidirectional byte stream maintained in kernel memory with a read descriptor (`fd[0]`) and write descriptor (`fd[1]`). The producer writes to `fd[1]` and the consumer reads from `fd[0]`. The kernel buffers data up to pipe capacity (e.g. 64KB on Linux) and suspends the writer if full, or suspends the reader if empty.
- **Pipeline Wiring & File Descriptor Duplication** — For `cmd1 | cmd2`, the shell creates a pipe, forks both children:
  - Child 1: stdout redirected to pipe write end (`dup2(pipefd[1], STDOUT_FILENO)`).
  - Child 2: stdin redirected to pipe read end (`dup2(pipefd[0], STDIN_FILENO)`).
  - Shell: Closes both pipe ends in the parent process so that only the children hold open handles.
- **Downstream Early Termination & SIGPIPE** — When `head -n 5` finishes reading 5 lines, it exits. The kernel closes `head`'s read end. If `tail -f` attempts to write to the pipe, the kernel sends `SIGPIPE` causing `tail` to terminate. However, if `tail` is idle waiting for file changes, no write occurs; the shell must actively terminate any lingering upstream processes after the downstream consumer completes.

## What breaks it (failure modes)
- **Sequential Waiting Deadlock** — If the shell executes `processes.get(0).waitFor()` before `processes.get(1).waitFor()`, a pipeline like `tail -f file | head -n 5` deadlocks forever. `tail -f` never exits on its own while waiting for new input. The shell must wait for the consumer (`last.waitFor()`) first, and clean up active producers.
- **Leaked Write End in Parent Process** — If the parent shell holds an open handle to the write end of the pipe, `cmd2` will never read EOF when `cmd1` exits, hanging `cmd2`. `ProcessBuilder.startPipeline` handles OS-level descriptor closing in the parent process automatically.
- **Pipes Inside Quoted Strings** — An expression like `echo "hello | world"` must treat `|` as a string literal, not a pipeline delimiter. The parser must distinguish between quoted, escaped, and unquoted metacharacters.

## Tradeoffs
- **`ProcessBuilder.startPipeline` vs Java-Thread Stream Copying** — `startPipeline` creates OS pipes directly in kernel space with zero Java heap allocations, zero user-space copying overhead, and native backpressure. Threaded byte copying (`stream.transferTo()`) incurs context-switching latency, requires thread pool management, and poorly simulates OS pipe semantics.
- **Waiting on Last Process vs Sequential Waiting** — In POSIX shells, a pipeline's exit status is dictated by the last command. Waiting on `last` first ensures that pipelines with finite consumers (`head`, `read`) unblock the shell prompt immediately upon consumer termination.

## CLI / Protocol format
```bash
# Basic pipeline between two external commands:
$ cat /tmp/foo/file | wc
       5      10      78

# Streaming pipeline with real-time producer and early consumer exit:
$ tail -f /tmp/foo/file-1 | head -n 5
1. blueberry apple
2. pear banana
3. mango grape
# (tester appends lines 4 and 5)
4. grape apple
5. banana pear
$ 
```

## Java specifics — lookup, don't memorize
- `ProcessBuilder.startPipeline(List<ProcessBuilder> builders)` — Starts a pipeline of processes connected by OS pipes. All intermediate inputs and outputs must remain `Redirect.PIPE`.
- `process.isAlive()` — Tests whether the subprocess represented by this `Process` is still running.
- `process.destroy()` — Sends a termination signal (`SIGTERM` on POSIX) to politely terminate the process.
- `process.waitFor()` — Causes the current thread to wait until the subprocess has exited.
