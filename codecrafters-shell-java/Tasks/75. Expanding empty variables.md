# Stage 75: Expanding empty variables

## In one line
Expand unset or empty shell variables to an empty string during parameter expansion, retaining surrounding literal text while dropping standalone unquoted empty tokens.

## Self-test (cover the answers below and answer these first)
- What does `${UNSET}` expand to when surrounded by text like `${UNSET}suffix`?
- What does `${UNSET}` expand to when completely standalone and unquoted?
- What does `"${UNSET}"` expand to when enclosed in double quotes?
- Why does unquoted `${UNSET}` not introduce an empty string element into the argument vector?

## The problem it solved
In shell execution, variables referenced before assignment or without values evaluate to empty strings rather than raising errors or stopping execution. If an unset variable is part of a word (e.g. `${missing}end`), the non-empty surrounding characters must form the resulting token (`end`). If an unset variable stands alone without quotes (e.g. `${missing}`), standard word splitting drops the empty word entirely, preventing empty strings from polluting the argument vector.

## Concepts (the transferable part)
- **Empty Expansion Semantics** — Unset variables evaluate to empty strings `""` instead of throwing undefined variable exceptions.
- **Word Token Omission** — In the lexical phase, unquoted words that expand strictly to empty content without any surrounding literal characters or quotes do not trigger token creation (`hasToken` remains false).
- **Compound Word Concatenation** — Any literal characters adjacent to the empty expansion seamlessly coalesce into the final word without spaces or delimiters.

## What breaks it (failure modes)
- Emitting empty argument strings for unquoted unset variables — Passing `""` as an argument when `${missing}` is passed alone violates POSIX shell word-splitting rules.
- Dropping adjacent literal characters — Accidental reset of the token buffer when an unset variable is encountered mid-word would lose leading or trailing characters (e.g., losing `end` in `${missing}end`).
- Treating unset as literal string `"${missing}"` — Failing to resolve an undefined variable must not fall back to printing the variable syntax literally.

## Tradeoffs
- Lexical omission via `hasToken` flag vs post-processing filter — Tracking token presence with a boolean flag (`hasToken = true` only when characters are actually added or quotes were opened) handles unset variable omission cleanly in a single pass without needing a secondary array filtering step.

## CLI / Protocol format

## Java specifics — lookup, don't memorize
- Safe resolution and token omission logic in `parseArguments`:
  ```java
  String val = SHELL_VARIABLES.containsKey(varName) ? SHELL_VARIABLES.get(varName) : System.getenv(varName);
  if (val != null && !val.isEmpty()) {
      current.append(val);
      hasToken = true;
  }
  // When val is null or empty, current is untouched and hasToken remains false
  // Unless surrounding characters or quotes set hasToken to true
  ```

## Rebuild checklist
1. When `${VAR}` or `$VAR` is expanded, resolve via `SHELL_VARIABLES` with fallback to `System.getenv`.
2. If the value is null or empty:
   - In unquoted context: do not append anything to `current` and do not set `hasToken = true`.
   - In double-quoted context: `hasToken` is already true (because double quotes open a token), so an empty string argument `""` is preserved if nothing else is in the quoted token.
3. Verify standalone unquoted `${missing}` produces zero arguments.
4. Verify compound `${missing}text` retains `text`.
