# Stage 1: Print a prompt

---

## In one line
Start an interactive shell loop by displaying a command prompt (`$ `) and waiting for standard input.

---

## Self-test (cover the answers below and answer these first)
- What is a shell prompt and why does it need to be printed without a newline?
- Why does the shell need to wait on `stdin` after displaying the prompt?
- What is standard I/O buffering, and why might an unbuffered flush matter in an interactive REPL?

---

## The problem it solved
Before this stage, there was no user-facing interface. The program did nothing and exited immediately. This stage establishes the initial visual contract of a command-line interface: displaying the prompt symbol `$ ` to signal readiness and pausing for user input.

---

## Concepts (the transferable part)

- **[CONCEPT] REPL (Read-Eval-Print Loop)** — The fundamental architecture of any interactive shell or interpreter. The cycle consists of:
  1. Print prompt & **Read** user input from `stdin`.
  2. **Eval** (parse commands, resolve paths, execute builtins or subprocesses).
  3. **Print** results to `stdout` / errors to `stderr`.
  4. **Loop** back to step 1 until an exit signal occurs.
- **[CONCEPT] Standard Streams (`stdin`, `stdout`, `stderr`)** — Inherited file descriptors (0, 1, 2) that connect the process to its terminal or pipeline. The prompt is printed to `stdout` (fd 1), while user keystrokes arrive via `stdin` (fd 0).
- **[CONCEPT] Line Buffering & Newlines** — `System.out.println()` appends a newline (`\n`), placing the cursor on the next line. A shell prompt must stay on the same line (`System.out.print("$ ")`) so the user types adjacent to the symbol.

---

## The Solution

```java
import java.util.Scanner;

public class Main {
    public static void main(String[] args) throws Exception {
        System.out.print("$ ");

        // Wait for user input
        Scanner scanner = new Scanner(System.in);
        String input = scanner.nextLine();
    }
}
```

---

## What breaks it (failure modes)

- **Printing a newline (`println`) instead of inline (`print`)** — Puts the user's cursor on the following line rather than next to `$ `, violating terminal prompt convention and failing automated testers.
- **Exiting before reading input** — If the program prints `$ ` and immediately terminates, EOF is sent to the terminal/tester before commands can be entered.
- **Flushing issues** — In certain buffered streams, output without a trailing newline is held in memory until the buffer fills or is explicitly flushed. In Java, `System.out` is typically auto-flushed, but explicit flushing (`System.out.flush()`) prevents hung prompts across diverse runtime environments.

---

## Tradeoffs

- `Scanner(System.in)` vs `BufferedReader(new InputStreamReader(System.in))` — `Scanner` is concise and sufficient for early stages; `BufferedReader` gives lower-level control and slightly better performance for large stream processing.

---

## CLI / Protocol format

- **Prompt**: `$ ` (dollar sign followed by a single space)
- **Input**: UTF-8 text ending with newline (`\n` or `\r\n`)

---

## Java specifics — lookup, don't memorize

- `System.out.print("$ ")` — Writes characters to standard output without trailing newline.
- `new Scanner(System.in)` — Wraps standard input stream with token and line parsing capabilities.
- `scanner.nextLine()` — Blocks until a full line of text is read from `System.in`.
