# Stage 53: Recycle job numbers

## In one line
Recycle shell job IDs to 1 when the job table is empty, or assign one higher than the current maximum active job ID.

## Self-test (cover the answers below and answer these first)
- When a job table becomes completely empty and a new background job is launched, what ID should it receive?
- If jobs [1] and [3] are currently running (job [2] finished and was reaped), what ID does a newly launched background job receive under this stage's specification?
- Why do operating systems and shells recycle job identifiers instead of letting them monotonically increment indefinitely?

## The problem it solved
Previously, job numbers incremented monotonically (`AtomicInteger nextJobId`), meaning if jobs were continuously started and finished, job IDs would grow to arbitrary magnitudes (`[50]`, `[51]`, ...). This stage implements job number recycling: if the active job table is empty, start back at `1`; otherwise, assign `max(active_job_ids) + 1`.

## Concepts (the transferable part)
- **Identifier Recycling & Resource Compaction** — Unlike kernel PIDs which wrap around a large integer range (e.g. 32768 or 4194304) using a bitmap or PID allocator, shell job numbers are user-facing, compact, low-integer handles (`%1`, `%2`). Shells keep them small and predictable by recycling numbers once jobs terminate.
- **Dynamic ID Selection Policy** — When starting a background job:
  $$\text{jobId} = \begin{cases} 1 & \text{if } \text{table is empty} \\ \max_{j \in \text{table}}(j.\text{id}) + 1 & \text{otherwise} \end{cases}$$

## What breaks it (failure modes)
- **Reaping race / Stale job entries** — If finished jobs aren't reaped before calculating the new job ID, their terminated IDs will falsely inflate `maxJobId`.
- **Empty table edge condition** — If `backgroundJobs.isEmpty()`, the loop finding the maximum does not execute or defaults to 0, ensuring `0 + 1 = 1`.

## Tradeoffs
- **`max + 1` vs First Available Gap (Lowest Unused ID)** — POSIX and bash standardly assign the lowest unused positive integer (filling gaps). This stage explicitly specifies `max + 1` (or 1 if empty), which is simpler to compute ($O(N)$ scan or maintained max) and avoids re-using an ID that just terminated while older jobs remain.

## CLI / Protocol format
```bash
# Example 1: Reset to 1 when empty
$ sleep 1 &
[1] 84470
# After job 1 terminates and is reaped:
$ sleep 10 &
[1] 84490

# Example 2: Reusing number 2 when job 2 exits but job 1 remains
$ sleep 100 &
[1] 84470
$ sleep 1 &
[2] 84471
# After job 2 terminates and is reaped:
$ sleep 10 &
[2] 84490
```

## Java specifics — lookup, don't memorize
- `for (Job j : backgroundJobs) { if (j.id > maxId) maxId = j.id; }` — simple traversal to calculate maximum job ID across active background jobs.
