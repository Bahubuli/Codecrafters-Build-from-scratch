# Stage 55: Pipelines with built-ins

## In one line
Execute shell built-ins within pipeline streams using isolated threads and standard I/O redirection while preserving subshell semantics.

## Self-test (cover the answers below and answer these first)
- Why can't built-in commands like `echo`, `type`, or `exit` simply be passed into `ProcessBuilder.startPipeline()`?
- How do pipeline stages achieve subshell semantics in Java threads (e.g., preventing `exit` from killing the main shell and `cd` from mutating parent directory state)?
- Why must an upstream built-in stage explicitly close its output stream in a `finally` block when feeding an external downstream process like `wc`?

## The problem it solved
Previously, pipelines only supported external binaries via `ProcessBuilder.startPipeline()`. Attempting to pipeline commands containing built-ins (such as `ls | type exit` or `echo apple-orange | wc`) failed either with `IOException: Cannot run program "type"` or by erroneously falling back to external OS binaries (`/bin/echo`). This stage introduces a unified execution model handling built-in commands at any position in a pipeline.

## Concepts (the transferable part)
- **Subshell Pipeline Execution** — In POSIX shells, each stage in a pipeline runs in an isolated subshell environment. Changes to shell state (like changing working directory via `cd` or setting variables) do not persist to the parent interactive shell. In a multithreaded runtime like Java, subshells can be modeled as threads with scoped state and disabled parent process termination.
- **Inter-stage I/O Binding** — Connecting arbitrary producers and consumers requires bridging in-memory streams (`PipedInputStream`/`PipedOutputStream`) for internal stages and OS pipes (`Process.getInputStream()` / `Process.getOutputStream()`) when crossing process boundaries.
- **Pipe EOF Propagation** — A downstream consumer waiting on standard input will block indefinitely until the upstream producer finishes and closes its output channel. Explicitly flushing and closing upstream stream handles on thread completion delivers the EOF signal.

## What breaks it (failure modes)
- **Dangling Open Pipes & Consumer Hangs** — If an upstream built-in thread exits without closing `process.getOutputStream()`, downstream external utilities (e.g. `wc`, `grep`, `sort`) hang waiting for EOF. Solved by placing `finalOut.flush(); finalOut.close();` inside a `finally` block.
- **Parent Shell Exit on Pipeline Builtin** — If `type exit` or `exit` within a pipeline calls `System.exit()`, the entire shell process terminates. Solved by passing `inSubshell = true` to `executeBuiltin`, turning `exit` into a thread return rather than process exit.
- **State Mutation in Pipelines** — If `cd /tmp | wc` executed `currentDir = target`, it would violate POSIX subshell isolation. With `inSubshell = true`, directory validity is checked and errors are reported, but `currentDir` remains unchanged.
- **Infinite Upstream Producers** — In pipelines like `tail -f file | head -n 5`, the consumer exits while the producer remains running. The supervisor waits on the terminal stage first, and subsequently destroys any still-alive upstream processes.

## Tradeoffs
- **Threads with Piped Streams vs Separate Java JVM Subprocess** — Spawning a new JVM subprocess for built-ins provides 100% memory isolation but incurs extreme startup latency and memory overhead. Running built-ins on concurrent Java threads connected via piped streams is lightweight, near-instantaneous, and safe when subshell state updates are guarded.
- **Specialized external pipeline fallback vs Universal thread pump** — Retaining `ProcessBuilder.startPipeline` for purely external pipelines guarantees zero-copy native OS pipe streaming for high-throughput commands, while activating `executeMixedPipeline` only when built-ins are present.

## CLI / Protocol format
- Pipeline syntax: `<command1> [args...] | <command2> [args...] [| <commandN> ...]`
- Built-ins supported: `echo`, `exit`, `type`, `pwd`, `cd`, `complete`, `jobs`.
- Stdin / Stdout: Upstream stdout binds to downstream stdin; first stage inherits stdin; last stage inherits terminal stdout (unless redirected with `>` / `>>`).

## Java specifics — lookup, don't memorize
- `java.io.PipedOutputStream` & `java.io.PipedInputStream(pos, bufferSize)` — Inter-thread stream conduit connecting Java threads.
- `Process.getInputStream()` — The `InputStream` connected to the standard output of the subprocess.
- `Process.getOutputStream()` — The `OutputStream` connected to the standard input of the subprocess.
- `Thread.join()` — Blocks the calling thread until the worker thread finishes execution.
