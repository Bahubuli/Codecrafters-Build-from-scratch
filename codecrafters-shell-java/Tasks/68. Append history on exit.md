# Stage 68: Append history on exit

## In one line
Append only the unwritten commands executed during the current session to `HISTFILE` upon exit instead of rewriting the entire history file.

## Self-test (cover the answers below and answer these first)

- How does tracking `lastAppendedHistoryIndex` avoid duplicating commands already loaded at startup or saved by `history -a`?

## The problem it solved
In Stage 67, the shell persisted history on exit by truncating and rewriting `HISTFILE`. However, if the user or another shell session had preexisting commands in `HISTFILE`, truncating the file wiped out any commands that had not been loaded into memory. Furthermore, overwriting instead of appending destroys entries from concurrent shell sessions. Standard shells like Bash (with `histappend`) append session commands to `HISTFILE` on exit.

## Concepts (the transferable part)
- **Incremental State Persistence** — Maintaining an offset pointer (`lastAppendedHistoryIndex`) tracking the high-water mark of persisted records, ensuring only fresh delta entries are flushed to disk.
- **Append Semantics vs Truncate Semantics** — Using `StandardOpenOption.APPEND` to safely write records to the end of a persistent log without invalidating preexisting log entries.
- **Idempotent Flush Gate** — Checking `if (sb.length() > 0)` and advancing `lastAppendedHistoryIndex = commandHistory.size()` inside synchronization to ensure that multiple calls (e.g. `exit` builtin followed by JVM shutdown hook) only flush newly appended records once.

## What breaks it (failure modes)
- Duplicating startup history — If the exit routine appends all in-memory commands from index 0 instead of `lastAppendedHistoryIndex`, commands loaded from `HISTFILE` at startup are written to the file a second time.
- Double-flushing on exit — If the `exit` command writes commands but does not advance `lastAppendedHistoryIndex`, the JVM shutdown hook fires on process exit and writes the exact same commands again.
- Missing the `exit` command — The user's terminating command `exit` must be included in `commandHistory` before evaluating builtins, so it is present when the exit handler loops through the unwritten commands.

## Tradeoffs
- Append vs Truncate — Appending preserves preexisting lines and works well with multiple terminal sessions, but does not truncate files when history size exceeds max limits (unless combined with a separate compaction or `HISTFILESIZE` truncation mechanism).

## CLI / Protocol format
- Preexisting history file `/tmp/banana.txt`:
  ```txt
  echo initial_command_1
  echo initial_command_2
  ```
- Interactive Session:
  ```bash
  HISTFILE=/tmp/banana.txt ./your_program.sh
  $ echo new_command
  new_command
  $ exit
  ```
- Resulting `/tmp/banana.txt`:
  ```txt
  echo initial_command_1
  echo initial_command_2
  echo new_command
  exit

  ```

## Java specifics — lookup, don't memorize
- `Files.writeString(Path path, CharSequence csq, OpenOption... options)` — Passing `StandardOpenOption.CREATE`, `StandardOpenOption.APPEND`, `StandardOpenOption.WRITE` appends text to the end of the file or creates it if it does not yet exist.
- Loop slice from index to end:
  ```java
  for (int i = lastAppendedHistoryIndex; i < commandHistory.size(); i++) {
      sb.append(commandHistory.get(i)).append("\n");
  }
  lastAppendedHistoryIndex = commandHistory.size();
  ```
