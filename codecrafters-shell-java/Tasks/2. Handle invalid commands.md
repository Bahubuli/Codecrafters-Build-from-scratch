# Stage 2: Handle invalid commands

---

## In one line
Read a command string from standard input and report an error message when the command cannot be resolved.

---

## The problem it solved
In Stage 1, the shell printed the prompt and halted after reading input without giving any feedback to the user. A shell must communicate the outcome of evaluation; when a command cannot be found or executed, the shell must inform the user rather than failing silently or crashing. This stage implements basic error reporting for unrecognized commands (`{command}: command not found`).

---

## Concepts (the transferable part)

- **[CONCEPT] Command Evaluation & Resolution** — In any shell, once an input line is read, the shell attempts to resolve the first token (the command name) against shell keywords, aliases, built-in commands, and finally executable files on the filesystem search path (`PATH`). If all resolution attempts fail, the shell emits an error.
- **[CONCEPT] Error Reporting Contract** — Shells follow standard diagnostic formats: `<command>: command not found` (or `<shell>: <command>: command not found`). Unrecognized commands should produce human-readable diagnostics and non-zero exit statuses in scripts.
- **[CONCEPT] Read vs Eval Separation** — Reading bytes/text from `stdin` is separated from evaluating the command line. Even before full tokenization or argument parsing is introduced, capturing the input line provides the foundation for command resolution.

---

## The Solution

```java
import java.util.Scanner;

public class Main {
    public static void main(String[] args) throws Exception {
        System.out.print("$ ");

        Scanner scanner = new Scanner(System.in);
        String input = scanner.nextLine();
        System.out.println(input + ": command not found");
    }
}
```

---

## What breaks it (failure modes)

- **Missing trailing space or formatting mismatch** — Printing `command not found` without the exact `{command}: command not found` format fails the automated test expectations.
- **Using `print` instead of `println` for the error** — Unlike the prompt (`$ `), command outputs and error messages must terminate with a newline so subsequent output or prompts begin on a clean line.
- **Unhandled empty or whitespace lines** — In a complete shell, pressing Enter on an empty line should simply redisplay the prompt without reporting `: command not found`. For this stage, all inputs are evaluated as invalid command strings.
- **NoSuchElementException on EOF** — Calling `scanner.nextLine()` when `stdin` is closed (EOF) throws `NoSuchElementException` unless guarded by `scanner.hasNextLine()`.

---

## Tradeoffs

- Direct line output (`input + ": command not found"`) vs Tokenized parsing (`input.split(" ")`) — Direct string interpolation suffices for this stage since arguments and builtins have not yet been introduced; tokenized parsing will be required once command arguments and PATH lookups are added.
- `System.out` vs `System.err` — In standard POSIX shells, command-not-found diagnostics go to standard error (`stderr`, fd 2). In early testing stages of this challenge, tests intercept standard output (`stdout`), so standard output is used.

---

## CLI / Protocol format

- **Prompt**: `$ `
- **User input**: UTF-8 string followed by Enter (e.g. `xyz`)
- **Error message output**: `{command}: command not found\n` (e.g. `xyz: command not found\n`)

---

## Java specifics — lookup, don't memorize

- `scanner.nextLine()` — Reads and returns the remainder of the current line from standard input, consuming the trailing line separator.
- `System.out.println(...)` — Prints the given string followed by a platform-appropriate newline separator to standard output.
- String concatenation (`+`) — Conveniently concatenates string literals and variables.
