# Stage 6: Implement the type builtin

---

## In one line
Implement the `type` builtin utility to inspect command names and report whether they are recognized shell builtins or unrecognized commands.

---

- Why is the unrecognized output for `type <target>` formatted as `<target>: not found` rather than `<target>: command not found`?

## The problem it solved
Users and shell scripts need command introspection to know how an identifier will be interpreted before executing it — whether as a built-in shell feature, an executable program on `$PATH`, an alias, or a function. In earlier stages, the shell could execute builtins (`exit`, `echo`) or reject commands, but had no way for the user to query command capabilities. Implementing `type` introduces command introspection and command classification.

---

## Concepts (the transferable part)

- **[CONCEPT] Command Introspection (`type`)** — Shells evaluate commands through a resolution order (typically: aliases -> special builtins -> functions -> regular builtins -> `$PATH` executables). The `type` utility provides visibility into this internal resolution mechanism by inspecting a target identifier without executing it.
- **[CONCEPT] Builtin Command Classification** — Builtin commands are routines linked directly into the shell process itself rather than external executable binaries residing on the filesystem. Checking against an in-memory set of recognized names enables instant lookup without incurring filesystem traversal or process creation overhead.
- **[CONCEPT] Distinct Error Messages for Invocation vs Introspection** — When attempting to execute a nonexistent command, standard shells report `<command>: command not found`. When introspecting an unknown command with `type`, POSIX shells report `<command>: not found`. Differentiating these messages matches POSIX command output specifications.

## The Solution

```java
import java.util.Arrays;
import java.util.Scanner;
import java.util.Set;

public class Main {
    private static final Set<String> BUILTINS = Set.of("echo", "exit", "type");

    public static void main(String[] args) throws Exception {
        Scanner scanner = new Scanner(System.in);

        while (true) {
            System.out.print("$ ");
            if (!scanner.hasNextLine()) {
                break;
            }
            String input = scanner.nextLine();
            String trimmed = input.trim();
            if (trimmed.isEmpty()) {
                continue;
            }
            String[] parts = trimmed.split("\\s+");
            String command = parts[0];

            if (command.equals("exit")) {
                int exitCode = 0;
                if (parts.length > 1) {
                    try {
                        exitCode = Integer.parseInt(parts[1]);
                    } catch (NumberFormatException ignored) {
                    }
                }
                System.exit(exitCode);
            } else if (command.equals("echo")) {
                String output = String.join(" ", Arrays.copyOfRange(parts, 1, parts.length));
                System.out.println(output);
            } else if (command.equals("type")) {
                if (parts.length > 1) {
                    String target = parts[1];
                    if (BUILTINS.contains(target)) {
                        System.out.println(target + " is a shell builtin");
                    } else {
                        System.out.println(target + ": not found");
                    }
                }
            } else {
                System.out.println(input + ": command not found");
            }
        }
    }
}
```

## What breaks it (failure modes)

- **Missing `type` in the BUILTINS set** — Because `type` is itself a shell builtin, forgetting to register `"type"` in `BUILTINS` causes `$ type type` to report `type: not found` instead of `type is a shell builtin`.
- **ArrayIndexOutOfBoundsException on missing argument** — If the user types `type` with no arguments, referencing `parts[1]` without checking `parts.length > 1` throws an exception and crashes the shell.
- **Wrong error message format** — Outputting `<target>: command not found` instead of `<target>: not found` fails test assertions because POSIX `type` uses `: not found`.
- **Case sensitivity hazards** — Shell builtins in standard Unix environments are strictly lowercase (e.g. `echo`, not `ECHO` or `Echo`). Lookups should respect exact string matches unless case-folding is explicitly specified.

---

## Tradeoffs

- `Set.of(...)` vs `switch` statement / `List.contains(...)` — An immutable `Set<String>` provides clean $O(1)$ constant-time membership lookups and single-source-of-truth definition for builtins, avoiding duplicative checks as more builtins are added.
- Dedicated command table vs inline `if/else` checks — For early stages with few builtins, an `if/else` ladder with a helper `Set` is simple and readable. In larger shells, a command dispatch table (e.g. `Map<String, BuiltinHandler>`) decouples dispatch from individual implementations.

---

## CLI / Protocol format

- **Type Command Syntax**: `type <command>`
  - If `<command>` is a known builtin:
    ```
    <command> is a shell builtin
    ```
    Examples:
    - `$ type echo` -> `echo is a shell builtin`
    - `$ type exit` -> `exit is a shell builtin`
    - `$ type type` -> `type is a shell builtin`
  - If `<command>` is unrecognized:
    ```
    <command>: not found
    ```
    Example:
    - `$ type foo` -> `foo: not found`

## Java specifics — lookup, don't memorize

- `Set.of(E... elements)` — Static factory method (introduced in Java 9) that returns an unmodifiable set containing the given elements. Disallows null elements and duplicate keys.
- `Set.contains(Object o)` — Returns `true` if this set contains the specified element in average $O(1)$ time complexity.
