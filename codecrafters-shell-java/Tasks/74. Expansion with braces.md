# Stage 74: Expansion with braces

## In one line
Support parameter expansion using the `${VAR}` brace syntax to delimit variable names from adjoining literal text during command-line word tokenization.

## Self-test (cover the answers below and answer these first)
- Why is `${VAR}` syntax needed when `$VAR` already exists?
- How does the shell parser identify the end of a variable name in `${FOO}bar` vs `$FOObar`?
- What occurs when `${UNSET_VAR}` is expanded outside quotes vs inside double quotes?
- Are braces preserved in the output if the variable expands?

## The problem it solved
In simple expansion `$FOObar`, the tokenizer greedily matches `FOObar` as a single variable identifier, making it impossible to append literal suffix characters directly to a variable value without intervening whitespace. Braced parameter expansion `${FOO}bar` explicitly delimits the identifier boundary so `FOO` expands and `bar` remains intact as part of the same word token.

## Concepts (the transferable part)
- **Explicit Identifier Delimitation** — `${VAR}` uses paired enclosing delimiters `{` and `}` to clearly mark the beginning and end of a parameter reference, preventing lexical ambiguity with adjacent alphanumeric characters.
- **Compound Word Assembly** — Multiple expansions and literals within the same word (e.g. `prefix_${Var1}_and_${Var2}`) evaluate sequentially into a single concatenated argument token in the argument vector.
- **Whitespace and Boundary Preservation** — Token generation continues within the active word buffer `current` until boundary delimiters (like whitespace outside quotes) or command terminators are encountered.

## What breaks it (failure modes)
- Retaining `${` and `}` in the parsed argument — The curly braces are syntactic meta-delimiters and must be consumed during expansion.
- Misindexing past the closing brace — The parser index must skip to `closeIdx` so that the closing `}` is not evaluated as literal character data.
- Unclosed braces `${FOO` — If no closing `}` exists in the token, treating `$` as literal prevents runaway scanner crashes.

## Tradeoffs
- Parsing `${...}` alongside `$VAR` in tokenizer vs dedicated expansion AST pass — Scanning for `{` immediately after `$` in the lexical tokenizer avoids the overhead of multi-pass AST transformations while fully supporting both unquoted and double-quoted expansions.

## CLI / Protocol format
```bash
$ declare Item=widget
$ declare Foo1=Bar2
$ ./custom_exe_1234 stock_${Item}_id ${Foo1}
Program was passed 3 args (including program name).
Arg #0 (program name): custom_exe_1234
Arg #1: stock_widget_id
Arg #2: Bar2
```

## Java specifics — lookup, don't memorize
- Handling `${VAR}` syntax inside `parseArguments`:
  ```java
  } else if (c == '$') {
      if (i + 1 < input.length() && input.charAt(i + 1) == '{') {
          int closeIdx = input.indexOf('}', i + 2);
          if (closeIdx != -1) {
              String varName = input.substring(i + 2, closeIdx);
              String val = SHELL_VARIABLES.containsKey(varName) ? SHELL_VARIABLES.get(varName) : System.getenv(varName);
              if (val != null && !val.isEmpty()) {
                  current.append(val);
                  hasToken = true;
              }
              i = closeIdx;
          } else {
              current.append(c);
              hasToken = true;
          }
      } else {
          // simple $VAR identifier scan
      }
  }
  ```
