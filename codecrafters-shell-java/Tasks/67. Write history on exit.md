# Stage 67: Write history on exit

## In one line
Persist the full in-memory command history to the file specified by `HISTFILE` upon shell termination, whether via the `exit` builtin or EOF.

## Self-test (cover the answers below and answer these first)
- Does the `exit` command itself get written to the history file when the shell terminates?
- How is the destination file opened when saving history on exit: appended or truncated?
- What happens if the `HISTFILE` environment variable is unset, empty, or points to a file in a nonexistent folder?
- Why is it helpful to register a JVM shutdown hook in addition to invoking persistence before `System.exit()`?

## The problem it solved
Users expect command history from their current session to be preserved across shell invocations. While commands are collected in memory during the interactive REPL session, they would be lost upon exit unless serialized to persistent storage (`HISTFILE`). Standard shells commit their in-memory history to disk upon orderly exit.

## Concepts (the transferable part)
- **Orderly Shutdown Lifecycle** — Ensuring critical state transitions (e.g. flushing buffers, saving history, restoring terminal TTY settings) execute reliably prior to process termination.
- **Defense in Depth Termination Hooks** — Explicitly calling cleanup logic (`saveHistoryOnExit()`) on user-directed exit commands while also registering a JVM runtime shutdown hook (`Runtime.getRuntime().addShutdownHook(...)`) to catch EOF, SIGINT, or external termination.
- **Idempotent File Rewriting** — Using `StandardOpenOption.TRUNCATE_EXISTING` (or creating the file) to write the complete, updated history file from start to finish without leaving duplicate stale entries.

## What breaks it (failure modes)
- Omitting the `exit` command from history — Because `commandHistory.add(input)` must happen before builtin execution, `exit` is already present in `commandHistory` and gets saved to disk. Omitting it fails the CodeCrafters stage test.
- Appending instead of rewriting — If the history was loaded from `HISTFILE` on startup, appending the whole history on exit would duplicate every pre-existing command. Using `TRUNCATE_EXISTING` writes the current in-memory history cleanly.
- Unhandled parent directory creation — If `HISTFILE` specifies a path inside subdirectories that do not yet exist, failing to call `Files.createDirectories(p.getParent())` causes `NoSuchFileException`.
- Missing JVM raw mode restoration — If the shell terminates without resetting terminal settings, the user's terminal is left in raw/non-canonical mode without echo.

## Tradeoffs
- Full Overwrite vs Incremental Append on Exit — Rewriting the entire file on exit guarantees exact alignment with the session's in-memory view, but concurrent shell sessions running simultaneously will overwrite each other's changes. (Standard shells offer options like `histappend` for finer concurrency control).

## CLI / Protocol format
- Invocation: `HISTFILE=<path_to_history_file> ./your_program.sh`
- Interactive Session:
  ```bash
  $ echo hello
  hello
  $ echo world
  world
  $ exit
  ```
- Resulting `<path_to_history_file>` contents:
  ```txt
  echo hello
  echo world
  exit

  ```

## Java specifics — lookup, don't memorize
- `Files.writeString(Path path, CharSequence csq, OpenOption... options)` — Writes the formatted string to disk. Options `StandardOpenOption.CREATE`, `StandardOpenOption.TRUNCATE_EXISTING`, and `StandardOpenOption.WRITE` ensure the file is created if absent or replaced cleanly if present.
- `Runtime.getRuntime().addShutdownHook(Thread hook)` — Registers an asynchronous hook that executes when the JVM begins its shutdown sequence.
