# Stage 09: List for an unknown topic

## In one line
Parsing `DescribeTopicPartitions` (API key 75) v0 requests with Request Header v2 and emitting Response Header v1 with error code 3 (`UNKNOWN_TOPIC_OR_PARTITION`) for non-existent topics.

## Self-test (cover the answers below and answer these first)
- What distinguishes Response Header v1 from Response Header v0 in the Kafka wire protocol?
- How are string lengths encoded in `COMPACT_STRING` versus standard protocol `STRING`?
- What numeric error code represents `UNKNOWN_TOPIC_OR_PARTITION`, and what default topic ID is returned when a topic is absent?
- What does a `next_cursor` value of `-1` (`0xFF`) signify in paginated partition listings?

## The problem it solved
Clients querying topic metadata send `DescribeTopicPartitions` (API key 75) to discover partition leaders, replicas, and ISRs before reading or writing data. When a requested topic has not been created, the broker must respond with structured metadata indicating error code 3 (`UNKNOWN_TOPIC_OR_PARTITION`), an empty partitions list, and a null UUID rather than failing the connection.

## Concepts (the transferable part)
- **Response Header v1 Evolution** — Newer API response formats (like `DescribeTopicPartitions`) adopt Response Header v1, adding a `TAG_BUFFER` (1 byte, `0x00`) immediately following `correlation_id` (4 bytes).
- **Compact String Encoding** — Similar to compact arrays, `COMPACT_STRING` stores length as an unsigned varint where:
  - `0`: represents `null`
  - Values $\ge 1$: represent $\text{string\_byte\_length} + 1$, followed directly by UTF-8 bytes
- **Null Topic UUID & Empty Partitions** — When a topic does not exist on the broker, Kafka convention dictates:
  - `topic_id`: 16 bytes of zeros (`00000000-0000-0000-0000-000000000000`)
  - `is_internal`: `0` (`false`)
  - `partitions`: empty `COMPACT_ARRAY` (length 0, encoded as varint `1`)
  - `topic_authorized_operations`: `0x00000000`
  - `next_cursor`: `0xFF` (`-1`), signaling pagination end

## What breaks it (failure modes)
- **Header Version Mismatch** — Omitting the Response Header v1 `TAG_BUFFER` byte causes the client parser to read the first byte of `throttle_time_ms` as the header tag, corrupting the entire response body alignment.
- **Compact String Varint Bias** — Forgetting the $+1$ bias in `COMPACT_STRING` causes string length truncation or stream underflow.
- **Unread Tagged Fields in Request Header** — Request Header v2 includes tagged fields after `client_id`. Not parsing or skipping these tagged fields causes the request body parser to read header tags as the `topics` array length.

## Tradeoffs
- **Modular Dispatching vs Inline Processing** — Branching on `apiKey` in `handleClient` to dedicated handler methods (`handleApiVersions`, `handleDescribeTopicPartitions`) provides clean isolation as additional RPC handlers are added.

## CLI / Protocol format
- Request Header v2 + DescribeTopicPartitions Request v0:
  ```
  +------------------+------------------+-----------------------+-------------------+
  | message_size(4B) | api_key(2B, 75)  | api_version(2B, 0)    | correlation_id(4B)|
  | client_id_len(2B)| client_id bytes  | header_tags (U_VARINT)| topics (C_ARRAY)  |
  +------------------+------------------+-----------------------+-------------------+
  ```
- Response Header v1 + DescribeTopicPartitions Response v0:
  ```
  +--------------------------------+-------------------+
  | message_size (INT32)           | dynamic (47B)     |
  | correlation_id (INT32)         | <echoed ID>       |
  | header TAG_BUFFER (1B)         | 0x00              |
  | throttle_time_ms (INT32)       | 0                 |
  | topics (COMPACT_ARRAY)         | 2 (1 item + 1)    |
  |   error_code (INT16)           | 3 (UNKNOWN_TOPIC) |
  |   topic_name (COMPACT_STRING)  | "foo"             |
  |   topic_id (UUID 16B)          | 16 x 0x00         |
  |   is_internal (BOOLEAN 1B)     | 0x00              |
  |   partitions (COMPACT_ARRAY)   | 1 (0 items + 1)   |
  |   authorized_ops (INT32)       | 0x00000000        |
  |   topic TAG_BUFFER (1B)        | 0x00              |
  | next_cursor (INT8)             | 0xFF (-1)         |
  | response TAG_BUFFER (1B)       | 0x00              |
  +--------------------------------+-------------------+
  ```

## Java specifics — lookup, don't memorize
- `in.readFully(byte[] b)` — Blocks until all bytes of the array are completely read from the stream.
- `out.writeByte((byte) -1)` — Writes signed byte `-1` as `0xFF`.
- `new byte[16]` — Allocates 16 zero-initialized bytes for the null UUID.

## Rebuild checklist
- [ ] Parse `client_id` and header tagged fields.
- [ ] Read `topics` compact array and extract each `topic_name` compact string.
- [ ] Write Response Header v1: `correlation_id` + `0x00` (TAG_BUFFER).
- [ ] For each topic: write error code 3, topic name, 16 zero bytes, boolean false, empty partitions compact array (1), and tag buffer (0).
- [ ] Write `next_cursor` (-1) and body tag buffer (0).
- [ ] Calculate `responseMessageSize = 5 + body.length` and flush.
