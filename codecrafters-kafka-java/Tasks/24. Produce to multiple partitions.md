# Stage 24: Produce to multiple partitions

## In one line
Iterating over multi-partition arrays in a Produce request, independently persisting each partition's RecordBatch to its dedicated log directory, and assembling all partition responses.

## The problem it solved
High-throughput Kafka producers distribute records across multiple partitions of a topic to balance load. In a single Produce request, records for several partitions arrive together. The broker must unpack the partition array, route and persist each batch to the correct partition log directory (`<topic>-<partition>/00000000000000000000.log`), and respond with individual partition status blocks in the same order.

## Concepts (the transferable part)
- **Multi-Partition Batch Routing**:
  - The Produce request v11 `topic_data` contains a `COMPACT_ARRAY` of partitions:
    ```
    partitions (COMPACT_ARRAY):
      partition_index (INT32)
      records (COMPACT_RECORDS)
      TAG_BUFFER (0x00)
    ```
  - For each partition entry:
    - Validate existence in the cluster metadata (`__cluster_metadata-0`).
    - If valid, write `records` to disk at `<log-dir>/<topic-name>-<partition-index>/00000000000000000000.log`.
    - Emit response block: `error_code: 0`, `base_offset: 0`, `log_append_time_ms: -1`, `log_start_offset: 0`.
    - If unknown partition, emit `error_code: 3 (UNKNOWN_TOPIC_OR_PARTITION)` with offsets set to `-1`.
- **Partition Directory Isolation**:
  - Each partition maintains its own log segment file directory `<topic>-<partitionIndex>`. Writes to partition 0 do not interfere with partition 1 or 2.

## What breaks it (failure modes)
- **Shared File Descriptors**: Reusing a single partition log file across different partition indexes rather than creating distinct `<topic>-<index>` directories.
- **Wrong Partition Count in Response**: Mismatching the compact array length of `partition_responses` with the number of requested partitions.
- **Corrupted Record Offsets**: Returning a single base offset for all partitions instead of evaluating each partition independently.

## Tradeoffs
- **Per-Partition File Synchronization vs Aggregated Buffer Sync**: Writing each partition's batch independently simplifies isolation and error reporting per partition at the cost of multiple file open/flush operations per network request.

## CLI / Protocol format
- Produce Response Partition Block (v11):
  ```
  index: INT32 (partition index)
  error_code: INT16 (0 for success)
  base_offset: INT64 (0L)
  log_append_time_ms: INT64 (-1L)
  log_start_offset: INT64 (0L)
  record_errors: COMPACT_ARRAY (empty: 0x01)
  error_message: COMPACT_STRING (null: 0x00)
  TAG_BUFFER: 0x00
  ```

## Java specifics — lookup, don't memorize
- `File.mkdirs()`: Ensures parent partition directory `<logDir>/<topic>-<partition>` is created before creating the `.log` file.
- `FileOutputStream(File, true)`: Opens file in append mode so existing records aren't overwritten.
