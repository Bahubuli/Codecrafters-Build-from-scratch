# Stage 24: Produce to multiple partitions

## In one line
Persisting independent RecordBatches across multiple partitions of a topic within a single Produce Request v11.

## Self-test (cover the answers below and answer these first)
- How does the partition loop in a Produce request map to disk directories?
- Can a Produce request succeed for partition 0 while failing for an unknown partition 99?
- Does Kafka guarantee ordering across different partitions in the Produce response?
- How are partition logs isolated on the filesystem?

## The problem it solved
Producers often distribute high-throughput event streams across multiple partitions of a single topic using hash or round-robin partitioners. This stage verifies handling of multiple partition entries inside a single Produce request topic block, persisting each batch into its respective partition log directory (`<topic>-<partition>/00000000000000000000.log`) and returning partition responses.

## Concepts (the transferable part)
- **Multi-Partition Batching** — Kafka batching happens at the partition level: each partition entry carries its own isolated `RecordBatch`.
- **Partition Isolation** — Each partition has a separate directory and active segment file on disk. A write to partition 0 does not block or contend with a write to partition 1 at the storage layer.
- **Per-Partition Error Isolation** — Validation and offset tracking are calculated independently per partition. If partition 0 is valid and partition 1 does not exist, partition 0 receives `error_code: 0` while partition 1 receives `error_code: 3`.

## What breaks it (failure modes)
- **Writing to a Single Directory** — Hardcoding partition 0 or neglecting to interpolate `partitionIndex` into the file path.
- **Partition Count Array Discrepancy** — Generating an incorrect length for `partition_responses` compact array ($M + 1$).
- **Early Exit on Error** — Aborting the entire request when one partition fails validation instead of processing each partition independently.

## Tradeoffs
- **Sequential Disk Writes vs Parallel I/O** — For small batches, looping sequentially through partitions keeps code simple and deterministic without the thread synchronization overhead of concurrent disk writes.

## CLI / Protocol format
- Request `partition_data` compact array contains $M$ entries:
  ```
  partition_index: INT32
  records: COMPACT_RECORDS
  TAG_BUFFER: 0x00
  ```
- Response `partition_responses` compact array contains $M$ matching responses:
  ```
  index: INT32
  error_code: INT16
  base_offset: INT64
  log_append_time_ms: INT64
  log_start_offset: INT64
  record_errors: COMPACT_ARRAY
  error_message: COMPACT_NULLABLE_STRING
  TAG_BUFFER: 0x00
  ```

## Java specifics — lookup, don't memorize
- `new File(logDir, topicName + "-" + partitionIndex)` — Isolates each partition to its canonical directory.
- `writeUnsignedVarint(out, ptd.partitions.size() + 1)` — Encodes the compact array length prefix.
