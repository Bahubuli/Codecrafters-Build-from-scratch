# Stage 10: List for a single partition

## In one line
Parsing KRaft metadata log batches (`__cluster_metadata-0/00000000000000000000.log`) to resolve topic UUIDs, partition leadership, and replica lists for valid `DescribeTopicPartitions` responses.

## Self-test (cover the answers below and answer these first)
- Where does KRaft store cluster metadata, and what are the two primary metadata record types parsed in this stage?
- How are metadata records structured inside a Kafka RecordBatch v2?
- What are the fields and compact array formats required for each partition entry in `DescribeTopicPartitions` response?
- How does the broker distinguish between an unknown topic and an existing topic with partitions?

## The problem it solved
In Stage 09, the broker treated every topic as non-existent (error code 3). In production Kafka, topic creation and partition replica assignments are committed to the internal `__cluster_metadata` partition. To answer metadata queries for legitimate topics, the broker must parse these committed log segments, extract topic IDs and partition states, and return error code 0 alongside accurate partition topology.

## Concepts (the transferable part)
- **KRaft (Kafka Raft Metadata Mode)** — Replaces ZooKeeper by managing cluster state as an internal event log (`__cluster_metadata`). Controllers write state transitions (topic registration, leader election, configuration changes) as strongly-typed records into partition 0.
- **RecordBatch v2 Internal Anatomy** — Each batch has a fixed 49-byte header following `batchLength` containing base offset, leader epoch, CRC, attributes, producer identity, and record count. Records inside the batch use ZigZag-encoded varints for deltas and byte lengths.
- **KRPC Metadata Serialization (`MetadataRecordSerde`)** — Record values use an envelope:
  - `frameVersion`: Unsigned varint (1)
  - `apiKey`: Unsigned varint (2 for `TopicRecord`, 3 for `PartitionRecord`)
  - `version`: Unsigned varint (0)
  - Schema payload:
    - `TopicRecord`: `topicName` (compact string), `topicId` (16-byte UUID)
    - `PartitionRecord`: `partitionId` (INT32), `topicId` (UUID), `replicas` (compact array of INT32), `isr` (compact array of INT32), `leader` (INT32), `leaderEpoch` (INT32)
- **Partition Metadata Serialization** — For each partition of a valid topic:
  - `error_code`: `0` (INT16)
  - `partition_index`: partition ID (INT32)
  - `leader_id`: leader broker ID (INT32)
  - `leader_epoch`: leader epoch (INT32)
  - `replica_nodes`: compact array of broker IDs
  - `isr_nodes`: compact array of in-sync broker IDs
  - `eligible_leader_replicas`, `last_known_elr`, `offline_replicas`: empty compact arrays (length 0 $\to$ varint `1`)
  - `TAG_BUFFER`: `0x00`

## What breaks it (failure modes)
- **ZigZag Varint Decoding Flaw** — Kafka record batch lengths and deltas use signed ZigZag varints (`(n >>> 1) ^ -(n & 1)`). Reading them as raw unsigned varints leads to catastrophic length miscalculations on negative values (e.g. key length `-1` representing null keys).
- **Batch Length Boundary Overflow** — `batchLength` covers all bytes from `partitionLeaderEpoch` to the end of the batch. Reading directly from an unbuffered or unbounded stream without wrapping in `batchBytes` risks reading past the batch on corruption.
- **UUID Byte Equality** — Using Java's default `equals` or reference comparison on raw `byte[]` arrays checks memory references rather than byte equality. Wrapping in `ByteBuffer` or using `Arrays.equals()` is mandatory.

## Tradeoffs
- **On-Demand Log Scanning vs In-Memory Metadata Cache** — Scanning the metadata log on-demand per request ensures 100% up-to-date state with zero cache invalidation complexity, which is optimal for small metadata logs during tests. High-scale brokers maintain an in-memory replicated state machine updated by a continuous log follower thread.

## CLI / Protocol format
- Request: `DescribeTopicPartitions` (API key 75, v0) for topic `"foo"`.
- Metadata log scanned: `/tmp/kraft-combined-logs/__cluster_metadata-0/00000000000000000000.log`.
- Response:
  ```
  +-------------------------------------+--------------------+
  | message_size (INT32)                | dynamic (74B)      |
  | correlation_id (INT32)              | <echoed ID>        |
  | header TAG_BUFFER (1B)              | 0x00               |
  | throttle_time_ms (INT32)            | 0                  |
  | topics (COMPACT_ARRAY)              | 2 (1 item + 1)     |
  |   error_code (INT16)                | 0 (NO_ERROR)       |
  |   topic_name (COMPACT_STRING)       | "foo"              |
  |   topic_id (UUID 16B)               | <actual metadata>  |
  |   is_internal (BOOLEAN 1B)          | 0x00               |
  |   partitions (COMPACT_ARRAY)        | 2 (1 partition + 1)|
  |     partition error_code (INT16)    | 0                  |
  |     partition_index (INT32)         | 0                  |
  |     leader_id (INT32)               | 1                  |
  |     leader_epoch (INT32)            | 0                  |
  |     replica_nodes (COMPACT_ARRAY)   | [1]                |
  |     isr_nodes (COMPACT_ARRAY)       | [1]                |
  |     elr, last_elr, offline (C_ARRAY)| empty (1, 1, 1)    |
  |     partition TAG_BUFFER (1B)       | 0x00               |
  |   topic_authorized_operations (4B)  | 0x00000000         |
  |   topic TAG_BUFFER (1B)             | 0x00               |
  | next_cursor (INT8)                  | 0xFF (-1)          |
  | response TAG_BUFFER (1B)            | 0x00               |
  +-------------------------------------+--------------------+
  ```

## Java specifics — lookup, don't memorize
- `ByteBuffer.wrap(byte[] array)` — Provides indexed and relative buffer access for integers, shorts, longs, and byte slices.
- `(value >>> 1) ^ -(value & 1)` — Standard bitwise operation for decoding ZigZag-encoded signed 32-bit integers.
