# Stage 11: List for multiple partitions

## In one line
Aggregating and ascending-sorting multiple `PartitionRecord` entries for a single topic from the KRaft metadata log into the `partitions` compact array of `DescribeTopicPartitions`.

## Self-test (cover the answers below and answer these first)
- Why must partition entries in `DescribeTopicPartitions` responses be sorted in ascending order by partition ID?
- How does the compact array length prefix scale when serializing $N$ partitions?
- How are multiple partition records associated with the same topic in the KRaft metadata log?
- What happens if a broker hosts multiple partitions with distinct leader broker IDs?

## The problem it solved
In Stage 10, the broker responded to metadata queries for topics possessing a single partition (partition index 0). Production Kafka topics frequently have tens or hundreds of partitions distributed across the cluster. When a topic contains multiple partitions, the broker must collect every partition associated with the topic's UUID and serialize each distinct partition record in ascending index order.

## Concepts (the transferable part)
- **Topic-to-Partition One-to-Many Relational Model** — In KRaft logs, `TopicRecord` (API key 2) introduces the topic identity (`name` $\leftrightarrow$ `topicId`). Subsequent `PartitionRecord`s (API key 3) reference the parent topic via `topicId` and define each partition's ID, leader broker ID, replicas, and ISR set.
- **Deterministic Partition Ordering** — Kafka clients expect partition arrays in metadata responses to be ordered monotonically ($0, 1, 2, \dots$). Sorting via `topic.partitions.sort(Comparator.comparingInt(p -> p.partitionId))` guarantees deterministic ordering regardless of log append order.
- **Compact Array Scaling for Collections** — A topic with $N$ partitions serializes its partitions array with varint length $N + 1$. Each partition element serializes its own replica arrays and ISR arrays using the same compact array rules ($M + 1$).

## What breaks it (failure modes)
- **Unordered Partitions** — Emitting partitions in arbitrary hash or append order causes client partition index lookups to fail validation or map to incorrect brokers.
- **Incorrect Length Prefix on Partitions Array** — Writing fixed length `2` (single element) when two partitions exist causes the client parser to read the second partition's bytes as trailing metadata, triggering protocol parsing errors.
- **Lost Partitions during Multi-Batch Appends** — If partition records span multiple RecordBatches in `00000000000000000000.log`, stopping after the first batch drops subsequent partitions. Looping through all available batches is essential.

## Tradeoffs
- **In-Memory Sort vs Indexed Metadata Map** — Sorting the partition list on request takes $O(P \log P)$ where $P$ is typically small ($\le 100$), avoiding complex sorted collection overhead during log parsing.

## CLI / Protocol format
- Request: `DescribeTopicPartitions` for topic with 2 partitions (0 and 1).
- Response:
  ```
  +-------------------------------------+--------------------+
  | message_size (INT32)                | dynamic (101B)     |
  | correlation_id (INT32)              | <echoed ID>        |
  | header TAG_BUFFER (1B)              | 0x00               |
  | throttle_time_ms (INT32)            | 0                  |
  | topics (COMPACT_ARRAY)              | 2 (1 item + 1)     |
  |   error_code (INT16)                | 0 (NO_ERROR)       |
  |   topic_name (COMPACT_STRING)       | "foo"              |
  |   topic_id (UUID 16B)               | <actual UUID>      |
  |   is_internal (BOOLEAN 1B)          | 0x00               |
  |   partitions (COMPACT_ARRAY)        | 3 (2 items + 1)    |
  |     [0] partition_index (INT32)     | 0                  |
  |         leader_id (INT32)           | 1                  |
  |         replica_nodes (C_ARRAY)     | [1]                |
  |         isr_nodes (C_ARRAY)         | [1]                |
  |     [1] partition_index (INT32)     | 1                  |
  |         leader_id (INT32)           | 2                  |
  |         replica_nodes (C_ARRAY)     | [2]                |
  |         isr_nodes (C_ARRAY)         | [2]                |
  |   topic_authorized_operations (4B)  | 0x00000000         |
  |   topic TAG_BUFFER (1B)             | 0x00               |
  | next_cursor (INT8)                  | 0xFF (-1)          |
  | response TAG_BUFFER (1B)            | 0x00               |
  +-------------------------------------+--------------------+
  ```

## Java specifics — lookup, don't memorize
- `list.sort(Comparator.comparingInt(p -> p.partitionId))` — In-place sort using primitive integer comparator.
- `writeUnsignedVarint(bodyOut, topic.partitions.size() + 1)` — Encodes dynamic partition count into compact array header.
