# Stage 02: Send Correlation ID

## In one line
Emitting an 8-byte big-endian response containing a 4-byte message frame length prefix and a 4-byte response header v0 `correlation_id` (7).

## The problem it solved
In Stage 01, the broker simply accepted a connection and terminated. Clients sending a Kafka RPC received an abrupt connection close without a protocol response. This stage introduces the Kafka framing layer and response header v0, returning a valid binary frame with a 4-byte length prefix and a 4-byte `correlation_id`.

## Concepts (the transferable part)
- **Length-Prefixed Framing** — TCP provides an unstructured stream of bytes, not discrete packets. Application protocols must establish message boundaries. Kafka frames every request and response with a leading 32-bit signed integer (`message_size`) indicating the number of subsequent bytes in the header and body.
- **Request-Response Correlation** — High-performance distributed clients send multiple requests asynchronously over a single TCP connection without waiting for individual replies. The `correlation_id` (a 32-bit integer generated by the client) is echoed identically in the broker's response, allowing the client to match responses to pending request callbacks out-of-order.
- **Big-Endian Network Byte Order** — Big-endian stores the most significant byte at the lowest memory address ($0x00000007 \to [00, 00, 00, 07]$). Java's standard I/O streams (`DataOutputStream.writeInt`) natively write in network byte order.

## What breaks it (failure modes)
- **TCP Connection Reset by Peer (`ECONNRESET`)** — If the server writes to the socket or closes the connection while unread client bytes remain in the kernel TCP receive buffer, the OS sends an `RST` segment rather than a clean `FIN`, dropping the server's response. Reading the client request before responding prevents this.
- **Endianness Mismatch** — Writing little-endian integers results in byte reversal ($7 \to [07, 00, 00, 00]$), which the client interprets as $117,440,512$, failing protocol verification.
- **Partial Writes / Missing Flush** — Buffered network streams may hold small 8-byte frames in userspace memory. Forgetting `out.flush()` prevents the frame from being immediately transmitted over the wire.

## Tradeoffs
- **Fixed-Length Framing vs Delimiter Framing** — Fixed 4-byte length prefixes allow the receiver to allocate exact buffers with a single read, avoiding the per-byte scanning overhead and escaping issues of delimiter-based framing (e.g. `\r\n` in HTTP or RESP).

## CLI / Protocol format
- Request: Any incoming byte payload from client.
- Response Layout:
  ```
  +------------------+------------------+
  | message_size (4B)| correlation_id(4B)
  +------------------+------------------+
  | 00 00 00 00      | 00 00 00 07      |
  +------------------+------------------+
  ```
- Total bytes: 8 bytes.

## Java specifics — lookup, don't memorize
- `DataOutputStream.writeInt(int v)` — Writes a 32-bit integer in big-endian network byte order.
- `out.flush()` — Flushes the stream buffer to the underlying TCP socket.
- `in.read(byte[] b)` — Reads up to `b.length` bytes into the buffer from the TCP input stream.
