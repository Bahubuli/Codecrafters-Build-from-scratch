# Stage 05: Handle ApiVersions requests

## In one line
Serializing the complete Kafka `ApiVersions` response v4, featuring compact arrays encoded with unsigned varints (`length + 1`), supported API version ranges, throttle time, and tagged buffer fields.

## The problem it solved
In Stage 04, the broker only returned an error code for unsupported versions and had no mechanism to advertise supported APIs. In real Kafka clusters, clients initiate handshakes by issuing `ApiVersions` requests to discover supported features and wire schemas before sending functional RPCs. This stage implements the full ApiVersions response v4 schema.

## Concepts (the transferable part)
- **Compact Data Types (KIP-482)** — Traditional Kafka protocols used 32-bit integers for array lengths and 16-bit integers for strings. KIP-482 modernized the wire protocol with compact types using unsigned varints (LEB128):
  - 0 indicates `null`.
  - Values $\ge 1$ represent $\text{length} + 1$. Thus, a 1-element array has length 1, encoded as integer 2 (`0x02`).
- **Unsigned Varint Encoding (LEB128)** — Each byte stores 7 data bits. The most significant bit (MSB, bit 7) acts as a continuation flag: `1` means more bytes follow, `0` marks the final byte. Small numbers ($< 128$) fit in a single byte, saving wire bandwidth over high-volume RPCs.
- **Tagged Fields (`TAG_BUFFER`)** — Forward-compatible schema evolution mechanism. Instead of bumping protocol versions for every minor metadata addition, fields are appended as tagged key-value pairs. An empty tag buffer is represented as a single `0x00` byte (0 tagged fields).

## What breaks it (failure modes)
- **Varint Offset Confusion** — Forgetting the $+1$ offset in `COMPACT_ARRAY` (e.g. writing `1` instead of `2` for a single element) causes the client to decode an empty array or throw an EOF/underflow exception.
- **Missing Tagged Buffers** — ApiVersions v4 introduced flexible versions, requiring tagged buffers both on the inner array elements and on the top-level response body. Omitting the trailing `0x00` shifts all subsequent fields.
- **Breaking Error Code Branching** — When `errorCode != 0`, sending extraneous fields causes client decoding failures on unsupported version errors. The error response must only contain `error_code`.

## Tradeoffs
- **Compact Varints vs Fixed-Length Integers** — Compact varints reduce network serialization overhead for typical small collections and strings, at the cost of slight CPU overhead for bitwise shifting during encoding/decoding.

## CLI / Protocol format
- ApiVersions Response v4 Binary Layout:
  ```
  +--------------------------------+-------------------+
  | message_size (INT32)           | 19 (0x00000013)   |
  | correlation_id (INT32)         | <echoed ID>       |
  | error_code (INT16)             | 0 (NO_ERROR)      |
  | api_keys length (U_VARINT)     | 2 (1 item + 1)    |
  |   api_key (INT16)              | 18 (ApiVersions)  |
  |   min_version (INT16)          | 0                 |
  |   max_version (INT16)          | 4                 |
  |   TAG_BUFFER (1B)              | 0                 |
  | throttle_time_ms (INT32)       | 0                 |
  | TAG_BUFFER (1B)                | 0                 |
  +--------------------------------+-------------------+
  ```

## Java specifics — lookup, don't memorize
- `out.writeByte(int v)` — Writes a single 8-bit byte.
- `value >>>= 7` — Unsigned right bitwise shift by 7 bits, shifting in zeroes from the left.
- `(value & ~0x7F) != 0` — Checks whether bits beyond the lowest 7 bits remain set.
