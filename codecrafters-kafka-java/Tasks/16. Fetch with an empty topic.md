# Stage 16: Fetch with an empty topic

## In one line
Responding to Fetch (v16) queries for existing cluster topics that contain no messages by emitting partition `error_code = 0` (`NO_ERROR`) and an empty `records` compact byte array.

## Self-test (cover the answers below and answer these first)
- What partition error code is returned when a requested topic UUID exists in cluster metadata but has no records?
- How is an empty `records` field represented in `COMPACT_RECORDS`?
- What are the values of `high_watermark`, `last_stable_offset`, and `log_start_offset` for an empty partition?
- Does the broker return a topic-level error code or partition-level error code?

## The problem it solved
Consumers regularly poll topics before producers publish any messages or after all available records have already been consumed. The broker must recognize existing topic UUIDs from KRaft metadata and signal `NO_ERROR` (0) with zero record bytes rather than falsely reporting `UNKNOWN_TOPIC_ID` (100).

## Concepts (the transferable part)
- **Zero-Record Partition Response Framing** — When a topic UUID is found in `catalog.byId`, partition responses specify `error_code = 0`, 64-bit zero offsets for watermark / log start, and an empty `records` payload.
- **Compact Record Encodings** — The `records` field in Fetch v16 uses `COMPACT_RECORDS` (an unsigned varint length prefix $+ 1$, followed by raw record bytes). An empty batch is encoded as varint `1` (denoting 0 bytes).
- **Catalog UUID Resolution**:
  - Unregistered UUID $\rightarrow$ partition `error_code = 100`.
  - Registered UUID $\rightarrow$ partition `error_code = 0`, empty record batch.

## What breaks it (failure modes)
- **UUID Lookup Failures** — Incorrect endianness or failing to compare raw 16-byte UUID arrays via wrapped byte buffers causes existing topics to be mistakenly treated as unknown.
- **Negative Offset Numbers** — Offsets must be serialized as big-endian INT64 zeros (`writeLong(0L)`). Emitting INT32 zeros shifts following fields by 4 bytes per offset.
- **Malformed Aborted Transactions Array** — Setting `aborted_transactions` length to 0 instead of varint 1 (for 0 items) misaligns the record byte stream.

## Tradeoffs
- **Immediate Return vs Max Wait** — In this stage, without pending log appends or blocking listeners, returning zero records immediately satisfies the client polling contract.

## CLI / Protocol format
- Request: Fetch v16 for existing UUID `4c7a6e12-4217-4972-88f1-e408ec20077c` partition 0.
- Response partition block:
  ```
  +---------------------------------------+--------------------+
  | partition_index (INT32)               | 0                  |
  | error_code (INT16)                    | 0 (NO_ERROR)       |
  | high_watermark (INT64)                | 0                  |
  | last_stable_offset (INT64)            | 0                  |
  | log_start_offset (INT64)              | 0                  |
  | aborted_transactions (C_ARRAY)        | 1 (0 items)        |
  | preferred_read_replica (INT32)        | 0                  |
  | records (COMPACT_RECORDS)             | 1 (0 bytes)        |
  | TAG_BUFFER (1B)                       | 0x00               |
  +---------------------------------------+--------------------+
  ```

## Java specifics — lookup, don't memorize
- `bodyOut.writeShort((short) 0)` — Emits `NO_ERROR`.
- `writeUnsignedVarint(bodyOut, 1)` — Encodes empty compact array / compact records.
