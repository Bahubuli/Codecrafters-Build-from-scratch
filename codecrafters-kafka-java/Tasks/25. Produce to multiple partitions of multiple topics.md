# Stage 25: Produce to multiple partitions of multiple topics

## In one line
Processing composite Produce Request v11 payloads distributing RecordBatches across multiple topics and partitions to disk in a single network round-trip.

## Self-test (cover the answers below and answer these first)
- How are multiple topics structured inside Produce Request v11?
- How does the broker resolve metadata validation when some topics/partitions in the request are valid and others are invalid?
- Where does the broker store each topic partition's log segment?
- What constitutes the completion of the Kafka challenge?

## The problem it solved
Real-world Kafka publishers batch writes destined for disparate topics and partitions into consolidated network requests to amortize socket I/O overhead. This final stage implements full multi-topic, multi-partition Produce routing, writing each partition's RecordBatch into its dedicated disk segment and returning complete structured responses matching client correlation.

## Concepts (the transferable part)
- **Hierarchical Batch Multiplexing** — A single RPC request carries a two-level hierarchy (`topic_data` array -> `partition_data` array -> `records`). The response mirrors this hierarchy (`responses` array -> `partition_responses` array).
- **Heterogeneous Validation** — Each topic and partition is evaluated against cluster metadata independently. A missing topic receives `error_code: 3`, while existing topic partitions are committed to disk and acknowledged with `error_code: 0`.
- **End-to-End Kafka Broker Loop**:
  1. Parse request framing & correlation ID.
  2. Traverse topics and partition record batches.
  3. Validate against `__cluster_metadata` catalog.
  4. Write `RecordBatch` bytes to `<topic>-<partition>/00000000000000000000.log`.
  5. Assemble response with `Response Header v1`.

## What breaks it (failure modes)
- **Mixing Topic Scopes** — Associating partition responses with the wrong parent topic name.
- **Corrupting Compact Array Lengths** — Encoding wrong length indicators ($N + 1$, $M + 1$) at topic or partition boundaries.
- **Dropping Tagged Fields** — Neglecting to write trailing `TAG_BUFFER` (0x00) for each partition response, topic response, and overall response body.

## Tradeoffs
- **Batch Processing Ordering** — Preserving request topic/partition order in responses eases debugging and matches client expectations, even though Kafka permits arbitrary response order.

## CLI / Protocol format
- Produce Request Body (v11):
  ```
  transactional_id: COMPACT_NULLABLE_STRING
  acks: INT16
  timeout_ms: INT32
  topic_data: COMPACT_ARRAY [
    name: COMPACT_STRING
    partition_data: COMPACT_ARRAY [
      index: INT32
      records: COMPACT_RECORDS
      TAG_BUFFER: 0x00
    ]
    TAG_BUFFER: 0x00
  ]
  TAG_BUFFER: 0x00
  ```
- Produce Response Body (v11):
  ```
  responses: COMPACT_ARRAY [
    name: COMPACT_STRING
    partition_responses: COMPACT_ARRAY [
      index: INT32
      error_code: INT16
      base_offset: INT64
      log_append_time_ms: INT64
      log_start_offset: INT64
      record_errors: COMPACT_ARRAY (0)
      error_message: COMPACT_NULLABLE_STRING (null)
      TAG_BUFFER: 0x00
    ]
    TAG_BUFFER: 0x00
  ]
  throttle_time_ms: INT32
  TAG_BUFFER: 0x00
  ```

## Java specifics — lookup, don't memorize
- `Map<String, TopicInfo>` — $O(1)$ topic lookup by name from parsed cluster metadata.
- `Files.write` / `FileOutputStream` — Append-only segment file logging.
