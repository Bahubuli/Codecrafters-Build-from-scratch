# Stage 25: Produce to multiple partitions of multiple topics

## In one line
Processing nested topic and partition compact arrays in Produce v11 requests, routing each RecordBatch to its topic-partition log file, and returning multi-topic responses.

## Self-test (cover the answers below and answer these first)
- How does the Kafka Produce v11 wire protocol structure multiple topics in a single request?
- How are tagged fields handled between nested arrays in flexible protocol versions?
- Where are the log segment files written on disk for distinct topics and partitions?
- What are the base offset and log append time conventions in the Produce v11 response?

## The problem it solved
In distributed messaging workloads, a producer application publishes events destined for several different topics simultaneously in a single network batch. The broker must process this two-dimensional hierarchy (`topics -> partitions -> records`), validate each topic and partition against cluster metadata, persist each RecordBatch to the proper file system path (`<logDir>/<topic>-<partition>/00000000000000000000.log`), and construct a response preserving the multi-topic structure.

## Concepts (the transferable part)
- **Hierarchical Wire Protocol Unpacking**:
  - Request wire layout:
    ```
    transactional_id: COMPACT_STRING
    acks: INT16
    timeout_ms: INT32
    topic_data (COMPACT_ARRAY):
      name: COMPACT_STRING
      partition_data (COMPACT_ARRAY):
        index: INT32
        records: COMPACT_RECORDS
        TAG_BUFFER: 0x00
      TAG_BUFFER: 0x00
    TAG_BUFFER: 0x00
    ```
- **Independent Log Target Resolution**:
  - Each topic-partition pair identifies an isolated directory:
    `<logDir>/<topicName>-<partitionIndex>/`
  - The RecordBatch bytes are written directly to `00000000000000000000.log`.
- **Response Structure**:
  - `responses` (COMPACT_ARRAY):
    - `name`: COMPACT_STRING
    - `partition_responses` (COMPACT_ARRAY):
      - `index`: INT32
      - `error_code`: INT16 (0)
      - `base_offset`: INT64 (0L)
      - `log_append_time_ms`: INT64 (-1L)
      - `log_start_offset`: INT64 (0L)
      - `record_errors`: COMPACT_ARRAY (empty: 0x01)
      - `error_message`: COMPACT_STRING (null: 0x00)
      - `TAG_BUFFER`: 0x00
    - `TAG_BUFFER`: 0x00
  - `throttle_time_ms`: INT32 (0)
  - `TAG_BUFFER`: 0x00

## What breaks it (failure modes)
- **Missing Tagged Field Bytes**: Forgetting `TAG_BUFFER` (0x00) after each partition, each topic, or at the end of the response body, causing client deserialization failure.
- **Path Collision**: Concatenating topic and partition incorrectly when creating log directories.
- **Offset Desynchronization**: Altering base offset values between partitions or topics.

## Tradeoffs
- **Single-Threaded Sequential Writes vs Concurrency**: Sequential disk writes per topic-partition keep implementation simple and avoid concurrency locking bugs while meeting benchmark latency.

## CLI / Protocol format
- Multi-Topic Produce Response (v11):
  ```
  Message Size: INT32
  Correlation ID: INT32
  Response Header TAG_BUFFER: 0x00
  responses: COMPACT_ARRAY (num_topics + 1)
    [for each topic]:
      name: COMPACT_STRING
      partition_responses: COMPACT_ARRAY (num_partitions + 1)
        [for each partition]:
          index: INT32
          error_code: INT16
          base_offset: INT64
          log_append_time_ms: INT64
          log_start_offset: INT64
          record_errors: COMPACT_ARRAY
          error_message: COMPACT_STRING
          TAG_BUFFER: 0x00
      TAG_BUFFER: 0x00
  throttle_time_ms: INT32
  TAG_BUFFER: 0x00
  ```

## Java specifics — lookup, don't memorize
- `Files.write(Path, byte[], StandardOpenOption.CREATE, StandardOpenOption.APPEND)`: Atomic append to partition log.
