# Stage 14: Fetch with no topics

## In one line
Handling `Fetch` (API key 1, v16) requests with zero topics by responding with Response Header v1, `throttle_time_ms = 0`, `error_code = 0`, `session_id = 0`, and an empty `responses` compact array.

## Self-test (cover the answers below and answer these first)
- Which response header version does `Fetch` v16 use?
- What is the difference between Response Header v0 and Response Header v1?
- What are the top-level fields of a Fetch Response (v16)?
- How is an empty `responses` array represented in compact array format?

## The problem it solved
Clients polling a Kafka broker often initiate a session or check for updates without subscribing to active topics yet, or during rebalances where no partitions are currently assigned. The broker must recognize API key 1 at version 16, drain any input fields, and reply with an empty responses array without crashing or closing the TCP connection.

## Concepts (the transferable part)
- **Response Header v1 vs v0** — Older RPCs (`ApiVersions` v4) use Header v0 (`correlation_id` INT32). Modern Kafka RPCs (`DescribeTopicPartitions` v0, `Fetch` v16) use Header v1, adding a trailing `TAG_BUFFER` (`0x00`) to the header frame before the response body begins.
- **Fetch Response v16 Structure**:
  - `throttle_time_ms`: INT32 (`0`)
  - `error_code`: INT16 (`0`, NO_ERROR)
  - `session_id`: INT32 (`0`)
  - `responses`: COMPACT_ARRAY (encoded length $0 + 1 = 1$, followed by 0 elements)
  - `TAG_BUFFER`: 1 byte (`0x00`)
- **Draining Request Fields** — A full Fetch v16 request includes `max_wait_ms`, `min_bytes`, `max_bytes`, `isolation_level`, `session_id`, `session_epoch`, `topics`, `forgotten_topics_data`, `rack_id`, and tagged fields. Reading them cleanly keeps the input stream aligned for persistent connections.

## What breaks it (failure modes)
- **Header v0 / v1 Mismatch** — Omitting the 1-byte tagged buffer in Response Header v1 shifts the response body by 1 byte, causing clients to misinterpret `throttle_time_ms`.
- **Missing Top-Level `error_code`** — Fetch responses in v16 include an outer `error_code` (INT16) right after `throttle_time_ms`. Omitting it causes `session_id` to be read as the error code.
- **Unconsumed Request Bytes** — If the client sends sequential requests on the same connection, failing to drain the entire request payload corrupts subsequent request framing.

## Tradeoffs
- **Immediate Response vs Long-Polling Suspension** — When `topics` is empty, there are no partitions to wait on, so the broker immediately returns with `error_code = 0` regardless of `max_wait_ms`.

## CLI / Protocol format
- Request: `Fetch` (API key 1, version 16) with 0 topics.
- Response:
  ```
  +------------------------------------+--------------------+
  | message_size (INT32)               | dynamic            |
  | correlation_id (INT32)             | <echoed ID>        |
  | header TAG_BUFFER (1B)             | 0x00               |
  | throttle_time_ms (INT32)           | 0                  |
  | error_code (INT16)                 | 0 (NO_ERROR)       |
  | session_id (INT32)                 | 0                  |
  | responses (COMPACT_ARRAY)          | 1 (0 items + 1)    |
  | response TAG_BUFFER (1B)           | 0x00               |
  +------------------------------------+--------------------+
  ```

## Java specifics — lookup, don't memorize
- `writeUnsignedVarint(bodyOut, 1)` — Encodes empty compact array.
- `out.writeByte(0)` — Emits empty tagged field buffer for Response Header v1.
