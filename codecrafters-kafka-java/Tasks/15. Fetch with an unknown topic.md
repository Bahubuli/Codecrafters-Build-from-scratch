# Stage 15: Fetch with an unknown topic

## In one line
Parsing 16-byte topic UUIDs and partition indices from Fetch Request (v16), matching them against the KRaft metadata catalog, and returning partition error code 100 (`UNKNOWN_TOPIC_ID`) for unregistered topic IDs.

## Self-test (cover the answers below and answer these first)
- What error code signifies an unknown topic UUID in Fetch responses?
- Does `UNKNOWN_TOPIC_ID` apply at the top response level or at the partition level?
- What are the required fields inside each partition block of a Fetch Response (v16)?
- How is an empty `records` field serialized in `COMPACT_RECORDS` format?

## The problem it solved
Modern Kafka clients query data by topic UUID rather than topic name to prevent race conditions during topic recreations. When a client requests partitions for a topic UUID that is absent from the cluster metadata, the broker must echo the requested topic UUID and respond with error code 100 (`UNKNOWN_TOPIC_ID`) on each requested partition while keeping the response-level error code 0 (`NO_ERROR`).

## Concepts (the transferable part)
- **Topic Identification by UUID** — In Fetch v13+, topics are addressed by 16 raw bytes (UUID) instead of strings. Brokers look up the UUID in their in-memory catalog (`Map<ByteBuffer, TopicInfo>`).
- **Granular Partition-Level Failure** — Top-level `error_code` in Fetch v16 conveys broker or session-level errors (e.g. invalid session ID). Per-partition issues like missing topics or unauthorized access are reported individually inside each partition's `error_code`.
- **Partition Response Block (v16)**:
  - `partition_index`: INT32
  - `error_code`: INT16 (`100` for `UNKNOWN_TOPIC_ID`)
  - `high_watermark`: INT64 (`0`)
  - `last_stable_offset`: INT64 (`0`)
  - `log_start_offset`: INT64 (`0`)
  - `aborted_transactions`: COMPACT_ARRAY (`1` for empty)
  - `preferred_read_replica`: INT32 (`0`)
  - `records`: COMPACT_RECORDS (varint length + 1; `1` for empty 0 bytes)
  - `TAG_BUFFER`: 1 byte (`0x00`)

## What breaks it (failure modes)
- **Top-Level Error 100** — Setting the outer `error_code` to 100 breaks the protocol; top-level remains 0 while partition-level receives 100.
- **Skipping Offset Metadata** — Omission of `high_watermark`, `last_stable_offset`, or `log_start_offset` (each 8 bytes) desynchronizes subsequent fields.
- **Malformed Empty Records** — Writing 0 instead of 1 for empty compact records causes client parsers to read negative length or desynchronize on varint decoding.

## Tradeoffs
- **Immediate Failure vs Awaiting Metadata** — When an unknown UUID is encountered, waiting for `max_wait_ms` is unnecessary because client metadata is out of date and must trigger an immediate refresh.

## CLI / Protocol format
- Request: Fetch v16 for unknown UUID `01234567-89ab-cdef-0123-456789abcdef` with partition 0.
- Response:
  ```
  +---------------------------------------+--------------------+
  | message_size (INT32)                  | dynamic            |
  | correlation_id (INT32)                | <echoed ID>        |
  | header TAG_BUFFER (1B)                | 0x00               |
  | throttle_time_ms (INT32)              | 0                  |
  | error_code (INT16)                    | 0 (NO_ERROR)       |
  | session_id (INT32)                    | 0                  |
  | responses (COMPACT_ARRAY)             | 2 (1 topic + 1)    |
  |   topic_id (UUID 16B)                 | <echoed UUID>      |
  |   partitions (COMPACT_ARRAY)          | 2 (1 part + 1)     |
  |     partition_index (INT32)           | 0                  |
  |     error_code (INT16)                | 100                |
  |     high_watermark (INT64)            | 0                  |
  |     last_stable_offset (INT64)        | 0                  |
  |     log_start_offset (INT64)          | 0                  |
  |     aborted_transactions (C_ARRAY)    | 1 (empty)          |
  |     preferred_read_replica (INT32)    | 0                  |
  |     records (COMPACT_RECORDS)         | 1 (empty)          |
  |     TAG_BUFFER (1B)                   | 0x00               |
  |   topic TAG_BUFFER (1B)               | 0x00               |
  | response TAG_BUFFER (1B)              | 0x00               |
  +---------------------------------------+--------------------+
  ```

## Java specifics — lookup, don't memorize
- `ByteBuffer.wrap(byte[])` — Wraps 16-byte UUID array for hash-based lookup in `Map<ByteBuffer, TopicInfo>`.
- `writeLong(0L)` — Writes 8-byte big-endian zero for offset fields.
