# Stage 17: Fetch single message from disk

## In one line
Locating partition log files on disk (`<log.dirs>/<topic_name>-<partition_index>/00000000000000000000.log`) by resolving the requested topic UUID, and returning the raw RecordBatch data in the Fetch response's `records` compact field.

## Self-test (cover the answers below and answer these first)
- Where are partition messages physically stored on the filesystem?
- How is the partition directory name derived from the topic and partition index?
- How is raw RecordBatch binary data wrapped inside the `records` field of a Fetch v16 response?
- What happens if the partition log file on disk is missing or empty?

## The problem it solved
Up to this stage, the broker only returned empty records or error codes. In this stage, clients actually consume persisted data. The broker must bridge request topic UUIDs to human-readable topic names using the KRaft metadata catalog, construct the corresponding log file path, read the RecordBatch bytes from disk, and embed them verbatim inside the Fetch response.

## Concepts (the transferable part)
- **Disk-to-Wire Zero-Copy Storage Mapping** — Kafka stores messages on disk in the exact binary format expected on the wire (RecordBatch v2). Serving messages does not require deserializing individual records into objects; reading the raw byte file directly copies it into the response buffer.
- **Partition Log Directory Topology**:
  - Base Directory: derived from `server.properties` `log.dirs` (defaults to `/tmp/kraft-combined-logs`).
  - Partition Directory: `<topic_name>-<partition_index>` (e.g. `foo-0`).
  - Active Segment File: `00000000000000000000.log`.
- **Compact Record Encodings** — The `records` field in Fetch v16 is encoded as `COMPACT_RECORDS`: an unsigned varint length prefix equal to `recordBytes.length + 1`, followed by the exact record batch payload.

## What breaks it (failure modes)
- **Path Misalignment** — Hardcoding `/tmp/kraft-combined-logs` without checking `server.properties` breaks when the tester passes custom `log.dirs`.
- **Off-By-One Varint Length** — Writing `recordBytes.length` instead of `recordBytes.length + 1` causes client parsers to drop the final byte or throw varint decoding errors.
- **Parsing UUID vs Name** — Fetch requests provide topic UUIDs, but directories on disk are named after topic strings. The broker must resolve `topicId -> topicName` through metadata prior to filesystem access.

## Tradeoffs
- **`Files.readAllBytes` vs Memory Mapping / `FileChannel.transferTo`** — For single small batches, reading the whole file into a byte array keeps response assembly within standard I/O streams without needing asynchronous file descriptors.

## CLI / Protocol format
- Log location on disk: `<log.dirs>/<topic_name>-<partition_index>/00000000000000000000.log`.
- Fetch Response Partition Block:
  ```
  +---------------------------------------+--------------------+
  | partition_index (INT32)               | 0                  |
  | error_code (INT16)                    | 0 (NO_ERROR)       |
  | high_watermark (INT64)                | 0                  |
  | last_stable_offset (INT64)            | 0                  |
  | log_start_offset (INT64)              | 0                  |
  | aborted_transactions (C_ARRAY)        | 1 (empty)          |
  | preferred_read_replica (INT32)        | 0                  |
  | records (COMPACT_RECORDS)             |                    |
  |   length (U_VARINT)                   | recordBytes.len + 1|
  |   payload                             | <file bytes>       |
  | TAG_BUFFER (1B)                       | 0x00               |
  +---------------------------------------+--------------------+
  ```

## Java specifics — lookup, don't memorize
- `Files.readAllBytes(logFile.toPath())` — Reads entire segment file into a `byte[]`.
- `writeUnsignedVarint(bodyOut, recordBytes.length + 1)` — Encodes compact record byte count.
