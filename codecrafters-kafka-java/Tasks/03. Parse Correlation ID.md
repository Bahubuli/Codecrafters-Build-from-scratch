# Stage 03: Parse Correlation ID

## In one line
Extracting the 32-bit `correlation_id` from the binary Kafka Request Header v2 and echoing it back in the response frame.

## Self-test (cover the answers below and answer these first)
- What is the byte offset of `correlation_id` in a Kafka Request frame when using Request Header v2?
- What are the field sizes of `request_api_key` and `request_api_version` in the Kafka protocol?
- Why must the broker consume/drain all bytes indicated by `message_size` before handling subsequent requests or closing the stream?
- How does `DataInputStream` in Java facilitate reading big-endian binary protocol primitives?

## The problem it solved
In Stage 02, the broker returned a hardcoded correlation ID (`7`). Real Kafka clients generate unique, arbitrary correlation IDs for every request and reject responses that do not match the expected ID. This stage introduces binary deserialization of the Kafka request header to dynamically extract and mirror the client's `correlation_id`.

## Concepts (the transferable part)
- **Binary Request Header Schema** — Kafka RPC headers are strictly typed and ordered. Under Request Header v2:
  1. `message_size`: INT32 (4 bytes)
  2. `request_api_key`: INT16 (2 bytes) — identifies RPC (e.g. 18 for `ApiVersions`, 1 for `Fetch`, 0 for `Produce`)
  3. `request_api_version`: INT16 (2 bytes) — version of the RPC
  4. `correlation_id`: INT32 (4 bytes) — client tracking identifier
  5. `client_id`: Nullable String (variable)
  6. `tagged_fields`: Compact tagged buffer (variable)
- **Frame Draining** — A TCP socket delivers a continuous byte stream. If a server reads only part of a framed message, unread bytes will be misinterpreted as the `message_size` of the next frame. Draining `remaining = message_size - bytes_read` preserves framing boundaries.
- **Header Decoupling** — The request header version and response header version are independent. A client may submit a v2 request header while receiving a v0 response header.

## What breaks it (failure modes)
- **Field Offset Off-By-One** — Miscalculating field widths (e.g. reading `request_api_key` as 4 bytes instead of 2) misaligns all subsequent reads, corrupting the correlation ID into nonsense.
- **Short Reads / Stream Underflow** — Calling `in.read(byte[])` without handling partial reads can slice binary primitives. Using `DataInputStream.readInt()` / `readShort()` or `readFully()` guarantees all required bytes are read before progressing.
- **Unread Remaining Payload** — Not skipping the rest of the message payload leaves trailing bytes in the stream, corrupting subsequent requests on persistent connections.

## Tradeoffs
- **Streaming Primitive Deserialization (`DataInputStream`) vs Full Buffer Slicing (`ByteBuffer`)** — `DataInputStream` decodes bytes directly off the network stream without intermediate buffering, minimizing allocations. `ByteBuffer` requires reading the entire frame into heap memory first, but simplifies random access and CRC checksum calculations.

## CLI / Protocol format
- Request Header v2 binary layout:
  ```
  +-------------------+-------------------+-----------------------+-------------------+
  | message_size(4B)  | request_api_key(2B| request_api_version(2B| correlation_id(4B)| ...
  +-------------------+-------------------+-----------------------+-------------------+
  ```
- Response Layout:
  ```
  +-------------------+-------------------+
  | message_size(4B)  | correlation_id(4B)|
  +-------------------+-------------------+
  | 00 00 00 00       | <echoed ID>       |
  +-------------------+-------------------+
  ```

## Java specifics — lookup, don't memorize
- `DataInputStream.readInt()` — Reads 4 bytes from input stream as a signed big-endian 32-bit integer.
- `DataInputStream.readShort()` — Reads 2 bytes as a signed big-endian 16-bit integer.
- `DataInputStream.skipBytes(int n)` — Skips over and discards exactly `n` bytes of data from the input stream.
