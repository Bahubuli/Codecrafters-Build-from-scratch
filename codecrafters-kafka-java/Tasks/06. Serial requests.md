# Stage 06: Serial requests

## In one line
Servicing multiple sequential Kafka RPC requests over a single persistent TCP connection until client-initiated EOF.

## Self-test (cover the answers below and answer these first)
- Why do high-throughput messaging systems like Kafka avoid opening and closing TCP sockets per request?
- How does the server detect when a persistent client has completed all requests and cleanly closed the TCP connection?
- What happens if the server closes the socket after responding to the first request instead of looping?
- Why is it critical to drain all unparsed bytes of a request payload before reading the subsequent request's `message_size`?

## The problem it solved
In Stages 01–05, the server terminated or closed the socket immediately after emitting a single response. Real Kafka clients maintain long-lived connection pools, multiplexing hundreds of requests over persistent TCP connections. Without a persistent loop, clients received broken pipe / EOF errors on subsequent requests.

## Concepts (the transferable part)
- **Persistent TCP Connections (Keep-Alive)** — TCP connection establishment entails round trips (3-way handshake, TLS negotiation, TCP slow start congestion window ramping). Reusing connections amortizes handshake latency to near zero and prevents TCP port exhaustion on busy hosts.
- **Framed Stream Looping** — Because Kafka messages are length-prefixed, a connection handler repeatedly reads:
  1. `message_size` (4 bytes)
  2. Exactly `message_size` bytes of header and payload
  3. Writes framed response
  4. Flushes and loops back to step 1
- **Clean Stream Teardown (`EOFException`)** — When a client shuts down its socket output stream (`half-close` or `close()`), Java's `DataInputStream.readInt()` encounters the end-of-stream and throws `EOFException`. Catching this exception signals normal client disconnection rather than an unexpected socket fault.

## What breaks it (failure modes)
- **Unbounded Loop on Stream Closure** — If using raw `read()` instead of `readInt()` or `readFully()`, checking for `-1` is mandatory; otherwise the server enters a 100% CPU spin loop reading empty buffers.
- **Frame Alignment Corruption** — If a handler reads fewer or more bytes than indicated by `message_size`, the next iteration reads random payload bytes as the next `message_size`, throwing a fatal protocol error or out-of-memory error.
- **Resource Leakage** — Failure to close the socket inside a `try-with-resources` or `finally` block when the loop terminates leaves file descriptors open in the kernel, eventually triggering `Too many open files`.

## Tradeoffs
- **One-Request-Per-Connection vs Persistent Connection Pooling** — Persistent connections require server memory to maintain socket state and buffers for idle clients, but drastically improve latency, throughput, and CPU utilization compared to per-request socket churn.

## CLI / Protocol format
- Client establishes TCP connection to port `9092`.
- Client sends Request 1 $\to$ Server replies Response 1.
- Client sends Request 2 on same socket $\to$ Server replies Response 2.
- ...
- Client closes socket $\to$ Server cleanly cleans up socket resources.

## Java specifics — lookup, don't memorize
- `EOFException` — Thrown by `DataInputStream` methods when reaching end of stream before reading all required bytes.
- `ExecutorService` / `Executors.newCachedThreadPool()` — Thread pool that dynamically allocates threads to handle concurrent sockets.

## Rebuild checklist
- [ ] Accept incoming `Socket` and hand off to handler method.
- [ ] Enclose request reading in a `while (true)` loop.
- [ ] Catch `EOFException` around `in.readInt()` to break loop cleanly on client disconnect.
- [ ] Process request, drain payload, and write flushed response on each iteration.
- [ ] Ensure socket is closed upon loop exit using `try (clientSocket; ...)`.
