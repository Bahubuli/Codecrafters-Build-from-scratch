# Stage 07: Concurrent requests

## In one line
Decoupling connection acceptance from request handling using thread-pool concurrency (`Executors.newCachedThreadPool()`) to service multiple clients simultaneously without blocking.

## The problem it solved
In a single-threaded server, while the broker is blocked inside `handleClient()` processing requests for client A, the main thread cannot call `serverSocket.accept()` to process connections for client B or C. Concurrent clients experience connection timeouts or serialized blocking. This stage introduces thread pool execution to handle multiple client sockets concurrently.

## Concepts (the transferable part)
- **Thread-per-Connection Concurrency Model** — The simplest scalable concurrency pattern in systems programming. The main accept loop immediately dispatches each established `Socket` to an executor thread. Each thread runs independent blocking reads and writes for that socket, providing total isolation between clients.
- **Dynamic Thread Pooling (`CachedThreadPool`)** — Creating raw OS threads (`new Thread(...)`) per connection incurs expensive stack allocation and kernel thread creation overhead. A cached thread pool reuses previously constructed threads when available and spawns new ones on demand, terminating idle threads after 60 seconds of inactivity.
- **Shared-Nothing State per Connection** — In read-only RPCs (like `ApiVersions`), each connection handler operates on isolated local socket streams with no mutable shared state, eliminating lock contention and race conditions.

## What breaks it (failure modes)
- **Thread Exhaustion (OOM)** — Unbounded thread creation under thousands of simultaneous connections can exhaust OS memory or hit thread limits (`java.lang.OutOfMemoryError: unable to create new native thread`). Production brokers bound the pool or migrate to non-blocking I/O (epoll/kqueue).
- **Socket Leak on Exception** — If an uncaught exception crashes a worker thread before closing the socket, the client hangs indefinitely. Enclosing the client handler in `try-with-resources` (`try (clientSocket; ...)`) guarantees the socket closes even on error.
- **Unhandled Partial Drains on Interleaving Streams** — Because each socket has its own dedicated input stream, request frames never interleave on the wire; each thread consumes only its client's byte stream.

## Tradeoffs
- **Multi-Threaded Blocking I/O vs Single-Threaded Event Loop (Reactor / Epoll / NIO)** — Thread-per-connection is simpler to implement and debug, but has higher memory footprint per connection (~1MB stack per thread). Event loops scale to 100k+ idle connections with low memory, but introduce callback/state machine complexity.

## CLI / Protocol format
- Client 1 connects to port `9092` $\to$ sends ApiVersions v4.
- Client 2 connects concurrently to port `9092` $\to$ sends ApiVersions v4.
- Client 3 connects concurrently to port `9092` $\to$ sends ApiVersions v4.
- All clients receive valid framed ApiVersions v4 responses concurrently without head-of-line blocking.

## Java specifics — lookup, don't memorize
- `Executors.newCachedThreadPool()` — Creates a thread pool that creates new threads as needed, reusing idle threads.
- `pool.submit(Runnable task)` — Submits a task for execution by a worker thread.
- `try (clientSocket; in; out)` — Automatic resource management for the socket and streams within the worker thread.
