# Stage 19: Include Produce in ApiVersions

## In one line
Advertising support for the Produce API (`api_key: 0`, versions `0` to `11`) in the `ApiVersions` response by expanding the compact array to 4 entries.

## Self-test (cover the answers below and answer these first)
- What is the API key for the Produce protocol in Kafka?
- What are the minimum and maximum supported versions advertised for Produce in this stage?
- How is an array of 4 API key entries length-prefixed in a `COMPACT_ARRAY`?
- What trailing byte buffer is required per API key entry?

## The problem it solved
Before producing records to a cluster, producers invoke `ApiVersions` to discover supported wire protocol versions. If the broker omits API key 0 (`Produce`), clients assume publishing is unsupported or fail message delivery. Adding `api_key: 0` enables Kafka producer clients to negotiate the Produce protocol.

## Concepts (the transferable part)
- **Produce API Protocol Key** — `api_key = 0`. Represents produce/publish operations in Kafka's wire specification.
- **Capabilities Matrix Expansion** — As new RPC capabilities are unlocked, the broker extends its `ApiVersions` table:
  1. `ApiVersions` (`18`): min `0`, max `4`
  2. `DescribeTopicPartitions` (`75`): min `0`, max `0`
  3. `Fetch` (`1`): min `0`, max `16`
  4. `Produce` (`0`): min `0`, max `11`
- **Compact Array Length Encoding** — With 4 entries in `api_keys`, the compact array prefix is encoded as $4 + 1 = 5$ (`0x05`).

## What breaks it (failure modes)
- **Stale Array Length Prefix** — Leaving length prefix as 4 (from Stage 13) causes clients to ignore the newly appended Produce entry or fail stream decoding.
- **Incorrect Max Version** — Advertising max version less than 11 fails the stage validation.
- **Missing Tag Buffer** — Each API key entry in `ApiVersions` v4 ends with a tagged fields buffer (`0x00`). Omission misaligns the next entry.

## Tradeoffs
- **Version Compatibility Ceiling** — Version 11 adds support for flexible tagged fields and modern transaction markers. Advertising 0–11 lets contemporary clients use efficient framing.

## CLI / Protocol format
- ApiVersions Response Body (v4) `api_keys` block:
  ```
  +---------------------------------------+--------------------+
  | api_keys length (U_VARINT)            | 5 (4 entries + 1)  |
  | Entry 1: ApiVersions                  | 18 (0 - 4) + 0x00  |
  | Entry 2: DescribeTopicPartitions      | 75 (0 - 0) + 0x00  |
  | Entry 3: Fetch                        | 1  (0 - 16)+ 0x00  |
  | Entry 4: Produce                      | 0  (0 - 11)+ 0x00  |
  |   api_key (INT16)                     | 0                  |
  |   min_version (INT16)                 | 0                  |
  |   max_version (INT16)                 | 11                 |
  |   TAG_BUFFER (1B)                     | 0x00               |
  | throttle_time_ms (INT32)              | 0                  |
  | response TAG_BUFFER (1B)              | 0x00               |
  +---------------------------------------+--------------------+
  ```

## Java specifics — lookup, don't memorize
- `bodyOut.writeShort((short) 0)` — Serializes `api_key = 0` (Produce).
- `bodyOut.writeShort((short) 11)` — Serializes `max_version = 11`.
