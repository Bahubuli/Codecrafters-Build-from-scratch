# Stage 04: Parse API Version

## In one line
Extracting `request_api_version` from Request Header v2, validating against supported versions (0–4), and returning an INT16 `error_code` (35 `UNSUPPORTED_VERSION` vs 0 `NO_ERROR`) in the response body with accurate 4-byte `message_size` framing.

## The problem it solved
Kafka brokers evolve across releases with changing request and response schemas. Clients send an `ApiVersions` request to discover which schemas the broker supports. If a client attempts an unsupported version, the broker must reject the request gracefully using error code 35 (`UNSUPPORTED_VERSION`) rather than dropping the socket or crashing on unexpected fields.

## Concepts (the transferable part)
- **Granular RPC Versioning** — Instead of a monolithic protocol version number, Kafka assigns each RPC an API key (`INT16`, e.g. 18 for `ApiVersions`, 0 for `Produce`) and an independent version range (`INT16`). This allows backwards and forwards compatibility between differing client and broker versions without breaking existing endpoints.
- **Error Code Convention** — Kafka uses standardized 16-bit signed integers for error reporting:
  - `0`: `NONE` / `NO_ERROR`
  - `35`: `UNSUPPORTED_VERSION`
- **Dynamic Message Sizing** — The framing prefix `message_size` must match the sum of bytes that follow:
  $$\text{message\_size} = \text{sizeof}(\text{correlation\_id}) + \text{sizeof}(\text{response\_body})$$
  Buffering the body into a `ByteArrayOutputStream` allows dynamically computing the exact byte length before writing the 4-byte header prefix.

## What breaks it (failure modes)
- **Miscalculated Message Size** — If `message_size` is too small, the client truncates the frame; if too large, the client hangs waiting for additional bytes from the stream.
- **Signed vs Unsigned 16-bit Comparisons** — `request_api_version` is a signed 16-bit integer. When comparing versions, check both lower bound ($\ge 0$) and upper bound ($\le 4$).
- **Writing Big-Endian Short vs Int** — The `error_code` field is an `INT16` (2 bytes). Writing it as a 4-byte `INT32` corrupts response body alignment.

## Tradeoffs
- **Buffering Body in Memory (`ByteArrayOutputStream`) vs Two-Pass Size Calculation** — Buffering the response body in memory allows writing length-prefixed frames in a single streaming pass to the socket without calculating sizes by hand, at the minimal cost of a small heap allocation.

## CLI / Protocol format
- Request Header:
  ```
  +-------------------+-------------------+-----------------------+-------------------+
  | message_size(4B)  | request_api_key(2B| request_api_version(2B| correlation_id(4B)|
  +-------------------+-------------------+-----------------------+-------------------+
  ```
- Response Layout:
  ```
  +-------------------+-------------------+-------------------+
  | message_size(4B)  | correlation_id(4B)| error_code(2B)    |
  +-------------------+-------------------+-------------------+
  | 00 00 00 06       | <echoed ID>       | 00 23 (35) or 00 00
  +-------------------+-------------------+-------------------+
  ```

## Java specifics — lookup, don't memorize
- `ByteArrayOutputStream` — In-memory buffer that captures written bytes.
- `DataOutputStream.writeShort(int v)` — Writes 2 bytes in big-endian network order.
- `bodyStream.toByteArray()` — Returns byte array of captured stream content.
