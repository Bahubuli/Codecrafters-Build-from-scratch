# Stage 12: List for multiple topics

## In one line
Handling multi-topic `DescribeTopicPartitions` requests by iterating through requested topic names in request order, resolving each against the KRaft metadata catalog, and packing mixed known/unknown topic responses.

## Self-test (cover the answers below and answer these first)
- How must the broker order topic entries in the `DescribeTopicPartitions` response?
- How does the broker handle a request containing a combination of both existing and non-existent topics?

- Does resolving multiple topics require multiple metadata log reads?

## The problem it solved
Kafka clients (such as consumer groups subscribing to pattern topics or multiple distinct topic streams) frequently batch metadata discovery into a single `DescribeTopicPartitions` RPC. The broker must process every requested topic, look up each one in the cluster catalog, and return an array preserving the client's request order with appropriate per-topic error codes (0 for existing, 3 for unknown).

## Concepts (the transferable part)
- **Request Order Preservation** — Kafka RPC conventions mandate that array responses (such as `topics` in metadata and fetch requests) preserve the exact order specified in the client request to allow predictable client-side indexing and correlation.
- **Heterogeneous Error Statuses** — Kafka metadata responses are granular: error code 0 for existing topics and error code 3 (`UNKNOWN_TOPIC_OR_PARTITION`) for missing topics can coexist in the same response payload.
- **Single-Pass Catalog Lookup** — By caching or buffering parsed KRaft records into a map (`Map<String, TopicInfo>`), resolving $K$ requested topics requires only $O(1)$ lookups per topic.

## What breaks it (failure modes)
- **Reordering Topics by Alphabetical or Hash Order** — Iterating over `topicsMap.values()` rather than the request's `topicNames` list violates the client's expected ordering.
- **Corrupting Message Size Framing** — Multiplying fixed lengths instead of dynamically measuring `body.length` breaks the outer INT32 `message_size` frame as topic counts vary.
- **Dropping Tagged Fields per Topic** — Each topic entry in the compact array requires its own trailing `TAG_BUFFER` (`0x00`). Forgetting this after each topic desynchronizes subsequent topic entries.

## Tradeoffs
- **Full Catalog Scan vs Targeted Topic Scan** — Reading all `TopicRecord` and `PartitionRecord` entries into an in-memory map on request is fast ($< 1$ ms) and simple, scaling naturally to arbitrary numbers of queried topics.

## CLI / Protocol format
- Request: `DescribeTopicPartitions` for `["foo", "bar"]`.
- Response:
  ```
  +-------------------------------------+--------------------+
  | message_size (INT32)                | dynamic (123B)     |
  | correlation_id (INT32)              | <echoed ID>        |
  | header TAG_BUFFER (1B)              | 0x00               |
  | throttle_time_ms (INT32)            | 0                  |
  | topics (COMPACT_ARRAY)              | 3 (2 topics + 1)   |
  |   [0] "foo"                         |                    |
  |       error_code (INT16)            | 0                  |
  |       topic_id (UUID 16B)           | <foo UUID>         |
  |       partitions (COMPACT_ARRAY)    | [partition 0]      |
  |       TAG_BUFFER (1B)               | 0x00               |
  |   [1] "bar"                         |                    |
  |       error_code (INT16)            | 0                  |
  |       topic_id (UUID 16B)           | <bar UUID>         |
  |       partitions (COMPACT_ARRAY)    | [partition 0]      |
  |       TAG_BUFFER (1B)               | 0x00               |
  | next_cursor (INT8)                  | 0xFF (-1)          |
  | response TAG_BUFFER (1B)            | 0x00               |
  +-------------------------------------+--------------------+
  ```

## Java specifics — lookup, don't memorize
- `writeUnsignedVarint(bodyOut, topicNames.size() + 1)` — Formats the outer topics compact array header.
- `topicsMap.get(topicName)` — Constant time lookup against the populated cluster metadata map.
