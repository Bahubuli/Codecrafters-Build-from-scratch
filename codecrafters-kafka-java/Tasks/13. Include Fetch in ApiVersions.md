# Stage 13: Include Fetch in ApiVersions

## In one line
Expanding the `ApiVersions` response compact array from 2 to 3 keys by advertising API key 1 (`Fetch`) with supported versions 0 through 16.

## Self-test (cover the answers below and answer these first)
- What is the numeric API key for the Kafka `Fetch` RPC?
- What version range is advertised for the `Fetch` API in this stage?
- How does adding a third API key update the compact array length prefix?
- Why do Kafka clients query `ApiVersions` before attempting to consume messages via `Fetch`?

## The problem it solved
Before subscribing to topic partitions or consuming streaming data, Kafka clients query the broker's `ApiVersions` to establish version compatibility for data transfer protocols. Without advertising support for API key 1 (`Fetch`), consumer clients assume the broker cannot serve message data and disconnect or degrade into incompatible legacy modes.

## Concepts (the transferable part)
- **Protocol Discovery for Data Plane Operations** — Unlike administrative RPCs (`DescribeTopicPartitions`), `Fetch` belongs to Kafka's high-throughput data plane. Advertising version 16 indicates support for compact string headers, KIP-320 epoch-based truncation, and KRaft topic UUID addressing.
- **Incremental Capability Expansion** — Adding protocol capabilities does not require changing broker listening sockets or response framing structures—it simply expands the `api_keys` compact array by bumping the count prefix to 4 ($3 + 1$) and appending the 7-byte entry.
- **Fetch API Entry Anatomy**:
  - `api_key`: `1` (`0x0001`, INT16)
  - `min_version`: `0` (`0x0000`, INT16)
  - `max_version`: `16` (`0x0010`, INT16)
  - `TAG_BUFFER`: `0x00` (empty tagged fields)

## What breaks it (failure modes)
- **Compact Array Length Undercount** — Retaining varint length 3 (from 2 keys) causes the parser to read only the first two entries and treat the Fetch entry as `throttle_time_ms`.
- **Misconfigured MaxVersion** — Advertising `max_version < 16` causes the tester to fail version checks, while advertising an unsupported version range causes clients to emit unsupported RPC schemas.
- **Byte Width Inconsistency** — Writing API key or versions as INT32 instead of INT16 corrupts subsequent field alignments.

## Tradeoffs
- **Static API Catalog vs Dynamic Registration** — Hardcoding supported core APIs in `handleApiVersions` maintains straightforward Big-Endian serialization without reflection overhead.

## CLI / Protocol format
- Request: `ApiVersions` (API key 18, version 4).
- Response `api_keys` compact array:
  ```
  +--------------------------------+-------------------+
  | api_keys length (U_VARINT)     | 4 (3 keys + 1)    |
  | [0] ApiVersions                |                   |
  |     api_key (INT16)            | 18                |
  |     min_version (INT16)        | 0                 |
  |     max_version (INT16)        | 4                 |
  |     TAG_BUFFER (1B)            | 0x00              |
  | [1] DescribeTopicPartitions    |                   |
  |     api_key (INT16)            | 75                |
  |     min_version (INT16)        | 0                 |
  |     max_version (INT16)        | 0                 |
  |     TAG_BUFFER (1B)            | 0x00              |
  | [2] Fetch                      |                   |
  |     api_key (INT16)            | 1                 |
  |     min_version (INT16)        | 0                 |
  |     max_version (INT16)        | 16                |
  |     TAG_BUFFER (1B)            | 0x00              |
  +--------------------------------+-------------------+
  ```

## Java specifics — lookup, don't memorize
- `bodyOut.writeShort((short) 1)` — Writes 2-byte big-endian short for API key 1.
- `bodyOut.writeShort((short) 16)` — Writes 2-byte big-endian short for maximum version 16.
