# Stage 21: Respond for valid topic and partition

## In one line
Validating topic and partition existence against KRaft cluster metadata and returning `error_code: 0` (`NO_ERROR`) with initial base offset `0` when valid.

## Self-test (cover the answers below and answer these first)
- Where does a KRaft broker look up whether a topic exists?
- Where does the broker look up whether a partition belongs to a given topic?
- What are `base_offset` and `log_start_offset` for the first record appended to an empty partition?
- What is `log_append_time_ms` when the broker indicates the log append timestamp is not explicitly overridden?

## The problem it solved
In Stage 20, all produce requests were treated as targeting non-existent partitions. In this stage, the broker inspects cluster metadata loaded from disk (`__cluster_metadata-0/00000000000000000000.log`) to distinguish valid topics and partitions from invalid ones, returning `NO_ERROR` (`0`) on valid produce requests.

## Concepts (the transferable part)
- **Metadata-Driven Request Routing** — Producers route batches based on cluster metadata. The broker validates incoming requests against its cached/replayed KRaft log:
  1. Look up topic by name in `catalog.byName`.
  2. If topic exists, search `topic.partitions` for matching `partitionIndex`.
- **Produce Success Offsets**:
  - `error_code`: `0` (`NO_ERROR`).
  - `base_offset`: `0L` (first append offset).
  - `log_append_time_ms`: `-1L` (indicates broker timestamp not used / CreateTime retained).
  - `log_start_offset`: `0L` (log begins at 0).
- **Graceful Error Preservation**:
  - If either topic or partition is missing, continue emitting `error_code: 3` (`UNKNOWN_TOPIC_OR_PARTITION`) and `-1L` offsets.

## What breaks it (failure modes)
- **Case Sensitivity & Partial Matches** — Topic names in Kafka are case-sensitive exact strings; partition IDs are 32-bit integers.
- **Ignoring Partition List** — Validating only the topic name while accepting non-existent partitions (e.g., partition 918 when only 0 and 1 exist).
- **Offset Discrepancy** — Emitting `-1` instead of `0` on success breaks producer offset tracking.

## Tradeoffs
- **In-Memory Catalog vs On-Demand Parsing** — `loadClusterMetadata()` reads the metadata log into `MetadataCatalog`. Reusing the catalog across DescribeTopicPartitions, Fetch, and Produce guarantees uniform cluster views.

## CLI / Protocol format
- Produce Response Partition Entry (Success vs Invalid):
  ```
  Success (Valid):
    index: INT32 (partitionId)
    error_code: 0 (NO_ERROR)
    base_offset: 0
    log_append_time_ms: -1
    log_start_offset: 0
    record_errors: 1 (empty)
    error_message: 0 (null)
    TAG_BUFFER: 0x00

  Failure (Invalid):
    index: INT32 (partitionId)
    error_code: 3 (UNKNOWN_TOPIC_OR_PARTITION)
    base_offset: -1
    log_append_time_ms: -1
    log_start_offset: -1
    record_errors: 1 (empty)
    error_message: 0 (null)
    TAG_BUFFER: 0x00
  ```

## Java specifics — lookup, don't memorize
- `ti.partitions.stream().anyMatch(pi -> pi.partitionId == partitionIndex)` — Verifies partition existence within the topic metadata.
