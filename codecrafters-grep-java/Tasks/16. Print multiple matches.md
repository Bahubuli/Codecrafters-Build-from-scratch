# Stage 16: Print multiple matches

## In one line
Iterative cursor advancement after finding a match to harvest all non-overlapping slices $[start, end)$ from a string, with special handling for zero-width matches and boundary anchors.

## Self-test (cover the answers below and answer these first)
- Once a match spanning $[start, end)$ is identified, at what index should the engine resume scanning to find subsequent matches without overlap?
- What hazard arises when a pattern matches an empty substring ($end == start$), and how must the search cursor advance to prevent an infinite loop?
- How do anchors (`^` and `$`) restrict multiple-match iteration across an input string?

## The problem it solved
Previously, `-o` (`--only-matching`) extracted only the very first match on an input line, silently dropping subsequent occurrences. Real `grep -o` functions as a tokenizer: it extracts and outputs every non-overlapping substring on the line that matches the pattern, each on its own line in stdout.

## Concepts (the transferable part)
- **Non-Overlapping Tokenization / Lexing** — Regex matching across a stream models lexical analysis. When a token spanning $[start, end)$ matches, the engine commits that slice and advances the search cursor strictly to `start = end`. This prevents overlapping matches (e.g. matching `\d\d` on `"123"` yields only `"12"` with `"3"` remaining, never overlapping `"23"`).
- **Zero-Width Progress Guarantee** — If a pattern matches an empty substring ($end == start$, e.g. with `?` or empty alternation branches), setting `start = end` leaves the cursor unchanged, causing an infinite loop. The engine must enforce forward progress by advancing `start = start + 1` whenever $end \le start$.
- **Anchor-Constrained Boundary Evaluation** — Anchors eliminate scan loops: `^` restricts matching strictly to start index `0` (at most one match per line), and `$` requires $end == \text{length}$, meaning no subsequent matches can follow it on that line.

## What breaks it (failure modes)
- Infinite loop on zero-width matches (`end == start`) — Occurs with patterns containing nullable quantifiers (`?`) or empty alternatives. Handled by checking `if (end > start) start = end; else start = start + 1;`.
- Overlapping match emission — Advancing `start++` regardless of match length emits overlapping substrings (e.g. finding `"10"` then `"0"` from `"10"` with `\d+`). Handled by advancing `start = end` on non-empty matches.
- State contamination between consecutive matches — Reusing the capture group map across multiple match evaluations on the same line causes backreferences from match 1 to falsely influence match 2. Handled by passing a fresh `new HashMap<>()` into each candidate start index evaluation.
- Failure to terminate on end-anchored patterns (`$`) — Continuing the loop after finding a match at the end of the line. Handled by breaking out of the loop immediately when `anchorEnd` is satisfied.
- Positional flag ordering in CLI — Accepting flags in any position (`-o -E <pattern>` vs `-E <pattern> -o`). Handled by flag scanning in `main`.

## Tradeoffs
- Eager `List<String>` collection vs Lazy Match Iterator — Storing matches in an `ArrayList<String>` is simple, fast, and idiomatic for standard line-by-line processing, whereas an iterator/generator saves memory when streaming very large inputs or piping into early-abort commands (e.g. `head -n 1`).
- Delegating `findFirstMatch` to `findAllMatches` vs maintaining separate loops — Calling `findAllMatches.get(0)` reuses the exact same parsing and matching logic with zero code duplication, with negligible overhead for typical text lines.

## CLI / Protocol format
- Flags: `-o` or `--only-matching` with `-E <pattern>`.
- Stdin: Input line stream.
- Stdout:
  - If `-o`: prints each match on its own line.
  - If `-o` omitted: prints the entire matching line.
- Exit code:
  - `0` if at least one match was found across the input stream.
  - `1` if no matches were found.

## Java specifics — lookup, don't memorize
- `List<String> results = new ArrayList<>()` — Standard dynamic list for collecting extracted match substrings.
- `String.substring(int beginIndex, int endIndex)` — Extracts slice from `beginIndex` (inclusive) to `endIndex` (exclusive).
- `new HashMap<>()` — Instantiates an empty map for captured groups per candidate start position.
