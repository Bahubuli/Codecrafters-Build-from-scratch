# Stage 24: Search a multi-line file

## In one line
Iterating line-by-line across disk files using streaming readers, executing pattern evaluation independently on each line, and returning exit code 0 if any line matches.

## Self-test (cover the answers below and answer these first)

## The problem it solved
Searching disk files often involves inspecting documents with thousands or millions of lines. If a program attempts to read entire multi-gigabyte files into memory or fails to reset line matching state between lines, memory exhaustion occurs and line boundaries are blurred. This stage ensures grep processes each line independently in a streaming loop, printing every matching line and reporting success if at least one match was found.

## Concepts (the transferable part)
- **Streaming Line-by-Line Processing**: By streaming lines via `Scanner.hasNextLine()` / `BufferedReader.readLine()`, the memory footprint remains $O(L_{\text{max}})$ (proportional to the longest single line) rather than $O(\text{total file size})$.
- **Independent Line Evaluation**: Every line represents an isolated input record. Regex matching state (e.g. anchors `^` and `$`, captured groups) is evaluated cleanly per line.
- **Match State Accumulator**: A boolean flag (`matchedAny`) is initialized to `false`. Whenever any line matches, it is printed immediately and `matchedAny` becomes `true`. Once the file EOF is reached, the process exits with `0` if `matchedAny` is true, otherwise `1`.

## What breaks it (failure modes)
- Short-circuiting after the first match — unlike queries that only test presence, `grep` must print *all* matching lines throughout the entire file before terminating. Exiting on the first match omits subsequent matching lines.
- Leaking capture groups across lines — persisting capture group maps across different lines can cause backreferences to match content from previous lines. Capture group state must be fresh per line.
- Ignoring newline delimiters — treating multi-line files as single un-split buffers causes patterns with `.*` to span across newlines inappropriately.

## Tradeoffs
- Immediate line streaming vs Batch buffer collection — Streaming matching lines directly to stdout reduces latency and peak memory usage compared to buffering all matches into a list before printing.
- `Scanner` vs `BufferedReader` — `Scanner` is convenient for unified stdin/file access in quick CLI tools, while `BufferedReader` provides higher throughput for I/O-heavy file scans.

## CLI / Protocol format
- Command: `./your_program.sh -E "<pattern>" <file_path>`
- Output:
  - Prints all lines in the target file that match `<pattern>` to stdout in appearance order.
  - Exits with `0` if one or more lines matched.
  - Exits with `1` if zero lines matched.

## Java specifics — lookup, don't memorize
- `while (scanner.hasNextLine()) { String line = scanner.nextLine(); ... }` — consumes input stream line-by-line.
- `System.exit(matchedAny ? 0 : 1)` — conveys process exit status to the operating system / calling shell.

## Rebuild checklist
- [ ] Open target file stream with `new Scanner(new File(path))`.
- [ ] Initialize `boolean matchedAny = false`.
- [ ] Loop over lines using `while (scanner.hasNextLine())`.
- [ ] For each line, test `matchPattern(line, pattern)`.
- [ ] If matched, print the line to `stdout` and set `matchedAny = true`.
- [ ] Close the scanner.
- [ ] Exit with code `0` if `matchedAny` is true, else exit with code `1`.
