# Stage 14: Print multiple matching lines

## In one line
Processing stream inputs by reading until EOF, filtering records through the regex engine, streaming matching lines to stdout, and summarizing match existence as the process exit status.

## The problem it solved
Earlier iterations assumed a single line of input on standard input and immediately terminated after testing that single line. Real grep processes multi-line streams (files, piped output from other commands) until EOF, streaming all matching lines to standard output and returning exit code 0 if at least one line matched, or 1 if none matched.

## Concepts (the transferable part)
- **Stream Processing / Filter Pipeline** — Reading input incrementally line-by-line until EOF (End Of File) allows programs to process arbitrarily large streams with $O(1)$ auxiliary memory per line rather than buffering entire files.
- **Stateful Exit Code Accumulation** — When an operation evaluates multiple records, aggregate status flags (`matchedAny`) track whether any element satisfied the predicate while still executing the filter over the entire stream.
- **Lazy Evaluation vs Memory Buffering** — Evaluating and printing matches on the fly (streaming) provides immediate output to downstream consumers without waiting for upstream EOF or exhausting memory.

## What breaks it (failure modes)
- Early termination on first match — Exiting after finding the first matching line discards subsequent matching lines in the stream.
- Early exit on first non-match — Exiting when the first line fails to match prevents checking subsequent lines that might match.
- Swallowing empty matching lines — Empty lines can match patterns (e.g. `^$`, `a*`, `.*`); skipping empty lines erroneously would corrupt the output.
- Inverted exit codes or resetting `matchedAny` — Overwriting `matchedAny = matchPattern(...)` on each iteration instead of accumulating `matchedAny = true` causes the exit code to only reflect the final line.

## Tradeoffs
- Streaming line-by-line (`Scanner.hasNextLine()`) vs Slurping all input (`readAllLines`) — Line-by-line streaming requires $O(L)$ memory where $L$ is line length, scaling to gigabytes of stream data, whereas slurping buffers all lines in memory causing potential OOM.
- `Scanner` vs `BufferedReader` — `Scanner` is convenient for simple token/line scanning with regex delimiter support, while `BufferedReader.readLine()` has lower overhead and higher throughput in performance-critical CLI tools.

## CLI / Protocol format
- Command: `./your_program.sh -E "<pattern>"`
- Stdin: Multi-line text stream terminated by EOF (`\n` separated).
- Stdout: Each matching line printed sequentially, preserving order. Non-matching lines are omitted.
- Exit code:
  - `0` if at least one line matched the pattern.
  - `1` if zero lines matched the pattern.

## Java specifics — lookup, don't memorize
- `Scanner.hasNextLine()` — Returns `true` if there is another line in the input of this scanner, blocking until input is available or EOF is reached.
- `Scanner.nextLine()` — Advances this scanner past the current line and returns the input that was skipped (excluding line separators).
- `System.exit(int status)` — Terminates the JVM with the given status code.
