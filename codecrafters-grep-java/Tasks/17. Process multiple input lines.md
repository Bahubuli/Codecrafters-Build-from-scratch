# Stage 17: Process multiple input lines

## In one line
Streaming line-by-line regex evaluation with `-o` across multi-line standard input streams, preserving document line ordering and record isolation.

## Self-test (cover the answers below and answer these first)
- Why must matching with `-o` across multi-line input preserve line boundaries rather than concatenating the entire document into a single continuous buffer?
- How does the engine prevent state contamination (such as backreferences or group capture maps) between line 1 and line 2?
- What is the POSIX exit status contract when processing a 10,000-line file where only line 9,999 contains a match?

## The problem it solved
Earlier stages verified `-o` on single-line inputs (`#cj0`, `#ss2`) or whole-line output on multi-line streams (`#pz6`). Combining `-o` (only-matching) with multi-line input requires streaming lines sequentially from `System.in`, extracting all non-overlapping matches from line 1, then from line 2, and so on, while outputting each match on its own line in sequential input order.

## Concepts (the transferable part)
- **Line-Oriented Streaming Filter** — Text processing utilities like `grep`, `sed`, and `awk` treat the newline character `\n` as the primary record separator. Each line is an independent evaluation boundary.
- **Ordered Flattening / Mapping** — Multi-line match extraction is a nested map-and-flatten operation ($Stream\langle Line \rangle \rightarrow Stream\langle Match \rangle$), where the original document ordering (line index, followed by match offset within line) is strictly preserved.
- **Record Isolation** — Regex state (line anchors `^`/`$`, capture groups, backreferences) must be localized to individual lines. An anchor `^` matches the beginning of each line, not just the beginning of the stream.

## What breaks it (failure modes)
- Concatenating lines into one buffer — Slurping the entire stream into one string changes anchor semantics: `^` would only match line 1 unless multiline mode `(?m)` is explicitly supported, and newline characters could inadvertently be consumed by `.` or character classes.
- Non-deterministic or grouped reordering — Printing matches out of order (e.g. grouping by pattern branch or line) violates the Unix streaming pipeline convention.
- Exiting on first line non-match — If line 1 does not match, the loop must not abort; it must continue evaluating subsequent lines until EOF.

## Tradeoffs
- Line-by-line iteration (`Scanner.hasNextLine()`) vs Slurping whole stream — Line-by-line consumes $O(L)$ memory (where $L$ is the length of the longest line) and begins emitting matching records immediately, whereas buffering the entire file consumes $O(N)$ memory and introduces pipeline latency.

## CLI / Protocol format
- Command: `./your_program.sh -o -E "<pattern>"`
- Stdin: Multi-line text stream.
- Stdout: Every match from line 1 (one per line), followed by every match from line 2, etc.
- Exit code:
  - `0` if at least one match was found across the entire input stream.
  - `1` if zero matches were found.

## Java specifics — lookup, don't memorize
- `Scanner.hasNextLine()` — Evaluates whether standard input contains another line.
- `Scanner.nextLine()` — Reads next line excluding the trailing `\r\n` or `\n`.
- `System.out.println(String)` — Writes string followed by platform newline to stdout.
