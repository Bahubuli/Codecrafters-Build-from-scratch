# Stage 23: Search a single-line file

## In one line
Extending CLI argument parsing to accept target file paths, opening file input streams via `Scanner(File)` alongside standard input (`System.in`), and processing lines uniformly.

## Self-test (cover the answers below and answer these first)
- How does standard `grep` differentiate between option flags and positional arguments like file targets?
- What input source should grep read from when no positional file paths are provided on the CLI?
- What exit codes should grep emit when searching across file contents?

## The problem it solved
Up to this stage, grep could only inspect text piped through standard input (`System.in`). Real-world grep commands frequently target disk files directly (e.g. `grep -E "pattern" fruits.txt`). Adding positional file argument parsing allows grep to read input streams from files on disk while retaining identical regex matching, line filtering, and exit status logic.

## Concepts (the transferable part)
- **Positional CLI Arguments** — Non-flag parameters that follow or interleave option flags represent operational targets (such as file paths).
- **Stream Abstraction** — Decoupling input sources (standard input `System.in` vs file streams `Scanner(File)`) so the core line matching pipeline executes identically regardless of the underlying I/O source.
- **Match Aggregation & Status Codes** — Exit code `0` is emitted if at least one matching line is found across the queried input; exit code `1` is emitted if no lines match.

## What breaks it (failure modes)
- Confusing flag parameters with file names — Blindly treating option arguments (such as the pattern string following `-E` or the mode following `--color`) as file paths.
- Missing default fallback — Failing to read from `System.in` when no file paths are specified on the command line.
- Unhandled missing files — Throwing unhandled exceptions or crashing if a specified file cannot be opened.

## Tradeoffs
- `Scanner(File)` vs `BufferedReader / Files.lines()` — `Scanner` provides a uniform `hasNextLine()` / `nextLine()` interface compatible with existing stdin reading routines, keeping the streaming loop concise for single-line and multi-line file processing.

## CLI / Protocol format
- Command: `./your_program.sh -E "<pattern>" <file_path>`
- When matching line found:
  - Prints matching line to stdout.
  - Exits with status `0`.
- When no match found:
  - Prints nothing to stdout.
  - Exits with status `1`.

## Java specifics — lookup, don't memorize
- `new Scanner(new File(path))` — Constructs a scanner that produces values scanned from the specified file using platform default character decoding.
- Resource management: Always close file scanners via `scanner.close()` or try-with-resources to release operating system file descriptors.
