# Stage 25: Search multiple files

## In one line
Aggregating multiple positional file arguments, executing line-by-line regex scanning across each input file, formatting matched lines with `<filename>:` prefixes when multiple files are searched, and returning code 0 if any file matches.

## Self-test (cover the answers below and answer these first)
- When should `grep` prepend a `<filename>:` prefix to matched output lines, and when should it omit the prefix?
- If a pattern matches lines in `file1.txt` but produces zero matches in `file2.txt`, what is the overall process exit status?
- How should missing or unreadable files among multiple targets be handled without aborting processing of remaining files?

## The problem it solved
Standard `grep` invocations frequently pass multiple target files (e.g. `grep -E "pattern" f1.txt f2.txt`). Previously, grep only handled single files or standard input without attributing matching lines to their source file. This stage adds multi-file scanning, attaching the `<filename>:` prefix to disambiguate matches across distinct files while retaining single-file and stdin formatting semantics.

## Concepts (the transferable part)
- **Multi-Source Line Ingestion**: Generalizing input streams into a list of sources (`FileInput { name, scanner }`) where `name` identifies the target file on disk or is `null` for `System.in`.
- **Conditional Output Prefixing**: In POSIX grep, the `<filename>:` prefix is conditionally enabled only when the number of target files is strictly greater than one (`filePaths.size() > 1`). Single file targets and stdin queries never print the prefix by default.
- **Global Match Aggregation Across Sources**: A shared `matchedAny` accumulator spans across all file evaluations, ensuring an exit code of `0` is emitted if at least one matching line occurs anywhere across the collection of target files.

## What breaks it (failure modes)
- Prepending filename prefixes on single files — users and automated test suites expect standard raw lines when only one file is provided.
- Terminating early on the first file with no matches — if `file1.txt` has no matches, the loop must continue scanning `file2.txt`, `file3.txt`, etc.
- Printing filenames on standard input — stdin inputs should never receive a filename prefix.

## Tradeoffs
- Sequential file iteration vs Concurrent scanning — Sequential scanning maintains deterministic output order matching the argument order provided by the user.
- Shared exit status vs Per-file status — Grep reports process-level success if any match is found, mirroring Unix pipeline conventions.

## CLI / Protocol format
- Command: `./your_program.sh -E "<pattern>" file1.txt file2.txt ...`
- Output:
  - `<filename>:<matched_line>` for each match across any file when `files.count > 1`.
  - Exits with `0` if at least one matching line is found in any file.
  - Exits with `1` if no matches are found in any file.

## Java specifics — lookup, don't memorize
- `boolean printFilenamePrefix = filePaths.size() > 1;` — checks whether multiple files were provided.
- `String prefix = (printFilenamePrefix && input.name != null) ? input.name + ":" : "";` — constructs the output line prefix.
