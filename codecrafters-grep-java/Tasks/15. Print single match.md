# Stage 15: Print single match

## In one line
Transforming the regex matcher from an existence predicate (`boolean`) into an extraction engine (`String` slice) driven by leftmost-start and greedy-end boundaries under the `-o` / `--only-matching` CLI flag.

## The problem it solved
Previously, `grep` only functioned as a record filter: it determined whether a pattern matched anywhere within a line and printed the entire line. The `-o` (`--only-matching`) option requires isolating and printing only the exact substring that satisfied the pattern, requiring the engine to return the span $[start, end)$ rather than a simple true/false answer.

## Concepts (the transferable part)
- **Predicate vs Extractor** — A regex engine can operate in two modes: decision (does $P$ match anywhere in $S$?) and extraction (find slice $S[i..j]$ that satisfies $P$). Adapting a backtracking evaluator to return the match end index unifies both modes, since a non-null extraction directly implies a true predicate.
- **Leftmost-Longest (Greedy) Match Semantics** — For unanchored searches, standard regular expressions anchor at the earliest possible starting index $i$ in the string (leftmost). At that starting index, greedy quantifiers explore maximum-length branches before backtracking to shorter ones (longest).
- **Flag Disjunction in CLI Parsing** — Command-line tools accept options in flexible orders (e.g. `-o -E <pattern>` or `-E <pattern> -o`); parsing flags into state variables decouples flag sequencing from execution logic.

## What breaks it (failure modes)
- Rigid positional argument parsing (`args[0] == "-o"`) — Rejecting valid permutations like `-E <pat> -o` or crashing on unexpected indices. Handled by iterating through all CLI arguments and toggling state flags.
- Returning the entire line instead of the matched slice — Printing `inputLine` when `-o` is enabled instead of `inputLine.substring(start, end)`.
- Selecting a later match over an earlier match — Skipping candidate start indices or searching right-to-left breaks POSIX leftmost rule. Handled by scanning `start` sequentially from `0` to `inputLine.length()`.
- Premature termination on multi-character quantifiers — Taking a non-greedy 1-character match when a quantifier like `\d+` could match more characters. Handled by sorting exploration from `maxMatch` down to `1`.
- Null pointer vs empty string ambiguity — An unanchored pattern matching empty input vs a failed match. Returning `null` on failure vs `""` for a zero-length match preserves distinction.

## Tradeoffs
- Returning substring directly vs returning `MatchResult { int start, int end }` — Returning `String` directly avoids object allocation overhead when only the extracted text is consumed, whereas returning an offset span is more flexible when building span-based tokenizers or match highlighters.
- Refactoring `matchPattern` to wrap `findFirstMatch` vs maintaining separate codebases — Wrapping `findFirstMatch(line, pattern) != null` guarantees identical matching semantics between filter mode and extract mode with zero logic duplication.

## CLI / Protocol format
- Flags: `-o` or `--only-matching` combined with `-E <pattern>`.
- Examples:
  - `./your_program.sh -o -E "\d"`
  - `./your_program.sh -E "\d" -o`
- Stdin: Input line stream.
- Stdout:
  - If `-o` enabled: prints only the matched substring for each line where a match occurs.
  - If `-o` omitted: prints the entire matching line.
- Exit code:
  - `0` if at least one match was found.
  - `1` if no matches were found.

## Java specifics — lookup, don't memorize
- `String.substring(int beginIndex, int endIndex)` — Returns a substring beginning at `beginIndex` (inclusive) and extending to `endIndex` (exclusive).
- `String.equals(Object anObject)` — Compares strings for value equality rather than reference identity (`==`).
- `System.out.println(String s)` — Prints string to stdout followed by a newline.
