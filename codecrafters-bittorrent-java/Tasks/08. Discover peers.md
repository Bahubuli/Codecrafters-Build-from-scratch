# Stage 08: Discover peers

## In one line

## The problem it solved
BitTorrent is a peer-to-peer network without centralized file hosts; clients must discover other peers who are currently uploading or downloading the desired file. The HTTP tracker acts as a rendezvous service. By issuing an announce GET request with the torrent's `info_hash`, client's `peer_id`, port, and progress statistics (`uploaded`, `downloaded`, `left`), the client receives an active list of swarm peers.

## Concepts (the transferable part)
- **Tracker Rendezvous Protocol**: P2P clients locate swarm participants by querying coordinating trackers via HTTP GET, providing cryptographic swarm identity (`info_hash`) and listening socket info (`port`).
- **Binary URL Encoding (RFC 3986)**: Standard string URL encoding assumes text input (often converting characters to UTF-8 first). Cryptographic identifiers (such as the 20-byte SHA-1 `info_hash`) are arbitrary byte sequences; percent-encoding must operate directly on the raw bytes (`%xx`) without character set conversion.
- **Compact Peer Representation (BEP 23)**: Rather than sending bulky JSON/Bencode lists of dictionary maps `[{"ip": "...", "port": ...}]`, each peer is serialized as exactly 6 contiguous bytes: 4 bytes for the IPv4 address (in network byte order) and 2 bytes for the port (big-endian unsigned 16-bit integer). This reduces payload size from ~50 bytes per peer to 6 bytes.

## What breaks it (failure modes)
- Sending hexadecimal info hash instead of raw URL-encoded 20 bytes — causes the tracker to look up a non-existent 40-byte hash and return an empty peer list or error.
- Text-based URL encoding (`URLEncoder.encode(String, "UTF-8")`) — attempting to convert binary bytes into a Java string before URL-encoding alters bytes that are not valid UTF-8 code points.
- Signed byte overflow in Java — Java bytes are signed (`-128` to `127`). Unmasking IP bytes with `& 0xFF` is mandatory (`(b & 0xFF)`), otherwise negative octets like `165` become `-91`.
- Big-endian port decoding — failing to shift the high byte `((b[4] & 0xFF) << 8) | (b[5] & 0xFF)` results in swapped or incorrect port numbers.

## Tradeoffs
- Compact representation (BEP 23) vs Dictionary list — Compact format saves >85% bandwidth and reduces tracker CPU overhead, but is restricted to IPv4 addresses (IPv6 requires BEP 7 compact format with 18 bytes per peer).
- HTTP Trackers vs UDP Trackers (BEP 15) / DHT (BEP 5) — HTTP trackers run over standard web infrastructure and easily traverse corporate proxies, but UDP trackers and DHT are much lower overhead and avoid single points of failure.

## Wire format / protocol
### Tracker Announce Request:
`GET /announce?info_hash=%d6%9f%91...&peer_id=00112233445566778899&port=6881&uploaded=0&downloaded=0&left=92063&compact=1 HTTP/1.1`

### Compact Peer Encoding (6 bytes per peer):
```
[ Byte 0 ] [ Byte 1 ] [ Byte 2 ] [ Byte 3 ] [ Byte 4 ] [ Byte 5 ]
<------------- IPv4 Address -------------> <--- Port (Big-Endian) --->
       165   .    232   .     38   .    164       (0xC8 << 8) | 0xE9 = 51433
```

## Java specifics - lookup, do not memorize
- `HttpClient.newHttpClient()` — immutable, thread-safe HTTP client introduced in Java 11.
- `HttpRequest.newBuilder().uri(URI.create(url)).GET().build()` — builds an HTTP GET request.
- `client.send(request, HttpResponse.BodyHandlers.ofByteArray())` — sends synchronous HTTP request and returns response body as `byte[]`.
- `(b & 0xFF)` — bitwise AND with `0xFF` promoting signed `byte` to unsigned `int`.
