# Stage 11: Download the whole file

## In one line
Orchestrated multi-piece downloads over persistent peer TCP connections, verified cryptographic integrity for each chunk, and reassembled all pieces into the complete target file.

## The problem it solved
Downloading a single piece yields only an isolated fragment of the target resource. To deliver the final file to the user, a BitTorrent client must iterate over all piece indices, systematically request and verify every piece against its corresponding SHA-1 hash in `pieces`, and stitch them into a contiguous binary file on disk.

## Concepts (the transferable part)
- **Persistent Binary Streaming**: Opening and tearing down TCP connections per chunk introduces connection handshake and slow-start penalties. Maintaining an open socket to an unchoked peer allows continuous back-to-back block pipelining.
- **Failover / Peer Fallback**: If a peer disconnects, throttles, or sends invalid blocks that fail SHA-1 verification, the client falls back to alternate swarm peers discovered from the tracker.
- **Offset-Based File Assembly**: Pieces are written into `fileData` at byte offset `pieceIndex * pieceLength`, ensuring the final file is byte-for-byte identical to the original torrent payload.

## What breaks it (failure modes)
- Truncating or padding the final piece — the final piece is usually smaller than `piece length`; copying `piece length` bytes for the final piece corrupts memory bounds or appends garbage bytes.
- Reusing static `peer_id`s across connections — test trackers and peers track client IDs; collisions trigger "Connection reset by peer". Generating random peer IDs per session resolves this.
- Out-of-order piece writing without byte offsets — appending pieces to a stream instead of positioning at `pieceIndex * pieceLength` will scramble files if pieces are fetched out of order.

## Tradeoffs
- In-memory Assembly vs RandomAccessFile — For smaller files (<100 MB), buffering the whole file in memory (`byte[]`) is simple and fast. For multi-gigabyte torrents, memory-mapped files (`FileChannel.map`) or sparse disk files (`RandomAccessFile.seek`) prevent `OutOfMemoryError`.
- Single-Peer vs Multi-Peer Swarming — Downloading sequentially from one peer minimizes state tracking, while a work queue distributing pieces across multiple concurrent peers maximizes aggregate bandwidth.

## Wire format / protocol
The protocol exchanges standard BitTorrent peer wire messages over a single stateful TCP session:
```
Client -> Peer: Handshake (68 bytes)
Peer -> Client: Handshake (68 bytes)
Client -> Peer: Interested (ID 2)
Peer -> Client: Unchoke (ID 1)
[Repeat for each piece]:
  [Repeat for each 16 KiB block]:
    Client -> Peer: Request (ID 6, index, begin, length)
    Peer -> Client: Piece (ID 7, index, begin, data)
  Verify SHA-1(piece) == expectedHash
```

## Java specifics - lookup, do not memorize
- `System.arraycopy(pieceData, 0, fullFile, (int) (pieceIndex * pieceLength), pieceSize)` — fast array block copying.
- `Files.write(Path.of(outputPath), fullFile)` — writes entire byte array to disk in a single atomic call.
- `String.format("-PC0001-%012d", System.currentTimeMillis() % 1000000000000L)` — generates randomized 20-character client peer IDs.
