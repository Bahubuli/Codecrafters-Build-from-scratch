# Stage 16: Request metadata

## In one line
Sent BEP 9 metadata extension request message (`id = 20`, `extended_id = <peer_ut_metadata_id>`) containing bencoded dictionary `{"msg_type": 0, "piece": 0}` to fetch torrent metainfo.

## Self-test (cover the answers below and answer these first)
- What is the difference between BitTorrent base protocol piece requests (`id = 6`) and BEP 9 metadata piece requests (`id = 20`)?
- What are the three `msg_type` values defined by BEP 9 metadata extension?
- Why is the extension message ID in the metadata request message set to the peer's `ut_metadata` ID rather than `0` or our local ID?

## The problem it solved
Magnet links omit torrent metainfo dictionaries (file names, file length, piece length, piece SHA-1 hashes). To reconstruct the torrent file and download data pieces, clients must retrieve this metadata dictionary from peers over the wire using the BEP 9 extension sub-protocol.

## Concepts (the transferable part)
- **Sub-Protocol Message Multiplexing**: Inside the BEP 10 outer container (`id = 20`), the second byte (`extended_id`) identifies the sub-protocol. For metadata exchange, this ID is the one negotiated in the extension handshake.
- **BEP 9 Metadata Message Types**:
  - `0`: `request` \u2014 requests a metadata piece (`{"msg_type": 0, "piece": <n>}`).
  - `1`: `data` \u2014 transmits metadata payload (`{"msg_type": 1, "piece": <n>, "total_size": <bytes>}`).
  - `2`: `reject` \u2014 denies metadata request (`{"msg_type": 2, "piece": <n>}`).
- **Metadata Piece Granularity**: Metadata is chunked into 16 KiB blocks. In this challenge, metadata fits within a single piece (`piece: 0`).

## What breaks it (failure modes)
- Using our own local `ut_metadata` ID instead of the peer's announced ID in the request packet \u2014 peer drops the request as unrecognized.
- Malformed bencode dictionary order \u2014 dictionary keys must be lexicographically sorted (`msg_type` before `piece`).
- Failing to read bitfield before extension messaging \u2014 protocol state misalignment desynchronizes TCP stream buffers.

## Tradeoffs
- Out-of-band metadata (.torrent file) vs In-band metadata exchange (BEP 9) \u2014 Magnet links are compact and easily shared via URIs, but require dynamic discovery and multi-step TCP handshake negotiation before downloading can commence.

## Wire format / protocol
BEP 9 Metadata Extension Request Message:
```
[Length Prefix: 4 bytes] (Big-endian uint32 = 1 + 1 + len(dict))
[Message ID: 1 byte = 20]
[Extension Message ID: 1 byte = peer_ut_metadata_id]
[Bencoded Payload: variable bytes]
  d8:msg_typei0e6:piecei0ee
```

## Java specifics - lookup, do not memorize
- `ByteBuffer.allocate(4 + 1 + reqPayloadLen)` \u2014 allocates buffer for wire framing.
- `metaReqMsg.put((byte) peerUtMetadataId)` \u2014 dynamically sets the target extension ID.

## Rebuild checklist
- [ ] Connect TCP socket and exchange 68-byte handshakes.
- [ ] Read bitfield message.
- [ ] Send BEP 10 extension handshake (`m: {ut_metadata: 16}`).
- [ ] Read peer extension handshake and extract `peer_ut_metadata_id`.
- [ ] Build metadata request packet with `id = 20`, `ext_id = peer_ut_metadata_id`, and `d8:msg_typei0e6:piecei0ee`.
- [ ] Transmit metadata request over socket.
