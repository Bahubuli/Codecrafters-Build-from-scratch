# Stage 18: Download a piece

## In one line
Integrated BEP 9 metadata resolution with the block download pipeline to fetch, assemble, and cryptographically verify an individual piece directly from a magnet link URI.

## The problem it solved
Unlike `.torrent` files that contain static metainfo on disk, a magnet link only supplies an info hash and tracker URL. In order to download a specific piece, the client must first dynamically negotiate with the tracker to find peers, perform extension handshakes (BEP 10 / BEP 9) to retrieve the raw `info` dictionary, calculate chunk sizes, express interest, wait for unchoke, and finally issue 16 KiB block `request` messages.

## Concepts (the transferable part)
- **Unified Handshake & Metadata Pipeline**: Establishing a TCP connection, conducting the 68-byte BitTorrent handshake with extension bit set (`reserved[5] |= 0x10`), executing the extension handshake (BEP 10), requesting metadata (BEP 9), and receiving the `info` dictionary.
- **Connection Continuity**: Rather than tearing down the connection after metadata extraction, the client keeps the socket open, transitions into the standard data transfer protocol state by sending `interested` (ID 2), and waits for `unchoke` (ID 1).
- **Sub-Piece Block Reassembly**: Pieces are partitioned into 16 KiB ($2^{14}$ bytes) blocks. The client requests blocks using `<id=6><index><begin><length>`, collects `<id=7><index><begin><block>` payloads, and writes each block to memory.
- **Cryptographic Verification**: Assembled pieces are validated using SHA-1 hashing against the corresponding 20-byte hash slice extracted from the newly fetched metadata.

## What breaks it (failure modes)
- Closing the socket after metadata download — reconnecting from scratch incurs unnecessary TCP handshake, BitTorrent handshake, and tracker latency. Reusing the open connection is faster and prevents peer rate limiting.
- Ignoring unchoke state — issuing block requests before receiving `unchoke` (ID 1) causes peers to ignore requests or terminate the connection.
- Reading partial TCP frames — TCP delivers stream segments. Relying on single `read()` calls without reading the exact expected message length leads to malformed block assembly.

## Tradeoffs
- Reusing metadata socket vs Multi-peer pooling — For single piece retrieval, reusing the socket that just delivered metadata minimizes connection overhead. For whole-file multi-piece downloads, spreading pieces across multiple peers maximizes throughput.
- In-memory assembly vs Incremental disk writes — Buffering the piece in memory allows SHA-1 verification before saving to disk, preventing corrupt blocks from being written to persistent storage.

## Wire format / protocol
Data Exchange Flow after BEP 9 Metadata Retrieval:
```
Client -> Peer: Interested [0, 0, 0, 1, 2]
Peer -> Client: Unchoke    [0, 0, 0, 1, 1]
Client -> Peer: Request    [0, 0, 0, 13] [6] [4-byte pieceIndex] [4-byte begin] [4-byte length]
Peer -> Client: Piece      [4-byte len]  [7] [4-byte pieceIndex] [4-byte begin] [block data...]
```

## Java specifics - lookup, do not memorize
- `ByteBuffer.allocate(17).putInt(13).put((byte)6).putInt(pieceIndex).putInt(begin).putInt(blockLen)` — packs binary big-endian block request frames.
- `MessageDigest.getInstance("SHA-1").digest(pieceData)` — calculates SHA-1 digest over the reassembled piece.
- `Files.write(outPath, pieceData)` — atomically writes the verified piece byte buffer to the target file.

## Rebuild checklist
- [ ] Parse magnet URI parameters (`xt`, `tr`).
- [ ] Query tracker to obtain peer IP:port list.
- [ ] Connect TCP socket to peer with extension bit enabled (`0x10` at byte 25).
- [ ] Perform BEP 10 extension handshake and BEP 9 metadata request.
- [ ] Parse bencoded `info` dictionary to extract `length`, `piece length`, and `pieces`.
- [ ] Calculate target piece size handling the last piece boundary.
- [ ] Send `interested` message (ID 2) and wait for `unchoke` (ID 1).
- [ ] Request piece in 16 KiB blocks and assemble into byte buffer.
- [ ] Verify SHA-1 hash of assembled piece against metadata `pieces`.
- [ ] Save piece to disk at `-o <output_path>` and print success confirmation.
