# Stage 19: Download the whole file

## In one line
Resolved complete metadata via BEP 9, established unchoked streaming sessions with peers, systematically downloaded and SHA-1-verified all sequential pieces, and concatenated them to reconstruct the full file.

## The problem it solved
To download an entire file from a magnet link URI, a BitTorrent client must execute the entire protocol stack: query the tracker, establish TCP connections, announce and negotiate extension protocols, retrieve the full metainfo dictionary, compute total pieces and chunk boundaries, maintain persistent unchoked peer states, sequentially download 16 KiB blocks for every piece, cryptographically verify each piece's SHA-1 digest, and write the contiguous payload to disk.

## Concepts (the transferable part)
- **End-to-End Magnet Architecture**: Combining URI parsing, tracker discovery, BEP 10/9 metadata resolution, and BitTorrent chunk streaming into a unified automated pipeline.
- **Sequential Block Pipelining Over Persistent Streams**: Keeping the peer socket open across piece boundaries avoids repeating TCP handshakes, BitTorrent handshakes, and choking transitions.
- **Piece Concatenation & Offset Tracking**: Writing pieces into a buffer at `pieceIndex * pieceLength` guarantees deterministic byte ordering and exact file sizing regardless of chunk arrival order.
- **Cryptographic File Integrity**: Validating each assembled piece against its corresponding 20-byte slice in the metadata `pieces` array ensures corrupt blocks never poison the final output.

## What breaks it (failure modes)
- Final piece size overflow — the final piece is typically smaller than `piece length`. Requesting the full `piece length` for the last chunk causes peer disconnects or file size corruption.
- Premature socket timeout on large files — downloading a multi-megabyte file sequentially across multiple pieces requires adequate socket read timeouts (`setSoTimeout(60000)`).
- Failing to create destination parent directories — `Files.write(outPath, fullFile)` throws `NoSuchFileException` if parent directories are missing.

## Tradeoffs
- Single socket reuse vs Peer swarming — Downloading all pieces through one peer is simple and reliable for moderate file sizes, while swarming across multiple peers with a work queue provides maximum throughput on large files.
- In-memory accumulation vs Memory-mapped files — Storing the full file in a contiguous `byte[]` buffer simplifies verification and atomic disk writes for files within memory limits.

## Wire format / protocol
Full Protocol Pipeline:
```
Magnet Link -> HTTP Tracker GET -> Peer List
TCP Connect -> Handshake (Ext bit 0x10) -> Peer Handshake
-> BEP 10 Handshake -> Peer Ext Handshake
-> BEP 9 Metadata Request -> Peer Metadata Data -> Info Dict Parsed
-> Interested (ID 2) -> Unchoke (ID 1)
-> For piece 0..N-1:
     For block 0..M-1:
       Request (ID 6, index, begin, len) -> Piece (ID 7, index, begin, data)
     Verify SHA-1(piece) == expectedHash
     Copy piece to fullFile[index * pieceLength]
-> Write fullFile to disk
```

## Java specifics - lookup, do not memorize
- `int totalPieces = (int) Math.ceil((double) meta.totalLength / meta.pieceLength)` — calculates total pieces.
- `System.arraycopy(pieceData, 0, fullFile, (int) (pieceIndex * meta.pieceLength), pieceSize)` — copies piece data into full file buffer.
- `Files.write(outPath, fullFile)` — writes full file bytes to destination path.
