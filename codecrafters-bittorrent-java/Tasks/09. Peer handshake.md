# Stage 09: Peer handshake

## In one line
Initiated a TCP connection to a swarm peer and exchanged the fixed 68-byte BitTorrent handshake to authenticate mutual interest in the torrent.

## Self-test (cover the answers below and answer these first)
- What are the five fields that constitute the 68-byte BitTorrent handshake message?

## The problem it solved
Discovering peer IP:Port endpoints is insufficient to start exchanging data; a client must establish a stateful TCP connection and verify that the remote peer is actually serving the intended swarm. The 68-byte peer wire handshake confirms the protocol version, the target `info_hash`, and assigns peer identities before any piece transfer messages occur.

## Concepts (the transferable part)
- **Binary Session Handshaking**: Connection-oriented binary protocols begin with a fixed-layout synchronization frame validating protocol version and shared session context (here, `info_hash`) before dynamic-length messaging starts.
- **Protocol Magic / Length-Prefixed Header**: Handshake starts with length byte `19` followed by protocol identifier ASCII string `"BitTorrent protocol"`, allowing network sniffers or servers to identify and demux protocol traffic cleanly.
- **Reserved Bitfield Extensions**: 8 reserved bytes (bytes 20..27) serve as a flags field for negotiating protocol extensions (e.g. BEP 10 extension protocol, DHT, fast discovery).

## What breaks it (failure modes)
- Info hash mismatch — if the client sends an info hash that the peer is not currently seeding/leeching, the peer drops the TCP connection immediately.
- Partial reads on TCP stream — calling `socket.getInputStream().read(byte[])` may return fewer than 68 bytes if packets are fragmented across network frames. Using `readNBytes(68)` ensures all 68 bytes are fully accumulated.
- Forgetting to flush socket output stream — buffered bytes remain in the client's output buffer; the peer never receives the handshake and hangs.
- Incorrect buffer offsets — off-by-one errors when copying the 20-byte `info_hash` or `peer_id` corrupts the handshake.

## Tradeoffs
- Fixed 68-byte initial framing vs Dynamic framing — The handshake is intentionally non-bencoded and fixed-length (68 bytes) to allow extremely fast hardware/software parsing and protocol detection without running a deserializer.
- Ephemeral vs Persistent Peer IDs — Clients may generate random peer IDs per session or per peer connection to enhance user privacy against swarm tracking.

## Wire format / protocol
Total size: exactly 68 bytes
```
[1 byte]  pstrlen = 19 (0x13)
[19 bytes] pstr = "BitTorrent protocol"
[8 bytes]  reserved = 0x00 0x00 0x00 0x00 0x00 0x00 0x00 0x00
[20 bytes] info_hash (raw binary SHA-1)
[20 bytes] peer_id (raw binary client ID)
```

## Java specifics - lookup, do not memorize
- `Socket socket = new Socket(ip, port)` — establishes TCP socket connection.
- `InputStream.readNBytes(int n)` — reads up to `n` bytes from the input stream, blocking until all `n` bytes are read or EOF is reached.
- `System.arraycopy(src, srcPos, dest, destPos, length)` — high-performance native memory copy between byte arrays.
