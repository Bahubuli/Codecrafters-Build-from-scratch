# Stage 03: Decode bencoded lists

## In one line
Decoded delimiter-bracketed bencoded heterogeneous lists formatted as `l<elements>e` into JSON arrays using recursive parsing.

## Self-test (cover the answers below and answer these first)
- How does Bencode represent lists and delineate individual list elements without item separators?
- Why is recursive descent parsing natural for Bencode lists?
- How does the parser differentiate between the closing delimiter `e` of an integer vs the closing delimiter `e` of a list?

## The problem it solved
Complex protocol data structures (such as tracker announce multi-tier lists, peer lists, and torrent file file-lists) require serializing ordered, heterogeneous sequences. Bencode frames sequences with a starting `l` and terminating `e` (`l<elements>e`) without any commas or delimiters between elements, relying on self-delimiting child tokens.

## Concepts (the transferable part)
- **Self-Delimiting Element Streams**: In Bencode, every data type (string, integer, list, dict) encodes its own boundary (length prefix or `e` sentinel). Because elements are self-delimiting, lists require no separators (e.g., no commas or spaces) between items.
- **Recursive Descent Deserialization**: Since lists can contain arbitrary bencoded values including other nested lists, calling the central `parse()` method recursively consumes each token and naturally constructs nested tree structures.
- **Ambiguity-Free Grammar**: Even though both integers (`i...e`) and lists (`l...e`) end with the ASCII character `e`, every sub-parser consumes its own terminating `e`, ensuring the outer list loop encounters only the `e` belonging to the list itself.

## What breaks it (failure modes)
- Truncated lists without the terminating `e` — scanning proceeds past the end of the input string, throwing index out-of-bounds exceptions unless guarded.
- Empty lists (`le`) — the loop must handle immediate termination without attempting to parse an element.
- Nested structures exceeding recursion limits — deeply nested lists can cause stack overflow if parsing depth is not bounded in hostile environments.
- Malformed inner element — errors inside nested elements must bubble up clearly without leaving the parser in an ambiguous state.

## Tradeoffs
- Recursive descent vs iterative state machine — Recursive descent is clean, expressive, and directly mirrors grammar rules, but consumes call stack frames for each nesting level; an iterative parser using an explicit stack prevents stack overflows at the cost of boilerplate.
- Heterogeneous `List<Object>` vs strongly-typed AST nodes — `List<Object>` pairs effortlessly with dynamic JSON serializers (like Gson) for simple CLI decoding, but requires type casting when extracting specific fields in later stages.

## Wire format / protocol
`le` -> `[]`  
`l5:helloi52ee` -> `["hello", 52]`  
`lli42eee` -> `[[42]]`  
`l<bencoded_element_1><bencoded_element_2>...e`

## Java specifics - lookup, do not memorize
- `List<Object> list = new ArrayList<>()` — resizable array implementation of the `List` interface.
- `src.charAt(index)` — retrieves char at current index in O(1).
- `Gson.toJson(list)` — recursively serializes Java collections and primitives into standard JSON arrays.
