# Stage 14: Send extension handshake

## In one line
Sent BEP 10 extension handshake message (`id = 20`, `extended_id = 0`) containing bencoded dictionary `{"m": {"ut_metadata": 16}}` after receiving peer handshake and bitfield message.

## Self-test (cover the answers below and answer these first)
- What is the outer message ID for all BitTorrent extension protocol messages (BEP 10)?
- In the payload of an extension handshake message, what is the extension message ID?
- Why do extension message mappings use an inner dictionary `m` rather than a global fixed ID assignment across all peers?

## The problem it solved
Once two peers advertise extension support via bit 20 in the handshake reserved bytes, they must negotiate dynamic message IDs for individual sub-protocols (such as `ut_metadata` in BEP 9 or `ut_pex` in BEP 11). Each peer announces the numeric ID it expects to receive for each supported extension by transmitting an extension handshake message.

## Concepts (the transferable part)
- **Dynamic Protocol Multiplexing**: Rather than reserving global message IDs from the limited standard BitTorrent byte space (`0..19`), BEP 10 multiplexes all extensions under message ID `20`.
- **Peer-Specific ID Negotiation**: Each peer assigns its own local IDs to extensions. When Peer A sends a `ut_metadata` request to Peer B, Peer A must use the ID that Peer B mapped `ut_metadata` to in Peer B's extension handshake.
- **Handshake Payload Structure**:
  - Message ID: `20` (extension).
  - Extension Message ID: `0` (handshake).
  - Bencoded dictionary: `{"m": {"ut_metadata": <id>}}` (where `<id>` is a non-zero byte `1..255`).

## What breaks it (failure modes)
- Sending extension handshake before reading the peer's initial bitfield message \u2014 peers typically send their bitfield immediately after the 68-byte handshake; failing to read or handle the bitfield first causes synchronization failures.
- Sending extension handshake to a peer that did not advertise extension support \u2014 violating backwards compatibility causes legacy peers to disconnect.
- Miscalculating message length prefix \u2014 length prefix must equal `1 (msg_id: 20) + 1 (ext_id: 0) + len(bencoded_dict)`.

## Tradeoffs
- Static ID Mapping vs Dynamic Negotiation \u2014 Dynamic negotiation requires an extra handshake step, but prevents ID conflicts between independently developed community extensions.

## Wire format / protocol
Extension Handshake Message:
```
[Length Prefix: 4 bytes] (e.g. 1 + 1 + 25 = 27 = 0x0000001B)
[Message ID: 1 byte = 20]
[Extension Message ID: 1 byte = 0]
[Bencoded Payload: variable bytes]
  d1:md11:ut_metadatai16eee
```

## Java specifics - lookup, do not memorize
- `ByteBuffer.allocate(4 + 1 + 1 + dictBytes.length)` \u2014 builds binary wire packet with length prefix, message id, and payload.
