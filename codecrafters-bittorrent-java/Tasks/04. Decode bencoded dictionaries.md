# Stage 04: Decode bencoded dictionaries

## In one line
Decoded delimiter-bracketed key-value mappings formatted as `d<key1><val1>...e` into JSON objects using alternating string-key and arbitrary-value recursive parsing.

## Self-test (cover the answers below and answer these first)
- What constraint does Bencode enforce on dictionary keys?
- Why must dictionary keys be sorted lexicographically in raw Bencode?
- How does the parser distinguish between the end of an inner value and the terminating `e` of the dictionary?

## The problem it solved
BitTorrent metainfo files (.torrent) and tracker responses represent structured key-value configurations (such as announce URLs, piece length, info dictionaries, and file metadata). Bencode frames dictionaries with opening `d` and closing `e` delimiters (`d<k1><v1>...e`), where keys must be byte strings sorted lexicographically.

## Concepts (the transferable part)
- **Alternating Key-Value Streaming**: Bencode dictionaries do not use colons or commas between keys and values. The parser alternates between strictly reading a bencoded string for the key, followed by recursively deserializing an arbitrary bencoded value (`parse()`).
- **Canonical Serialization & Determinism**: For cryptographic hashing (e.g. info-hash calculation), bencode requires dictionary keys to be sorted lexicographically. Preserving order using `LinkedHashMap` ensures deterministic serialization when inspecting or re-encoding.
- **Heterogeneous Recursive Trees**: Dictionaries can contain lists, integers, strings, and other nested dictionaries, completing the core bencode specification (the four BEP 3 primitive types).

## What breaks it (failure modes)
- Non-string keys — Bencode strictly requires keys to be strings (`<len>:<str>`); an integer or list encountered in the key position violates the specification.
- Unpaired keys (odd number of elements before `e`) — causes an unexpected end of input or parser crash.
- Missing terminating `e` — causes the parser to read past the end of the input stream.
- Duplicate or out-of-order keys — canonical bencode mandates unique keys in lexicographical order.

## Tradeoffs
- `LinkedHashMap` vs `TreeMap` — `LinkedHashMap` preserves the exact key order as decoded from the wire (beneficial for zero-modification roundtrips), whereas `TreeMap` enforces sorting in-memory regardless of input wire order.
- In-memory Object Map vs Streaming SAX-like Events — Building an in-memory `Map<String, Object>` is intuitive and easy to convert to JSON via Gson, but requires memory proportional to the entire dictionary size (which is modest for torrent metainfo, usually < few MB).

## Wire format / protocol
`de` -> `{}`  
`d3:foo3:bar5:helloi52ee` -> `{"foo":"bar","hello":52}`  
`d<key_string_1><bencoded_value_1><key_string_2><bencoded_value_2>...e`

## Java specifics - lookup, do not memorize
- `Map<String, Object> map = new LinkedHashMap<>()` — hash table and linked list implementation of `Map`, preserving insertion order.
- `map.put(key, value)` — associates the specified key with the specified value in the map.
- `Gson.toJson(Map)` — serializes key-value maps directly to standard JSON objects `{ "k": v }`.

## Rebuild checklist
- [ ] Detect leading `d` marker indicating a dictionary.
- [ ] Advance cursor past `d`.
- [ ] Loop while cursor has not reached terminating `e`:
  - [ ] Parse string key via `parseString()`.
  - [ ] Parse associated value via `parse()`.
  - [ ] Insert pair into `LinkedHashMap`.
- [ ] Consume terminating `e` and return the map.
