# Stage 15: Receive extension handshake

## In one line
Received and parsed the peer's BEP 10 extension handshake message (`id = 20`, `extended_id = 0`), extracting the peer's dynamic `ut_metadata` ID from its bencoded `m` dictionary.

## Self-test (cover the answers below and answer these first)
- Why must the peer's `ut_metadata` ID be dynamically extracted from the extension handshake rather than using the ID we transmitted in our own handshake?
- What is the structure of an incoming extension handshake wire packet?
- How is the bencoded dictionary extracted from the raw extension message payload?

## The problem it solved
Extension IDs are locally assigned by each peer independently. When Peer A assigns `ut_metadata: 16` and Peer B assigns `ut_metadata: 2`, any message Peer A sends to Peer B targeting the `ut_metadata` extension MUST use Peer B's ID (`2`), while Peer B sends requests to Peer A using Peer A's ID (`16`). To communicate via `ut_metadata`, our client must parse the peer's extension handshake dictionary and record its assigned extension ID.

## Concepts (the transferable part)
- **Asymmetric Dynamic ID Negotiation**: In peer-to-peer protocols with pluggable extensions, neither peer dictates the global ID mapping. Each peer informs the other which ID to use when addressing that specific extension.
- **Nested Bencoded Dict Traversal**: The extension handshake payload starts with a 1-byte extension message ID (`0` for handshake), followed immediately by the raw bencoded dictionary containing metadata capabilities:
  `{"m": {"ut_metadata": <id>, ...}}`.
- **Parsing Slices**: Slicing `payload[1..len]` cleanly strips the 1-byte extension ID header, leaving valid bencoded dictionary bytes parseable by standard bencode decoders.

## What breaks it (failure modes)
- Assuming peer extension ID equals our local extension ID \u2014 hardcoding `16` breaks communication with any standard BitTorrent client or test harness that selects a random ID.
- Off-by-one payload slicing \u2014 feeding `payload[0..len]` into the bencode parser fails immediately because byte 0 is binary `0x00`, not the dictionary start token `'d'`.
- Missing extension dictionary key \u2014 checking `mDict.containsKey("ut_metadata")` prevents `NullPointerException` when connecting to peers that support BEP 10 but do not implement `ut_metadata`.

## Tradeoffs
- Parsing On-the-fly vs Predefined Schema \u2014 Generic bencode dictionary parsing handles arbitrary unexpected extension keys (`ut_pex`, `metadata_size`, etc.) without schema breakage.

## Wire format / protocol
Incoming Extension Handshake Message:
```
[Length Prefix: 4 bytes] (Big-endian uint32 = 1 + 1 + len(dict))
[Message ID: 1 byte = 20]
[Extension Message ID: 1 byte = 0 (handshake)]
[Bencoded Payload: variable bytes]
  d1:md11:ut_metadatai<ID>eee
```

## Java specifics - lookup, do not memorize
- `Arrays.copyOfRange(extResp.payload, 1, extResp.payload.length)` \u2014 extracts raw bencoded dictionary bytes following the 1-byte extension message ID.
