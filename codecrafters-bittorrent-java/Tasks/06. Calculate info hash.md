# Stage 06: Calculate info hash

## In one line
Extracted the raw bencoded `info` dictionary bytes, calculated its 20-byte SHA-1 digest, and formatted the info-hash as a 40-character hexadecimal string.

## The problem it solved
BitTorrent swarms require a globally unique, tamper-evident identifier to register torrents with trackers and identify peers possessing the exact same files. The protocol defines this identifier as the 20-byte SHA-1 cryptographic digest of the bencoded `info` dictionary, ensuring any modification to file contents, sizes, or piece boundaries alters the hash.

## Concepts (the transferable part)
- **Cryptographic Content Addressing**: By addressing content via the cryptographic hash of its metainfo description (`info_hash`), the network achieves integrity verification and deduplication without depending on human-assigned names or tracker URLs.
- **Zero-Loss Source Slicing**: Bencode serialization rules mandate strict lexicographical key ordering and specific integer/string layouts. Slicing the exact byte range of the `info` dictionary directly from the source payload during parsing avoids subtle re-encoding bugs (such as altered key ordering or whitespace discrepancies).
- **Hexadecimal Digest Formatting**: Cryptographic digests produce raw binary byte arrays (20 bytes for SHA-1). Rendering binary digests for CLI and logs requires converting each unsigned byte into a two-digit lowercase base-16 string (`%02x`).

## What breaks it (failure modes)
- Re-serializing the in-memory `Map` with non-canonical bencoding — produces a different byte sequence and thus a completely wrong SHA-1 hash.
- Charset encoding alterations (UTF-8 transcoding) — modifying byte representations of binary piece hashes corrupts the resulting SHA-1 hash.
- Off-by-one errors in byte slicing — omitting the opening `d` or trailing `e` of the info dictionary produces an invalid hash.
- Incorrect hex formatting (e.g. `%x` instead of `%02x`) — strips leading zeros from bytes `< 0x10`, resulting in a malformed string with fewer than 40 hex characters.

## Tradeoffs
- Direct byte slicing vs Re-encoding `info` — Direct byte slicing guarantees exact canonical byte preservation in O(1) time without writing a bencode encoder; re-encoding is only required when dynamically creating or mutating torrents.
- SHA-1 vs Modern Hash Functions (SHA-256) — BitTorrent BEP 0003 was designed when SHA-1 was the standard; while collision attacks exist for SHA-1, BitTorrent swarms continue using 20-byte SHA-1 for backward compatibility across millions of clients (BitTorrent v2 later introduced SHA-256).

## Wire format / protocol
```
Raw info dictionary slice:
d6:lengthi92063e4:name10:sample.txt12:piece lengthi32768e6:pieces60:...e

SHA-1 Digest (20 bytes):
[0xd6, 0x9f, 0x91, 0xe6, 0xb2, 0xae, 0x4c, 0x54, 0x24, 0x68, 0xd1, 0x07, 0x3a, 0x71, 0xd4, 0xea, 0x13, 0x87, 0x9a, 0x7f]

Hexadecimal Representation (40 chars):
d69f91e6b2ae4c542468d1073a71d4ea13879a7f
```

## Java specifics - lookup, do not memorize
- `MessageDigest.getInstance("SHA-1")` — creates a cryptographic message digest instance for SHA-1.
- `md.digest(byte[])` — completes the hash computation by performing final operations and returning the 20-byte digest.
- `String.format("%02x", b)` — formats a byte as a two-digit hexadecimal string padded with leading zero if necessary.
