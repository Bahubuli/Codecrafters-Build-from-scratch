## The problem it solved
Downloading large files over untrusted P2P swarms is vulnerable to bit rot, network corruption, and malicious peers sending corrupted blocks. Rather than waiting until the entire multi-gigabyte download completes to verify integrity (where any error invalidates everything), BitTorrent splits files into pieces (e.g. 256 KiB - 1 MiB) with individual SHA-1 hashes. Corrupted pieces can be detected and re-downloaded immediately in isolation.

## Concepts (the transferable part)
- **Chunked Integrity Verification (Merkle Trees / Piecewise Hashes)**: Partitioning large datasets into fixed-size chunks verified by independent cryptographic hashes enables fault isolation, progressive verification, and pipelined verification while transfers are active.
- **Packed Binary Hashes**: Rather than incurring the framing overhead of a bencoded list of strings (e.g. `l40:<hex>...e`), Bencode packs piece hashes into a single contiguous byte string of length $N \times 20$, minimizing metainfo torrent file overhead.
- **Fixed-Width Binary Slicing**: Stepping through a byte array with a fixed step size (`step = 20`) to extract fixed-size records.

## What breaks it (failure modes)
- Not a multiple of 20 bytes — if `pieces.length % 20 != 0`, the torrent file is malformed.
- Slicing out of bounds — using an incorrect increment or loop bound crashes with `ArrayIndexOutOfBoundsException`.
- String-encoding the pieces — decoding the raw 20-byte hashes into Java strings with UTF-8 replaces unassigned byte sequences with `\uFFFD`, corrupting the hash comparison.
- Last piece size mismatch — the last piece in a torrent is typically smaller than `piece length` (equal to `length % piece length`); however, its SHA-1 hash in `pieces` is still exactly 20 bytes.

## Tradeoffs
- Concatenated 20-byte string vs Bencoded list of hashes — A concatenated binary string saves approximately 50% space compared to list of hex strings (`20` bytes per piece vs `43` bytes `40:<hex>`), keeping `.torrent` files compact.
- Fixed piece size vs Variable piece size — Fixed piece size simplifies indexing and block requests across peers, though the final piece requires bounds handling.

## Wire format / protocol
In `info` dictionary:
```
12:piece length -> i32768e (32 KiB)
6:pieces -> 60:<20-byte hash 0><20-byte hash 1><20-byte hash 2>
```
Total piece count = `pieces.length / 20`.

## Java specifics - lookup, do not memorize
- `Arrays.copyOfRange(pieces, i, i + 20)` — extracts a 20-byte slice from the byte array.
- Loop stepping by 20: `for (int i = 0; i < pieces.length; i += 20)` — iterates through each 20-byte boundary.
