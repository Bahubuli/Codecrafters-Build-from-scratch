# Stage 13: Announce extension support

## In one line
Announced BitTorrent Extension Protocol (BEP 10) capability during peer handshake by flipping the 20th bit from the right in the 8-byte reserved field.

## Self-test (cover the answers below and answer these first)
- In the 68-byte BitTorrent handshake, where are the 8 reserved bytes located, and which byte index corresponds to the 20th bit from the right?
- Why did BitTorrent design extensions (BEP 10) into the reserved handshake bytes instead of changing the protocol identifier?
- How does a client discover peers when only given a magnet link without file length?

## The problem it solved
Standard BitTorrent handshakes assume all peers only speak the baseline wire protocol. To exchange magnet link metadata (BEP 9), peers must first negotiate mutual support for the BitTorrent Extension Protocol (BEP 10). Rather than breaking backwards compatibility with existing clients, BEP 10 utilizes the 8 reserved bytes in the initial handshake message as a capability bitmask.

## Concepts (the transferable part)
- **Feature Negotiation via Reserved Bitmasks**: Protocol designers frequently reserve unused bitfields for future extensibility. Setting bit 20 from the right ($2^{20}$) in the 64-bit reserved field signals BEP 10 extension compatibility without modifying protocol framing.
- **Bitwise Layout in Big-Endian Handshake**: The 8 reserved bytes span indices 20 through 27 of the 68-byte handshake. The 20th bit from the right (0-indexed) lives in byte index 5 of the reserved bytes ($20 / 8 = 2$ bytes from the right, with bit offset $20 \pmod 8 = 4$, yielding $2^4 = 0x10$). Handshake offset: $20 + 5 = 25$.
- **Tracker Query for Magnet Swarms**: Without a local `.torrent` file, the file length is unknown upfront. Clients query the tracker endpoint extracted from `tr` with a dummy `left` parameter (e.g. `999` or `0`) along with the parsed `info_hash` to obtain active swarm peers.

## What breaks it (failure modes)
- Setting the wrong reserved byte index — indexing from the wrong direction or confusing bit 20 from the left vs right results in peer ignoring extension messages.
- Sending hex strings instead of raw 20-byte `info_hash` in the handshake — handshake byte slots 28..47 require the binary 20-byte digest, not the 40-character ASCII hex string.
- Zero or missing `left` parameter rejecting tracker queries — some trackers require an integer `left` parameter; supplying a placeholder integer (such as `999`) ensures tracker acceptance.

## Tradeoffs
- Static Handshake Flags vs Dynamic Discovery — Flipping a reserved bit costs zero roundtrips and zero additional framing bytes, whereas separate capabilities negotiation requires additional protocol steps.

## Wire format / protocol
Handshake byte offsets (68 bytes total):
```
Offset  0:       Length of protocol string (1 byte = 19)
Offset  1..19:   Protocol identifier ("BitTorrent protocol")
Offset 20..27:   8 reserved bytes:
                 [00 00 00 00 00 10 00 00]
                                 ^^ (offset 25 = 0x10)
Offset 28..47:   20-byte raw SHA-1 info_hash
Offset 48..67:   20-byte raw client peer_id
```

## Java specifics - lookup, do not memorize
- `handshake[25] = 0x10;` — sets bit 20 from the right ($2^4$ in 6th byte, offset 25) in 68-byte handshake.
- `Integer.parseInt(hex.substring(i * 2, i * 2 + 2), 16)` — parses hexadecimal byte pairs into binary bytes.
