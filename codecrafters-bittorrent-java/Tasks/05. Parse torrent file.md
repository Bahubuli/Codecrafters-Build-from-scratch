# Stage 05: Parse torrent file

## In one line
Parsed single-file `.torrent` metainfo files as raw byte streams to extract tracker announce URLs and file lengths while isolating binary piece data.

## Self-test (cover the answers below and answer these first)
- Why must `.torrent` metainfo files be read as raw byte arrays (`byte[]`) rather than decoded as UTF-8 or UTF-16 strings?
- Where is the file length stored in a single-file torrent versus a multi-file torrent?
- Why is it critical to capture the exact raw byte range of the `info` dictionary during parsing?

## The problem it solved
BitTorrent clients need metainfo files (.torrent) to discover the coordinating tracker and learn essential file characteristics before downloading. Because metainfo files contain raw 20-byte binary SHA-1 piece hashes alongside human-readable metadata, reading the file as text causes encoding corruption. Parsing the file directly as bytes preserves binary fidelity.

## Concepts (the transferable part)
- **Binary-Safe Wire Deserialization**: Network protocols and binary file formats frequently mix ASCII metadata headers with unconstrained binary payloads. Using byte-level parsers (`byte[]` with index offsets) prevents UTF-8 replacement character corruption (`\uFFFD`).
- **BitTorrent Metainfo Structure**: A torrent file is a top-level bencoded dictionary containing `announce` (tracker URL) and `info` (a nested dictionary with `length`, `name`, `piece length`, and `pieces`).
- **Raw Byte Range Preservation**: The cryptographic identifier of a torrent (the `info_hash`) is computed from the SHA-1 digest of the raw bencoded `info` dictionary. Slicing the exact source byte span during the initial parse guarantees a bit-exact match without needing a custom, error-prone bencode serializer.

## What breaks it (failure modes)
- Reading file with `Files.readString` or `FileReader` — invalid UTF-8 byte sequences in `pieces` get silently replaced with `\uFFFD`, corrupting data.
- Missing or malformed keys — accessing `torrent.get("info")` or `info.get("length")` on corrupt files throws `NullPointerException` or `ClassCastException` unless validated.
- Multi-file torrent structures — multi-file torrents specify a `files` list with individual file lengths instead of a single top-level `length` field in `info`.

## Tradeoffs
- Byte-array parser vs String-based parser — Operating on `byte[]` requires manual byte-scanning for delimiters (`:`, `i`, `e`), but is completely binary-safe and zero-copy for binary fields like piece hashes.
- Slicing raw info bytes during parse vs Re-encoding `info` map — Re-encoding requires sorting keys lexicographically and escaping strings identically to the original file; slicing the raw bytes is O(1), faster, and guarantees bit-exact fidelity.

## Wire format / protocol
```
d
  8:announce
  41:http://bittorrent-test-tracker.../announce
  4:info
  d
    6:length
    i92063e
    4:name
    10:sample.txt
    12:piece length
    i32768e
    6:pieces
    60:<binary 20-byte SHA-1 hashes>
  e
e
```

## Java specifics - lookup, do not memorize
- `Files.readAllBytes(Path.of(path))` — reads all bytes from a file into a `byte[]`.
- `Arrays.copyOfRange(byte[] original, int from, int to)` — copies the specified range of the array into a new byte array.
- `StandardCharsets.US_ASCII` / `StandardCharsets.UTF_8` — standard charset constants avoiding string lookups.
