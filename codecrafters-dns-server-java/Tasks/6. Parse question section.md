# Stage 6: Parse question section

## Problem Solved

In Stage 5, the DNS server parsed incoming packet headers to echo transaction identifiers and query flags, but the Question section was either hardcoded or ignored. In standard RFC 1035 DNS communication:
- Resolvers dispatch queries containing one or more domain inquiries in the Question section.
- Resolvers validate DNS responses by verifying that the Question section in the reply exactly mirrors the question (`QNAME`, `QTYPE`, `QCLASS`) of the original query.
- The Answer section records (`RR`) must correspond directly to the domain queried in the Question section.

In this stage, the server dynamically parses the Question section from incoming UDP datagrams, extracts variable-length label sequences, converts them to dot notation domain names, mirrors the parsed questions into the response message, and synthesizes matching `A` record answers pointing to `8.8.8.8` with a TTL of 60 seconds.

## Concepts

- **Dynamic Question Parsing**: Unlike the fixed 12-byte header, the Question section contains variable-length data determined by the domain name label chain. Deserializing requires parsing an arbitrary number of labels until reaching the zero-length root label terminator (`0x00`), followed by two 16-bit fields (`QTYPE` and `QCLASS`).
- **DNS Label Length-Prefix Framing**: DNS domain names on the wire do not use dot separators (`.`) or null-terminated C-strings. Instead, they are encoded as a Pascal-style sequence of length-prefixed labels. Each label begins with a single octet length byte $L$ ($0 \le L \le 63$), followed by exactly $L$ bytes of ASCII characters. The sequence terminates with a single null byte ($L = 0$).
- **Octet-Stream Decoding**: Reading octets sequentially from a contiguous byte buffer. The parser maintains an internal cursor (`ByteBuffer` position), extracting one length octet at a time, reading the slice of characters, and advancing past the final `0x00` root delimiter before reading the trailing 16-bit `QTYPE` and `QCLASS` fields.
- **Domain Reflection & Resource Record Synthesis**: The server reflects the client's query by preserving the requested domain name in both the mirrored Question section and the synthesized Answer section (`NAME`), binding the client's lookup intent to the resolved resource record.

| Field | Size | Type | Value / Description |
|---|---|---|---|
| `QNAME` | Variable | Byte sequence | Domain name formatted as length-prefixed labels ending in `0x00`. |
| `QTYPE` | 2 octets | Big-Endian uint16 | Query record type: `1` corresponds to `A` (IPv4 host address). |
| `QCLASS` | 2 octets | Big-Endian uint16 | Query record class: `1` corresponds to `IN` (Internet). |

## Failure Modes

- **Buffer Underflow on Malformed Labels**: If a label length octet specifies $L = 20$, but only 5 octets remain in the buffer, reading $L$ bytes causes an unchecked `BufferUnderflowException`. Deserialization must ensure `buffer.remaining() >= len` prior to fetching bytes.
- **Label Length > 63 Octets**: RFC 1035 §2.3.4 restricts individual labels to a maximum of 63 octets. The two most significant bits (`0xC0`) are reserved for DNS compression pointers. If a length octet exceeds 63 without the pointer mask, the packet is corrupted.
- **Infinite Loops on Missing Null Byte**: If a malformed packet omits the terminating `0x00` byte, naive parsers looping on `len != 0` overrun buffer boundaries. Parsers must check `buffer.hasRemaining()` on every iteration to guarantee loop termination.
- **Domain Casing & ASCII Preservation**: DNS domain names are case-insensitive, but query reflection conventions dictate that authoritative servers preserve the client's original casing in responses (e.g. `0x20` bit encoding used by resolvers to mitigate spoofing). Lowercasing the domain string during parsing alters wire bytes and can break client validation.

## Tradeoffs

- **Reusing Incoming Question Objects vs Recreating**: Passing the parsed `DnsQuestion` instance directly into the response question list avoids reallocating string objects and re-encoding labels, minimizing garbage collector pressure. Recreating allows sanitizing or normalizing fields if query filtering is needed.
- **Full String Storage vs Raw Byte Offsets**: Storing the domain name as a Java `String` (dot notation like `"codecrafters.io"`) provides high developer ergonomics and clean debugging logs, but requires encoding to/from wire format. Storing raw byte slices or buffer offsets avoids string conversion overhead at the cost of higher complexity during inspection.

## Java Specifics

- `ByteBuffer.get()`: Reads the next single byte at the current position and increments position by 1.
- `Byte.toUnsignedInt(buffer.get())`: In Java, `byte` is a signed 8-bit primitive ($-128$ to $127$). A length octet with high bit set would parse as negative without unsigned conversion. `Byte.toUnsignedInt()` masks with `0xFF` to yield a positive `int` in the range $[0, 255]$.
- `StandardCharsets.US_ASCII`: DNS wire labels are standard ASCII. Using `StandardCharsets.US_ASCII` avoids the overhead and character-mapping ambiguity of platform default encodings when converting label bytes to and from strings.
