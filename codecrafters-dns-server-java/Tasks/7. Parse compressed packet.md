# Stage 7: Parse compressed packet

## Problem Solved

In high-volume DNS traffic and complex multi-record messages, domain names frequently repeat across the Question, Answer, Authority, and Additional sections. To reduce UDP packet size and prevent fragmentation, RFC 1035 §4.1.4 introduces **DNS Message Compression**. 

Instead of repeating the entire sequence of labels, a domain name or a suffix of a domain name can be replaced by a 2-octet pointer that references an earlier occurrence of the domain name within the same DNS message.

In this stage:
- The server receives a DNS query containing multiple questions in the Question section (e.g., Question 1 with an uncompressed label sequence, and Question 2 with a compressed label sequence referencing Question 1).
- The server parses each question, following compression pointers where present to reconstruct the full dot-notation domain name.
- The server responds with all questions mirrored in uncompressed format, followed by corresponding `A` record answers pointing to `8.8.8.8` with a TTL of 60 seconds.

## Concepts

- **DNS Message Compression Pointer**: An octet pair where the two highest-order bits are set to `11` (binary `11xxxxxx`, or hex `0xC0`). The remaining 14 bits represent an unsigned offset from the very beginning of the DNS message (starting at byte 0 of the 12-byte header).
- **Composite Pointer Chaining**: A domain name may consist of initial literal labels followed by a compression pointer (e.g. `\x03def\xC0\x0C` representing `def.<name at offset 12>`). A pointer may even target another pointer, requiring recursive resolution until reaching the `0x00` root label.
- **Buffer Cursor Preservation**: When resolving a compression pointer, the parser must jump to the specified target offset, extract the referenced labels, and subsequently restore the buffer position to the byte immediately following the 2-octet pointer so that subsequent fields are read correctly.
- **Multiple Questions Handling**: Unlike simple DNS lookups with `QDCOUNT = 1`, RFC 1035 allows $QDCOUNT \ge 1$. The parser must sequentially iterate and unpack each question record from the buffer.

## Wire Format / Protocol

### Compression Pointer Encoding (RFC 1035 §4.1.4)

```
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
| 1  1|                OFFSET (14 bits)         |
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
```

- When the first byte $B_1$ has `(B1 & 0xC0) == 0xC0`, it signifies a compression pointer.
- Pointer Offset: `((B1 & 0x3F) << 8) | B2`.
- Offset is absolute from the start of the DNS header (offset `0`).

### Incoming Request Layout with Compression

```
Offset 00..11: DNS Header (QDCOUNT = 2)
Offset 12:     Question 1 Name: \x03abc\x04long\x03com\x00 (uncompressed: "abc.long.com")
               Question 1 Type (2B) + Class (2B)
Offset XX:     Question 2 Name: \x03def\xC0\x10 (points to offset 16 -> "long.com", yielding "def.long.com")
               Question 2 Type (2B) + Class (2B)
```

### Outgoing Response Layout

```
+-------------------------------------------------------------+
| Header: ID=query.ID, QR=1, QDCOUNT=2, ANCOUNT=2, RCODE=0    |
+-------------------------------------------------------------+
| Question 1: "abc.long.com", TYPE A, CLASS IN                |
+-------------------------------------------------------------+
| Question 2: "def.long.com", TYPE A, CLASS IN                |
+-------------------------------------------------------------+
| Answer 1:   "abc.long.com", TYPE A, CLASS IN, TTL=60, IP    |
+-------------------------------------------------------------+
| Answer 2:   "def.long.com", TYPE A, CLASS IN, TTL=60, IP    |
+-------------------------------------------------------------+
```

## Failure Modes

- **Circular Pointer Loops**: Malicious or corrupted packets could contain a pointer pointing back to itself or creating an infinite loop (e.g. offset A points to offset B which points back to offset A). Parsers should protect against infinite recursion via depth limiting or visited offset tracking.
- **Out-of-Bounds Pointer Offset**: A pointer specifying an offset beyond the valid buffer length or forward into unparsed packet data. The parser must check `pointer < buffer.limit()` before seeking.
- **Failure to Restore Buffer Position**: If the parser seeks to the pointer target and fails to restore the cursor to the byte following the pointer, parsing of subsequent records (`QTYPE`, `QCLASS`, or following questions) will read from the wrong location.
- **Signed Byte Sign Extension**: In Java, casting `(len & 0x3F) << 8` when `len` is a signed byte can produce sign-extension bugs. Using `Byte.toUnsignedInt()` ensures proper bitwise arithmetic.

## Tradeoffs

- **Recursive Pointer Resolution vs Iterative Loop**: Recursive resolution is concise and naturally handles arbitrary suffix chains, but requires recursion depth tracking to prevent stack overflow on circular pointers. Iterative pointer chasing with a hop counter is safer against hostile payloads.
- **Uncompressed vs Compressed Responses**: Re-encoding domain names without compression in the response is computationally cheaper and completely compliant with RFC 1035 for responses well under 512 bytes. Compressing responses saves bandwidth but requires maintaining an offset dictionary.

## Java Specifics

- `(len & 0xC0) == 0xC0`: Tests whether the two most significant bits are set to `11`.
- `int pointer = ((len & 0x3F) << 8) | Byte.toUnsignedInt(buffer.get())`: Unpacks the 14-bit unsigned offset across 2 octets.
- `int savedPos = buffer.position()` and `buffer.position(savedPos)`: Saves and restores the `ByteBuffer` cursor around pointer indirection.
- `buffer.position(pointer)`: Repositions the buffer's reading index to an absolute offset within the wrapped byte array.

## Rebuild Checklist

- [ ] Inspect length byte `len = Byte.toUnsignedInt(buffer.get())`.
- [ ] If `(len & 0xC0) == 0xC0`, read second byte `int b2 = Byte.toUnsignedInt(buffer.get())` and compute `pointer = ((len & 0x3F) << 8) | b2`.
- [ ] Save current `buffer.position()`.
- [ ] Jump to `buffer.position(pointer)` and recursively resolve remaining labels.
- [ ] Restore saved buffer position so parsing can proceed to `QTYPE` and `QCLASS`.
- [ ] Parse all questions according to `header.getQdCount()`.
- [ ] Generate matching answer records for all resolved questions.
- [ ] Serialize full response message with updated `QDCOUNT` and `ANCOUNT`.
