# Stage 1: Setup UDP server

## Problem Solved

DNS servers communicate primarily over UDP (User Datagram Protocol), a connectionless transport protocol suited for lightweight request-response interactions.

The server must bind a UDP datagram socket to port `2053`, enter an event loop to receive incoming datagram packets from clients, and echo or acknowledge by sending a response packet back to the client's socket address.

## Concepts

- **UDP Datagrams** - Unlike TCP streams, UDP is connectionless and message-oriented. Each packet (datagram) is independently routed, with message boundaries preserved by the OS transport stack.
- **Datagram Binding** - Binding associates a local UDP port (`2053`) with the process, allowing the OS networking stack to deliver incoming UDP datagrams addressed to this port.
- **Stateless Communication** - The server does not maintain a "connection" state with the client. The client's return address (`SocketAddress` containing IP and ephemeral port) is extracted directly from the incoming datagram packet.
- **Buffer Allocation** - A fixed-size byte buffer (512 bytes, matching the traditional maximum DNS UDP payload specified in RFC 1035) is pre-allocated to hold the received packet payload.

## Wire Format / Protocol

In this foundational stage, no application-layer DNS parsing is enforced.
The server receives an incoming UDP datagram packet on port `2053` and sends back a response packet to `packet.getSocketAddress()`.

```
+-------------------------------------------------------------+
| UDP Header (Source Port, Dest Port 2053, Length, Checksum)  |
+-------------------------------------------------------------+
| Payload: Arbitrary test payload or blank 512-byte buffer    |
+-------------------------------------------------------------+
```

## Failure Modes

- **Port Conflict** - If port `2053` is already bound by another process or previous run, `DatagramSocket` construction throws `BindException` / `IOException`.
- **Buffer Overflow / Truncation** - If incoming datagram exceeds buffer size, extra bytes are discarded by the UDP layer without error indication. 512 bytes is standard for RFC 1035 UDP DNS.
- **Client Unreachability** - If sending a datagram to an unreachable client address, UDP silently drops packets unless ICMP port unreachable is returned.
- **Resource Leaks** - Failing to enclose `DatagramSocket` in try-with-resources or manage cleanup will leave port 2053 occupied.

## Tradeoffs

- **UDP vs TCP** - UDP is faster, has lower latency with zero handshake overhead, and requires less server memory per query. TCP is reserved for DNS zone transfers or packets exceeding UDP truncation limits (EDNS0 / RFC 6891).
- **Blocking vs Non-blocking (NIO)** - Simple blocking `receive()` in a loop is minimal and correct for sequential query handling; non-blocking `DatagramChannel` or multi-threaded dispatch scales for high-throughput production servers.

## Java Specifics

- `java.net.DatagramSocket` - Represents a socket for sending and receiving datagram packets.
- `new DatagramSocket(2053)` - Binds the datagram socket to local port 2053.
- `java.net.DatagramPacket` - Encapsulates a byte array buffer, length, and destination `SocketAddress`.
- `serverSocket.receive(packet)` - Blocks until a datagram is received into the supplied packet buffer.
- `packet.getSocketAddress()` - Retrieves the remote client IP and port to which the response must be sent.
- `serverSocket.send(responsePacket)` - Transmits the response datagram through the bound socket.
