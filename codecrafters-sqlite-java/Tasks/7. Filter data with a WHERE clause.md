# Stage 7: Filter data with a WHERE clause

## In one line
Parse an optional equality `WHERE` filter clause, locate the target filter column in the table schema, perform a full table scan over leaf cells, evaluate predicate matching against decoded column values, and conditionally emit the projected row.

## Self-test (cover the answers below and answer these first)
- Why is a full table scan necessary to evaluate a WHERE clause when no secondary index exists?
- How does the engine evaluate a WHERE filter on a column that does not appear in the query's SELECT projection list?
- Why must string literals in SQL WHERE clauses have their enclosing quotes stripped before being compared against record values on disk?
- How does predicate evaluation interact with an `INTEGER PRIMARY KEY` column that aliases `rowid`?
- What happens when a row's column value is SQL `NULL` and compared via an equality predicate (`=`)?
- Why must `SELECT count(*)` bypass the page header's $O(1)$ cell count optimization whenever a WHERE clause is present?

## The problem it solved
In Stage 6, our engine performed unconditional sequential scans, projecting and printing every single row stored in the table root page. Real-world relational queries filter rows using selection predicates (`WHERE col = 'val'`). We now implement the relational algebra selection operator ($\sigma$), parsing equality conditions, resolving the filter column against the schema, comparing candidate row values, and skipping rows that do not satisfy the predicate.

## Concepts (the transferable part)
- **Relational Selection Operator ($\sigma$)** — Filters candidate rows based on a boolean predicate. Without an auxiliary index structure, a storage engine must perform a sequential full-table scan, evaluating the predicate against every record on the page ($O(N)$).
- **Decoupling Predicate Evaluation from Projection** — In SQL, any column defined in the table schema can appear in the `WHERE` clause, regardless of whether it is requested in the `SELECT` list. Unpacking the complete physical record into a random-access row array enables the engine to evaluate predicates on non-projected columns before emitting projected attributes.
- **SQL Literal Normalization & Quoting** — SQL queries denote string literals with enclosing single quotes (e.g. `'Yellow'`), while disk storage formats store raw UTF-8 byte sequences without quotes. Predicate evaluation requires stripping outer single or double quotes and unescaping internal escape sequences (e.g., `''` -> `'`) prior to comparison.
- **Three-Valued Logic & NULL Semantics** — In SQL, comparing any value to `NULL` via `=` evaluates to `UNKNOWN` (falsy in a `WHERE` clause). When a column contains `NULL` (serial type 0 on non-PK columns), equality tests against any literal must safely evaluate to false without throwing null pointer exceptions.
- **Header Cell Count Invalidation under Predicates** — B-tree page headers maintain an exact count of leaf cells on the page, enabling $O(1)$ execution for unfiltered `SELECT count(*)`. However, as soon as a `WHERE` filter is introduced, header metadata is insufficient; the engine must scan cells and tally matching rows.

## What breaks it (failure modes)
- **Filtering on Non-Projected Columns** — Queries like `SELECT name FROM apples WHERE color = 'Yellow'` project `name` but filter on `color`. If the decoder only unpacks columns present in `targetColIndices`, `color` is omitted and the filter cannot be evaluated.
- **Identifier Quoting vs Literal Quoting Confusion** — Column names may use identifier quotes (`"color"`, `[color]`, `` `color` ``) while values use literal quotes (`'Yellow'`). Failing to strip identifier quotes from the column or improperly stripping internal quotes from values causes lookup mismatches.
- **INTEGER PRIMARY KEY Column in Predicates** — If the WHERE clause targets a table's primary key (e.g. `WHERE id = 2`), SQLite serializes the value as the cell's `rowid` rather than inside the payload body (serial type 0). If the engine does not alias `rowid` into the row array, the column evaluates to `null` and misses matches.
- **Case Sensitivity of String Comparisons** — In SQLite, SQL keywords, table names, and column identifiers are case-insensitive, but string literal equality (`=`) is case-sensitive by default (unless explicitly defined with `COLLATE NOCASE`). Comparing filter values with `equalsIgnoreCase` would incorrectly match `'yellow'` against `'Yellow'`.
- **Fast Count Cache Trap** — Returning the 2-byte cell count from page header offset `103` when `WHERE` is present results in returning the total row count rather than the filtered row count.

## Tradeoffs
- **Full Table Scan vs Index B-Tree Lookup** — A full table scan evaluates every record sequentially on disk ($O(N)$). When tables grow large, databases create secondary index B-trees mapping indexed column values to `rowid`s, reducing lookup time to $O(\log N)$ or $O(K + \log N)$ where $K$ is the number of matching rows.
- **Unified String Representation vs Strongly-Typed Predicate AST** — Comparing values as normalized strings (`"1" == "1"`, `"Yellow" == "Yellow"`) avoids complex runtime type polymorphism across integers, floats, and strings for simple equality tests, at the minor cost of string formatting overhead.

## Storage / Protocol format

### Query Execution Pipeline: Selection ($\sigma$) and Projection ($\pi$)
```
SQL Query: SELECT name, color FROM apples WHERE color = 'Yellow'
Schema:    [0: id (PK), 1: name (text), 2: color (text)]
Filter:    whereColIndex = 2, whereValue = "Yellow"
Targets:   targetColIndices = [1, 2]

Page 1 Leaf Cells
  │
  ├─► Cell 0: [rowid: 1, payload: ["Granny Smith", "Light Green"]]
  │            Decoded row: ["1", "Granny Smith", "Light Green"]
  │            Predicate:   recordValues[2] == "Yellow" -> FALSE  ──► SKIP ROW
  │
  ├─► Cell 1: [rowid: 2, payload: ["Fuji", "Red"]]
  │            Decoded row: ["2", "Fuji", "Red"]
  │            Predicate:   recordValues[2] == "Yellow" -> FALSE  ──► SKIP ROW
  │
  ├─► Cell 2: [rowid: 3, payload: ["Honeycrisp", "Blush Red"]]
  │            Decoded row: ["3", "Honeycrisp", "Blush Red"]
  │            Predicate:   recordValues[2] == "Yellow" -> FALSE  ──► SKIP ROW
  │
  └─► Cell 3: [rowid: 4, payload: ["Golden Delicious", "Yellow"]]
               Decoded row: ["4", "Golden Delicious", "Yellow"]
               Predicate:   recordValues[2] == "Yellow" -> TRUE
               Projection:  recordValues[1] + "|" + recordValues[2]
                            "Golden Delicious|Yellow"             ──► EMIT ROW
```

## Java specifics — lookup, don't memorize
- `String.indexOf(String str)` — Finds the index of the first occurrence of the specified substring, useful for identifying comparison operators (`=` or `==`).
- `String.startsWith(String prefix)` / `String.endsWith(String suffix)` — Tests if this string begins or ends with the specified character or substring.
- `String.substring(int beginIndex, int endIndex)` — Extracts a substring from `beginIndex` (inclusive) to `endIndex` (exclusive), used to strip enclosing quotes.
- `String.replace(CharSequence target, CharSequence replacement)` — Replaces each substring matching literal target with replacement, used for unescaping SQL single quotes (`''` -> `'`).
- `String.equals(Object anObject)` — Performs exact, case-sensitive character equality comparison.
