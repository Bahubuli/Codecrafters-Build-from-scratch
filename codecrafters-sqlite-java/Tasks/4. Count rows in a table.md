# Stage 4: Count rows in a table

## In one line
Locate a user table's `rootpage` by querying `sqlite_schema` on page 1, decode integer serial types, jump to the table's root page offset, and read the cell count from its B-tree header.

## Self-test (cover the answers below and answer these first)
- Why does the B-tree page header start at offset 100 on page 1, but at offset 0 on all subsequent pages?
- How do you calculate the file offset of any page `P` given database `pageSize`?
- How are integer values encoded across serial types 1 through 9, and how do you decode a 24-bit signed integer (serial type 3)?
- Why does the cell count on a leaf table B-tree page directly correspond to the table's row count for single-page tables?
- What happens if a table name in `SELECT COUNT(*) FROM <table_name>` is specified with surrounding quotes or different casing?

## The problem it solved
Until now, our program could only inspect metadata about the database as a whole or list table names from `sqlite_schema`. We had no mechanism to navigate from metadata to actual user data pages. By extracting a table's `rootpage` from its schema record and reading that page's B-tree header, we can now execute our first real SQL query: `SELECT COUNT(*) FROM <table_name>`.

## Concepts (the transferable part)
- **Root Page Pointer** — In B-tree storage engines, every table or index is identified by the page number of its root node (`rootpage`). All reads and writes for that object begin by traversing from this root page.
- **Page Offset Calculation** — SQLite uses 1-based page indexing. Page `P` starts at byte offset `(P - 1) * pageSize` in the database file.
- **Header Offset Discrepancy** — Page 1 is special because it embeds the 100-byte database header. Thus, page 1's B-tree header is located at offset 100, whereas all other pages (`P >= 2`) have their B-tree header starting at offset 0 of that page.
- **Integer Serial Types (1–9)** — SQLite stores integers in variable widths depending on their magnitude (1, 2, 3, 4, 6, or 8 bytes big-endian two's complement, plus constants 0 and 1 requiring zero payload bytes).
- **Leaf Page Cell Count as Row Count** — In a leaf table B-tree (`0x0D`), each cell holds a row record and rowid. For tables small enough to fit on a single page, the 2-byte cell count at B-tree header offset 3..4 is exactly the row count.

## What breaks it (failure modes)
- **Offset 100 Bias on Page 2+** — Applying the 100-byte database header offset to pages other than page 1 will seek 100 bytes past the B-tree header, reading garbage data or cell payloads instead of the cell count.
- **Sign Extension Errors on 24-bit / 48-bit Integers** — Serial types 3 (24-bit) and 5 (48-bit) are signed integers. If the high bit of the first byte is set, failing to sign-extend to 32-bit or 64-bit yields incorrect positive values.
- **Serial Types 8 and 9 Byte Consumption** — Serial types 8 (value `0`) and 9 (value `1`) occupy 0 bytes in the record body. Attempting to read bytes for them will desynchronize buffer positions for subsequent columns.
- **Multi-Page Tables (Interior Pages)** — When a table exceeds a single page, its root page becomes an interior page (`0x05`) pointing to child pages. Stage 4 assumes single-page tables; interior traversal is required for multi-page tables (Stage 7).
- **Case and Delimiter Sensitivity** — SQL keywords and identifiers can vary in casing (`select count(*)` vs `SELECT COUNT(*)`), may contain spaces inside `COUNT ( * )`, or include trailing semicolons and quotes.

## Tradeoffs
- **Header Cell Count vs Full Page Scan** — Reading the 2-byte cell count from the page header executes in $O(1)$ time without parsing individual cells. However, this only reflects live rows if there are no deleted/freed cells and the table fits on a single leaf page.
- **Regex Query Matching vs Full SQL Parser** — Regex or whitespace tokenization is sufficient for basic `COUNT(*)` queries at this stage, avoiding the overhead of an AST parser while keeping the code lean until more complex queries are introduced.

## Storage / Protocol format

### Page Offset Formula
$$\text{Page Offset} = (P - 1) \times \text{pageSize}$$

### B-Tree Page Header Offsets
| Field | Offset on Page 1 | Offset on Page $P \ge 2$ | Size | Description |
|---|---|---|---|---|
| `page_type` | 100 | 0 | 1 B | `0x0D` = leaf table B-tree, `0x05` = interior table B-tree |
| `first_freeblock` | 101 | 1 | 2 B | Byte offset of first freeblock |
| `cell_count` | 103 | 3 | 2 B | Number of cells on this page (row count on leaf) |
| `cell_content_start` | 105 | 5 | 2 B | Offset to start of cell content area (0 = 65536) |
| `fragmented_bytes` | 107 | 7 | 1 B | Number of fragmented free bytes |

### Integer Serial Type Encodings
| Serial Type | Size | Data Type & Range |
|---|---|---|
| `1` | 1 byte | 8-bit signed two's complement integer ($-128$ to $127$) |
| `2` | 2 bytes | 16-bit big-endian signed integer ($-32768$ to $32767$) |
| `3` | 3 bytes | 24-bit big-endian signed integer ($-8388608$ to $8388607$) |
| `4` | 4 bytes | 32-bit big-endian signed integer |
| `5` | 6 bytes | 48-bit big-endian signed integer |
| `6` | 8 bytes | 64-bit big-endian signed integer |
| `8` | 0 bytes | Integer constant `0` |
| `9` | 0 bytes | Integer constant `1` |

### 24-Bit Big-Endian Integer Decoding
```java
int b0 = buffer.get(); // signed byte with sign extension in Java
int b1 = buffer.get() & 0xFF;
int b2 = buffer.get() & 0xFF;
int val = (b0 << 16) | (b1 << 8) | b2;
```

## Java specifics — lookup, don't memorize
- `RandomAccessFile.seek(long pos)` — Sets the file-pointer offset measured from the beginning of the file.
- `RandomAccessFile.readUnsignedShort()` — Reads two bytes from the file and returns an int in the range `0` to `65535`.
- `Pattern.compile(String regex, int flags)` — Compiles a regex with flags like `Pattern.CASE_INSENSITIVE`.
- `Matcher.find()` / `Matcher.group(int group)` — Finds matching patterns and extracts capture groups.
- `String.replaceAll(String regex, String replacement)` — Replaces all substrings matching regex (useful for stripping quotes or trailing semicolons).
