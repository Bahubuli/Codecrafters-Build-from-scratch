# Stage 2: Print number of tables

## In one line
Locate the root schema B-tree page header at offset 100 on page 1 and read the 2-byte big-endian cell count representing table entries.

## Self-test (cover the answers below and answer these first)
- Why does the B-tree page header on page 1 start at offset 100, while on every other page it starts at offset 0?
- What does each cell on page 1 (`sqlite_schema`) represent, and under what assumption does cell count equal table count?
- What byte offset within the B-tree page header contains the number of cells, and how many bytes is this field?

## The problem it solved
Previously, we only knew the page size geometry, but had zero visibility into the database contents or schema. Reading the cell count on page 1 allows determining how many schema records (tables) exist without doing a full parser pass over the schema DDL.

## Concepts (the transferable part)
- **Schema Table (`sqlite_schema`)** — The master catalog table stored on page 1 containing definitions for all tables, indexes, views, and triggers. In this challenge, each row corresponds to a table.
- **B-tree Page Header** — An 8-byte (for leaf) or 12-byte (for interior) header describing page type, freeblock offsets, cell count, and cell content area start.
- **Page 1 Offset Shift** — Page 1 is special because it embeds the 100-byte database header before the B-tree page header, shifting the page header from offset 0 to offset 100.

## What breaks it (failure modes)
- Assuming Page 1 B-tree header starts at 0 — Forgetting the 100-byte database header will read arbitrary file header fields as page header metadata.
- Multi-page schema tables — In real databases, `sqlite_schema` can overflow page 1 across multiple B-tree pages. Counting cells on page 1 only counts cells on that root page.
- Indexes / Views / Triggers — In full SQLite databases, `sqlite_schema` also stores rows for indexes, triggers, and views; cell count only equals table count when no auxiliary schema objects exist.
- Truncated file (< 105 bytes) — If the file does not contain the full 100-byte DB header + at least 5 bytes of the page header, reading bytes 103–104 will throw an `IndexOutOfBoundsException` or `EOFException`.

## Tradeoffs
- Reading cell count from page header vs full table scan — O(1) header lookup vs O(N) reading and parsing SQL schema strings in each cell payload. The header lookup is instantaneous but only works when schema fits on page 1 and contains only tables.

## Storage / Protocol format
| Byte Offset (File) | Byte Offset (Page 1 B-tree Header) | Size (Bytes) | Description |
|---|---|---|---|
| 100 | 0 | 1 | Page type flag (`0x0d` for leaf table B-tree, `0x05` for interior table B-tree) |
| 101–102 | 1–2 | 2 | Start of first freeblock (big-endian unsigned short, 0 if none) |
| 103–104 | 3–4 | 2 | Number of cells on this page (big-endian unsigned short) |
| 105–106 | 5–6 | 2 | Start of cell content area (offset from page start, 0 implies 65536) |
| 107 | 7 | 1 | Number of fragmented free bytes |

## Java specifics — lookup, don't memorize
- `InputStream.readNBytes(int len)` — reads up to `len` bytes from the input stream, blocking until all requested bytes are read or EOF is reached.
- `ByteBuffer.wrap(byte[] array, int offset, int length)` — creates a ByteBuffer view wrapping a slice of an array without copying bytes.
- `ByteBuffer.getShort()` — reads the next 2 bytes as a big-endian 16-bit signed short.
