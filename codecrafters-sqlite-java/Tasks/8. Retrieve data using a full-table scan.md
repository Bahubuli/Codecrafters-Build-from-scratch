# Stage 8: Retrieve data using a full-table scan

## In one line
Traverse multi-level table B-tree structures across interior pages (`0x05`) and leaf pages (`0x0D`) to perform an exhaustive full-table scan across thousands of records.

## Self-test (cover the answers below and answer these first)
- What is the fundamental difference between an interior table B-tree page (`0x05`) and a leaf table B-tree page (`0x0D`)?
- Where are the actual row payloads stored in a table B-tree: in interior cells, leaf cells, or both?
- What does an interior page cell contain, and what does the "rightmost child pointer" in the interior page header represent?
- In what order must child pages be traversed to guarantee ascending `rowid` ordering?
- How is the root page of a table identified when opening a database?

## The problem it solved
Prior to this stage, our queries operated on small tables that fit entirely on a single page (the table root leaf page). Real database tables grow beyond a single 4KB page and form a balanced multi-way tree (B+tree). To execute queries with selection predicates against multi-page tables, the engine must traverse interior pointer pages down to every leaf page containing row data.

## Concepts (the transferable part)
- **B+tree Hierarchy (Interior vs Leaf)** — In SQLite table B-trees (a B+tree variant), table data (payloads) resides exclusively in leaf pages (`0x0D`). Interior pages (`0x05`) contain only navigational routing keys (`rowid`s) and child page numbers.
- **Interior Cell Structure** — An interior table cell consists of:
  1. A 4-byte big-endian unsigned integer indicating the left child page number.
  2. A varint key indicating the highest `rowid` in that left child subtree.
- **Rightmost Child Pointer** — Because $K$ interior cells partition keys into $K + 1$ subtrees, the header of an interior page contains an explicit 4-byte pointer to the rightmost child page (for keys strictly greater than the last cell's key).
- **In-Order Tree Traversal** — To process rows sequentially by `rowid`, the engine traverses:
  $$\text{Child}_0 \to \text{Child}_1 \to \dots \to \text{Child}_{K-1} \to \text{Rightmost Child}$$
- **Full Table Scan ($O(N)$)** — Sequentially visiting every leaf page and evaluating filter conditions against every row. While simple, it scales linearly with table size.

## What breaks it (failure modes)
- **Omitting the Rightmost Child** — Forgetting to visit the page referenced by header offset 8 (`rightChildPage`) results in missing up to $\frac{1}{K+1}$ of the table's records.
- **Header Offset Off-by-One on Page 1** — If the table root page happens to be page 1, the B-tree header starts at byte offset 100, whereas on pages $> 1$ it starts at byte offset 0.
- **Interior Cell Pointer Offset** — On leaf pages (`0x0D`), the cell pointer array starts at offset 8. On interior pages (`0x05`), because of the 4-byte rightmost child pointer at offset 8..11, the cell pointer array starts at offset 12.
- **Assuming Fixed Tree Depth** — Assuming only 1 level of interior pages. Using recursive descent handles arbitrary B-tree depths naturally.

## Tradeoffs
- **Recursive Traversal vs Iterative Stack** — Recursive traversal is straightforward and uses minimal call stack depth (a B-tree of depth 4 can hold millions of rows). An explicit iterative cursor stack is used in production engines to support streaming `LIMIT`/`OFFSET` queries without holding the entire call stack.
- **Full Scan vs Index Lookup** — Scanning all leaf pages reads every data block from disk. Stage 9 will introduce secondary indexes to eliminate scanning unneeded pages.

## Storage / Protocol format

### Table B-tree Page Header Format
| Offset | Size | Description |
| :--- | :--- | :--- |
| `0` | 1 byte | Page type flag: `0x05` (Interior Table), `0x0D` (Leaf Table) |
| `1..2` | 2 bytes | First freeblock offset |
| `3..4` | 2 bytes | Number of cells on this page ($K$) |
| `5..6` | 2 bytes | Start of cell content area |
| `7` | 1 byte | Fragmented free bytes count |
| `8..11` | 4 bytes | *(Interior pages only)* Page number of the rightmost child |

### Interior Page Cell Layout (`0x05`)
```
+------------------------------------+----------------------------+
| 4-byte big-endian Left Child Page  | Varint RowID (Key)         |
+------------------------------------+----------------------------+
```

### Traversal Order
```
           [Interior Page (0x05)]
           /         |          \
      Cell 0       Cell 1    Rightmost Child
      (Page A)    (Page B)      (Page C)
        |           |              |
      [Leaf]      [Leaf]         [Leaf]
```

## Java specifics — lookup, don't memorize
- `ByteBuffer.getInt(int index)` — Reads a 4-byte big-endian signed integer from the specified buffer index.
- `databaseFile.seek((long) (pageNumber - 1) * pageSize)` — Positions the file pointer at the start of page $N$ using 64-bit long arithmetic to prevent integer overflow.
